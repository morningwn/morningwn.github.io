# Nacos Distro 协议是什么：原理、责任节点与工作流程

在 Nacos 作为注册中心的场景里，有一类数据变化非常频繁：

- 服务实例不断注册和注销。
- 临时实例持续发送心跳。
- 实例健康状态会快速变化。
- 服务列表需要尽快对消费端可见。

如果这类数据每次变化都走一条很重的强一致复制链路，集群写入成本会明显上升，心跳和注册吞吐也会被拖慢。

因此，Nacos 没有把所有注册中心数据都交给同一种协议处理，而是做了分层设计：

- 临时实例相关数据，主要使用 Distro。
- 持久实例相关数据，主要使用 Raft。

所以，Distro 协议并不是一个通用意义上的“强一致共识协议”，而是 Nacos 为高频、短生命周期、可接受短暂不一致的数据设计的一套 AP 风格分布式同步机制。

如果先用一句话概括它的本质，可以这样理解：

- Distro 通过“为数据分配责任节点，由责任节点接收主写入，再异步同步给其他节点”的方式，让临时实例数据在保证高可用的前提下逐步收敛。

## 一、Distro 协议到底解决了什么问题

要理解 Distro，先要看它面对的真实业务背景。

注册中心里的临时实例数据有几个非常鲜明的特点：

- 写多读多，而且写入非常频繁。
- 数据带有明显的时效性，晚几秒可能就已经过期。
- 即使出现短暂延迟，系统通常也还能依赖缓存、重试和心跳恢复。
- 比起“每次都绝对强一致”，系统往往更需要“先不要因为单点故障而无法注册和续约”。

这就带来一个核心取舍：

- 如果过于强调强一致，写路径会变重，吞吐和时延会受到影响。
- 如果完全不做约束，多节点同时处理同一份服务数据，又容易出现混乱。

Distro 要解决的就是这个中间问题：

- 既不能像无中心广播那样让每个节点都随意写同一份数据。
- 也不希望像强一致协议那样让每次心跳都必须经过多数派确认。

因此它采用了一条更适合注册中心临时数据的路径：

- 先确定谁负责这份数据。
- 再由负责节点处理这次变更。
- 最后把结果异步传播出去。

## 二、为什么 Nacos 不把临时实例也统一交给 Raft

这个问题很关键，因为只有理解了这点，才知道 Distro 的定位。

假设临时实例的每次注册、每次心跳、每次健康状态变化都走 Raft 这样的强一致流程，通常意味着：

- 写请求需要经过更重的复制与确认链路。
- 高频心跳会放大集群内部通信成本。
- 节点压力会随着实例规模增长更快上升。
- 在高频变更场景下，注册中心吞吐更容易成为瓶颈。

而临时实例的语义并不总是要求“所有节点在这一刻必须完全一致”。

很多时候，更现实的目标是：

- 服务能先注册上来。
- 心跳能先被及时处理。
- 其他节点在很短时间内完成收敛。
- 消费者最终拿到的新列表足够新、足够可用。

这就是 Distro 的设计前提。

换句话说，Nacos 不是不知道强一致更“严格”，而是判断出：

- 临时实例这类数据，更值得优先保住可用性和处理效率。

## 三、Distro 主要处理哪些数据

在 Nacos 命名服务场景里，Distro 主要面向的是临时实例相关数据，也就是 ephemeral instance 数据。

可以把它大致理解为下面几类：

- 临时实例的注册信息。
- 临时实例的心跳续约状态。
- 临时实例的健康状态变化。
- 与这些实例关联的服务目录视图。

这里有一个很容易混淆的点：

- Distro 并不是 Nacos 所有元数据的统一协议。
- 它主要服务于“变化频繁、依赖心跳、允许短暂不一致”的那一部分数据。

而更强调持久性、确定性和强一致的数据，通常不会交给 Distro。

## 四、Distro 的四个核心设计点

如果不展开源码，只从原理层面理解 Distro，最值得抓住的是四个点。

### 1. 数据会有责任节点

每一份服务相关数据，在集群中通常都会根据同一套映射规则，归属于某个责任节点。

你可以把这个责任节点理解成这份数据的 owner。

它的职责是：

- 作为这份数据的主处理入口。
- 负责接收对应的注册、心跳、注销等变更。
- 负责把变更结果传播给其他节点。

这样做的意义在于：

- 避免多个节点同时无序修改同一份临时实例数据。
- 让写路径有一个相对明确的归口。

### 2. 请求可以先打到任意节点

客户端并不一定知道某份数据的责任节点是谁，因此注册请求或心跳请求可能先到达任意一个 Nacos 节点。

这时，接收到请求的节点会先判断：

- 这份数据是不是由自己负责。

如果是，它就直接处理；如果不是，它就把请求转发给责任节点。

这意味着对客户端而言：

- 接入点可以比较灵活。
- 不需要把复杂的数据归属逻辑压到客户端侧。

### 3. 责任节点先本地写入，再异步同步

责任节点处理完这次变更后，不会要求所有节点都先完成多数派投票再返回成功。

相反，它更偏向这样的路径：

- 先更新本地临时实例状态。
- 再把这次变更异步同步到其他节点。
- 让其他节点的副本逐步收敛。

这正是 Distro 更偏 AP 的关键原因。

它带来的直接效果是：

- 写入链路更轻。
- 高频心跳更容易承载。
- 但短时间内不同节点看到的数据可能略有延迟。

### 4. 集群会做持续收敛与修复

Distro 并不是“一次转发成功就结束”的静态机制。

在真实运行中，集群成员变化、节点重启、网络抖动都可能导致副本短暂不齐。

因此 Distro 的另一个重要思想是：

- 数据不是要求每一刻都强同步，而是通过持续同步、校验和补齐，让集群最终收敛。

所以 Distro 更像一套“面向临时服务目录的分片写入加副本收敛机制”，而不是“所有写操作必须先达成多数共识”的协议。

## 五、Distro 的整体工作流程是怎样的

把它抽象成一条主链路，其实并不复杂：

1. 客户端发起注册、心跳或注销请求。
2. 请求先到达某个 Nacos 节点。
3. 节点判断自己是否为这份数据的责任节点。
4. 如果不是，则转发给责任节点。
5. 责任节点更新本地临时实例状态。
6. 责任节点把最新结果异步同步给其他节点。
7. 其他节点更新本地副本，整个集群逐步收敛。

可以用下面这张图理解：

```mermaid
flowchart LR
    A[客户端注册或心跳] --> B[任意 Nacos 节点]
    B --> C{是否为责任节点}
    C -->|是| D[更新本地临时实例状态]
    C -->|否| E[转发给责任节点]
    E --> D
    D --> F[异步同步到其他节点]
    F --> G[各节点本地副本逐步收敛]
    G --> H[消费者获取最新服务视图]
```

这张图里最核心的不是“转发”本身，而是这三个判断：

- 谁负责。
- 谁接主写。
- 什么时候同步给别人。

## 六、一次临时实例注册是怎么经过 Distro 的

下面把“服务注册”这条链路单独展开。

### 1. 客户端发起注册请求

服务实例启动后，客户端会把自己的服务名、IP、端口、集群、权重等元信息提交给 Nacos。

这时它打到的节点，不一定就是责任节点。

### 2. 接收节点判断数据归属

收到请求的节点会依据当前集群的映射规则判断：

- 这份服务数据是否应该由自己负责。

如果是，就继续处理；如果不是，就把请求转给真正负责的节点。

### 3. 责任节点更新实例状态

责任节点会把这次注册写入自己的服务目录数据结构中，例如：

- 新增对应实例。
- 记录实例元信息。
- 标记该临时实例为当前有效。

到这一步，这次注册就已经在主处理节点上成立了。

### 4. 结果异步传播到其他节点

责任节点随后会把这次变化同步给其他 Nacos 节点，让其他节点也拥有一份更新后的服务副本。

因此从全局上看，集群并不是“同时写成功”，而是：

- 先在责任节点生效。
- 再向其他节点扩散。

### 5. 消费者逐步感知到新服务视图

当副本收敛后，各节点对外提供的服务列表也会更新。订阅该服务的消费者随后就能拿到新的实例视图。

这也是为什么在注册中心场景里，经常会出现这样的描述：

- 服务实例已经注册成功。
- 但其他节点或部分消费者感知到它，可能会有一个很短的传播延迟。

## 七、心跳续约和健康状态为什么特别适合 Distro

临时实例真正高频的动作，不是注册，而是心跳。

服务一旦注册完成，后续通常会周期性发送心跳，用来证明：

- 实例还活着。
- 实例还应该继续留在服务列表里。

这类请求的特点非常鲜明：

- 次数多。
- 单次数据量小。
- 时效性很强。
- 一旦积压，影响会迅速放大。

如果把每次心跳都放到一条强一致的多数确认路径里，成本往往过高。因此 Distro 的责任节点模型就比较合适：

- 由责任节点集中处理心跳。
- 再把新状态异步同步给其他节点。

当某个实例长时间不再发送心跳时，责任节点会根据超时规则处理它，例如：

- 先标记为不健康。
- 随后从临时实例列表中移除。

然后这些变化再继续通过 Distro 链路传播出去。

## 八、节点宕机或网络抖动时，Distro 会发生什么

Distro 的价值，恰恰体现在异常场景里。

### 1. 非责任节点异常

如果异常的是一个非责任节点，那么对某份特定数据来说，主写路径并没有消失。

影响通常是：

- 这个节点本地副本可能暂时不新。
- 打到这个节点的部分请求需要重试或转发。
- 但整体服务注册与心跳处理能力通常还能维持。

### 2. 责任节点异常

如果异常的是责任节点，事情会更关键一些。

此时集群会基于当前可用节点重新形成数据归属关系，由新的责任节点接手这部分数据的处理。

在这个过程中，系统通常需要完成两件事：

- 让新的责任节点开始接收这部分写请求。
- 通过节点间的数据同步与补齐，让它恢复到可工作的数据视图。

这也是为什么 Distro 不是一次性写入逻辑，而是一套持续收敛机制。

### 3. 网络分区或短暂抖动

如果节点之间短时间通信异常，不同节点看到的服务实例状态可能会出现短暂差异。

例如：

- A 节点已经看到实例失效。
- B 节点还保留着旧副本。

这正是 Distro 为可用性付出的代价。

但在注册中心场景里，系统通常可以接受这种很短的窗口，因为：

- 实例本身会持续发心跳。
- 消费端通常有本地缓存和失败重试。
- 节点恢复通信后，副本会继续收敛。

## 九、Distro 与 Raft 的区别到底在哪里

很多人第一次接触 Nacos 时，最容易混淆的就是 Distro 和 Raft。

最直接的理解方式不是背定义，而是看它们分别服务什么目标。

| 对比维度 | Distro | Raft |
| --- | --- | --- |
| 主要处理对象 | 临时实例、心跳、健康状态等高频短生命周期数据 | 更强调持久性和一致性的元数据 |
| 一致性倾向 | 更偏 AP，允许短暂不一致 | 更偏强一致，强调多数派提交 |
| 写入路径 | 责任节点先处理，再异步同步 | Leader 处理后复制到多数节点再提交 |
| 性能取向 | 更轻量，适合高频写入 | 更严格，但写路径更重 |
| 异常时取舍 | 优先保持注册与续约能力 | 优先保证一致性正确性 |

因此，不能简单地说：

- Distro 比 Raft 弱。

更准确的说法应该是：

- 它们服务的数据类型不同。
- 它们面对的系统目标不同。
- 它们解决的问题也不同。

对 Nacos 来说，这不是“二选一”，而是“按数据特征分层使用”。

## 十、Distro 的优点和边界分别是什么

理解一个协议，不能只看优点，也要知道它不能做什么。

### 1. 优点

Distro 适合 Nacos 注册中心临时实例场景，主要因为它具备下面几个优势：

- 写入链路较轻，适合高频心跳与实例变化。
- 对单点异常更有弹性，整体可用性较高。
- 客户端不必感知复杂的责任节点分配细节。
- 集群可以通过持续同步逐步恢复一致视图。

### 2. 边界

它的边界也同样明确：

- 它不追求每一时刻所有节点都绝对一致。
- 它不适合承载必须强一致提交的关键状态。
- 在网络抖动或节点切换时，短时间内可能看到旧数据。

所以，Distro 适合的是：

- 服务注册中心里的临时目录数据。

而不适合的是：

- 那些一旦读到旧值就可能导致严重业务错误的强一致核心数据。

## 十一、可以怎样用一句话记住 Distro

如果最后只记一个结论，可以记这句话：

- Distro 是 Nacos 为临时实例设计的一套 AP 风格同步机制，它通过责任节点接主写入、异步复制和持续收敛，来在高频变更场景下兼顾可用性与最终一致性。

把这句话拆开，其实就是三层意思：

- 它服务的是临时实例数据。
- 它优先保证高可用和处理效率。
- 它接受短暂不一致，再通过同步让集群逐步收敛。

理解到这里，Distro 协议的定位、价值和边界基本就清楚了。
