倒排索引是全文检索系统的基础数据结构。它把文本分析结果预先组织成“词项 → 文档”的映射，使查询能够从关键词直接定位候选文档。本文通过一组简单文档说明倒排索引的结构和查询过程，并分析它解决的问题、适用条件与限制。

## 倒排索引是什么

倒排索引中的“倒排”描述映射方向发生了反转，并不表示索引内容按倒序排列。

| 组织方式 | 入口 | 保存的关系 | 适合回答的问题 |
| --- | --- | --- | --- |
| 正向组织 | 文档 | 文档 → 词项 | 一篇文档包含哪些词项 |
| 倒排组织 | 词项 | 词项 → 文档 | 哪些文档包含指定词项 |

一个基础倒排索引由两部分组成：

- **词项字典（term dictionary）**：保存所有可检索的词项，以及指向对应倒排列表的信息。
- **倒排列表（postings list）**：保存包含该词项的文档编号。列表中的一条记录称为倒排项（posting）。

基础倒排项只需要包含文档编号。实际系统还可以保存以下扩展信息：

| 扩展信息 | 含义 | 主要用途 |
| --- | --- | --- |
| 词频 | 词项在当前文档中的出现次数 | 相关性评分 |
| 位置 | 词项在 token 序列中的位置 | 短语和邻近查询 |
| 字符偏移量 | 词项在原文中的字符范围 | 结果高亮 |

这些信息扩展了查询能力，但不是倒排索引最小定义的必要部分。保存的信息越多，索引体积通常也越大。

## 一组文档如何转换为倒排索引

假设系统中有三篇文档。为避免具体中文分词规则影响示例，下面直接列出每篇文档经过文本分析后得到的词项：

| 文档编号 | 分析后的词项 |
| --- | --- |
| D1 | 搜索、引擎、索引 |
| D2 | 文本、搜索、索引 |
| D3 | 数据库、索引、查询 |

系统按词项聚合文档编号后，可以得到如下倒排结构：

| 词项 | 倒排列表 |
| --- | --- |
| 搜索 | D1、D2 |
| 引擎 | D1 |
| 索引 | D1、D2、D3 |
| 文本 | D2 |
| 数据库 | D3 |
| 查询 | D3 |

建立倒排索引通常包含以下步骤：

1. 读取需要建立索引的文档字段。
2. 将文本切分成 token，并按配置执行大小写转换、词形归一化或停用词过滤等处理。
3. 将处理结果作为词项，生成“词项—文档编号”记录。
4. 按词项聚合记录，形成词项字典和倒排列表。

文本分析规则决定哪些词项会进入索引。索引阶段将英文统一为小写，而查询阶段保留大写时，查询词就可能无法命中。因此，两个阶段通常需要采用相同或兼容的分析规则。

## 查询如何执行

查询“搜索 索引”时，系统先对查询文本执行分析，得到“搜索”和“索引”两个词项，再分别读取它们的倒排列表：

- 搜索：D1、D2
- 索引：D1、D2、D3

如果查询要求两个词项同时出现，系统对列表求交集，结果为 D1、D2；如果只要求至少出现一个词项，则求并集，结果为 D1、D2、D3。

倒排列表通常按文档编号排序，因此多个列表可以顺序合并。保存位置信息时，系统还可以检查词项是否相邻或保持指定顺序，从而支持短语查询。

倒排索引在这里负责产生候选文档。候选文档如何排序，则由相关性模型结合词频、文档频率和字段长度等信息计算；评分模型不等同于倒排索引本身。

## 倒排索引解决了什么问题

倒排索引改变了文本查询的访问路径。没有索引时，查找包含某个词项的文档通常需要读取并检查每篇文档；建立倒排索引后，系统可以先查询词项字典，再读取对应的文档编号集合。

在此基础上，它主要提供三类能力：

1. **全文匹配**：快速找到包含指定词项的候选文档。
2. **条件组合**：通过倒排列表的交集、并集和差集实现 AND、OR、NOT 等布尔条件。
3. **检索扩展**：借助词频、位置和偏移量支持相关性评分、短语查询与高亮。

倒排索引解决的是“从词项查找文档”的问题。它不会直接理解文本语义，最终效果仍取决于文本分析、查询表达和评分规则。

## 优点与适用条件

### 减少查询阶段的原文扫描

查询可以通过词项字典直接定位倒排列表，不必每次都扫描全部原文。这种方式适合文档数量较多、全文查询频繁，并且可以接受预先建立索引的场景。

### 适合组合关键词条件

排序后的倒排列表便于执行交集、并集等集合运算。保存位置和词频后，同一索引还可以为短语匹配与相关性排序提供输入。

### 只记录实际存在的词项关系

完整的“词项—文档”矩阵通常包含大量空关系。倒排索引只记录词项实际出现在哪些文档中，避免保存所有空项。词项字典、倒排项和扩展统计仍会占用额外空间。

### 查询性能可以通过预计算与压缩优化

文档频率等统计值可以在索引阶段计算，文档编号序列也可以压缩存储。查询阶段只需访问相关词项的数据。不过，实际性能仍取决于倒排列表长度、查询词数量、缓存和存储实现，不能仅根据是否使用倒排索引判断。

## 缺点与限制

### 写入和存储成本更高

建立索引需要执行文本分析、记录聚合和数据写入。保存词频、位置和偏移量会进一步增加索引体积。索引能力越丰富，写入时间与磁盘占用通常越高。

### 更新和删除需要维护词项关系

文档内容变化后，旧的词项关系需要失效，新的关系需要加入。具体实现可能通过追加、删除标记和数据合并处理更新，因此频繁修改会带来额外 I/O 和写放大。

### 匹配结果依赖文本分析

倒排索引匹配的是分析后的词项。分词粒度、大小写处理、同义词或词形归一化配置不合适时，可能漏掉预期结果，也可能生成过多候选文档。索引阶段与查询阶段的分析规则不兼容，也会造成无法命中。

### 高频词的倒排列表较长

一个词项出现在大部分文档中时，对应列表会占用更多空间，并增加集合运算和候选处理成本。压缩与查询优化可以降低开销，但不能改变高频词区分度较低的事实。

### 不能直接提供语义理解

传统倒排索引判断词项是否匹配。任意子串、拼写纠错、模糊匹配和语义相似度搜索需要额外的词项组织、查询算法或向量索引。

## 与其他索引结构的边界

现代搜索系统会按数据类型和访问方式组合多种结构，倒排索引只是其中之一：

| 需求 | 更适合的数据组织方式 |
| --- | --- |
| 按字段排序、聚合 | 面向文档的列式数据，例如 Lucene DocValues |
| 数值、日期或地理范围查询 | 点值索引，例如 Lucene 的 KD-tree/BKD 结构 |
| 向量相似度与语义近邻搜索 | 向量索引，例如近似最近邻图结构 |

这些结构可以与倒排索引同时存在。使用 Elasticsearch 不代表所有字段和查询都由倒排索引处理。

## 总结

倒排索引以词项为入口，记录包含该词项的文档。它把文本分析和关系组织提前到索引阶段，使全文查询能够直接获取候选文档，并通过倒排列表组合多个关键词条件。

这种访问方式用额外存储、写入处理和更新维护换取查询效率。它适合词项驱动的全文检索，但不能替代排序聚合所需的列式数据、数值范围索引或语义检索使用的向量索引。是否采用倒排索引，应由字段类型和主要查询方式决定。
