删除一批键以后，Redis 报告的数据内存已经下降，操作系统看到的进程内存却没有明显变化。这种现象很容易让人得出两个结论：要么 Redis 没有真正释放对象，要么统计数据不可信。

多数时候，这两个结论都不对。

问题在于，“对象已释放”和“物理内存已归还”之间隔着内存分配器。Redis 知道一个字符串、一张哈希表什么时候不再需要；分配器知道一小块地址怎样复用；操作系统管理的却是更大粒度的内存页。上一层完成释放，并不意味着下一层已经具备回收条件。

Redis 管理内存碎片的思路，正是建立在这三个层次之上：先让分配器复用空闲块；碎片严重时，由 Redis 搬迁仍然存活的对象，把空闲空间集中起来；当完整页面终于可以释放时，再由分配器将它们清理或归还给操作系统。

## 一次释放要经过三本账

理解碎片之前，需要先区分三种常被混在一起的内存。

第一种是 Redis 通过分配器申请、当前仍记在账上的内存。`INFO memory` 中的 `used_memory` 属于这一层。它统计 Redis 使用分配器得到的字节数，已经包含分配器为单次分配向上取整产生的内部浪费，但不等于整个进程的物理内存。

第二种是分配器管理的内存。以 jemalloc 为例，它不会把每次申请都直接交给操作系统，而是把内存组织成不同大小等级的块和承载这些块的页面。某个对象释放后，它占用的块可以回到分配器手中，等待下一次相近大小的申请。此时 `used_memory` 可以下降，分配器管理的页面却仍然存在。

第三种是进程的常驻内存 RSS，即此刻驻留在物理内存中的页面。Redis 的代码、共享库、线程栈以及不经过主分配器统计的内存也会进入 RSS。因此，RSS 与 `used_memory` 的差额不全是碎片。

```mermaid
flowchart LR
    A["Redis：对象是否仍在使用"] --> B["分配器：内存块是否可复用"]
    B --> C["分配器：页面是否仍需保留"]
    C --> D["操作系统：页面是否驻留"]
```

当 Redis 删除一个键时，首先变化的是最左边。其后的变化取决于分配器能否复用或释放相关页面，以及操作系统如何处理这些页面。把三个层次压成一个数字，正是许多误判的起点。

## 碎片究竟碎在哪里

“碎片”并不是一种单一的浪费。至少要区分内部碎片与外部碎片。

### 内部碎片：分到的块比对象稍大

通用分配器通常按大小等级管理小对象。假设一个对象需要 50 字节，而合适的大小等级提供 56 或 64 字节，那么块内剩余的部分暂时不能交给另一个对象使用。这就是内部碎片。

大小等级并非粗心的设计。若要为每一种长度维护刚好合适的块，查找、记录和复用成本都会上升。分配器用少量空间换取更稳定的分配速度、更简单的元数据和更高的复用概率。

因此，内部碎片是一次分配内部的差额。把对象从一个同等级的块复制到另一个块，通常不会消除这个差额。Redis 的主动碎片整理主要瞄准的不是它。

### 外部碎片：空房间很多，却退不掉整层楼

外部碎片发生在多个分配之间。可以把分配器管理的页面想象成一栋公寓楼，把小内存块想象成房间。随机删除对象后，每层楼都可能空出几个房间，但每层又都留着住户。

从房间数量看，空闲空间不少；从整层楼看，却没有一层能够完整退还。新对象的大小若与空房间不匹配，分配器还可能需要申请新页面。于是进程一边保留大量零散空闲块，一边继续增长。

这也是“删除了 2 GB 数据，RSS 为什么没有下降 2 GB”的根本原因。释放的 2 GB 可能散落在许多仍含存活对象的页面中。分配器可以在以后复用这些空间，却很难立刻把页面交还给操作系统。

## 只等待复用为什么不够

分配器保留空闲块并不一定是坏事。工作负载再次增长时，新对象可以使用旧块，RSS 可能在一段时间内保持不变。若每次释放都立即触发系统调用和页面回收，随后的重新申请反而会增加开销。

问题出现在内存形状发生变化时。例如，一次流量高峰创建了大量某种尺寸的对象，低峰期又随机删除其中大部分；之后新增的却是另一种尺寸的对象。旧空闲块可能迟迟找不到合适用途。即使对象尺寸不变，只要少数存活对象均匀散布在大量页面上，页面也无法整体释放。

此时，被动等待只能寄希望于未来的申请恰好填满洞。Redis 的主动碎片整理要做的，是改变存活对象的分布，让“许多页面各空一点”逐渐变为“少数页面仍在用，另一些页面完全空闲”。

## 主动整理的本质是搬家

传统的压缩式垃圾收集器能够移动对象，因为运行时掌握对象之间的引用，搬迁后可以统一修复引用。Redis 主要用 C 编写，大量结构通过普通指针连接；jemalloc 只看得到一个个分配地址，并不知道哪个地址是字典节点、字符串内容或跳表节点，更不知道还有谁指向它。

所以分配器不能擅自移动 Redis 对象。真正的协作方式是：分配器帮助判断某个分配是否值得迁移，Redis 负责理解对象并修复引用。

一次成功的迁移可以抽象为五步：

1. Redis 扫描到一个仍然存活的分配。
2. 向 jemalloc 询问：移动这个分配是否有助于降低碎片。
3. 如果值得移动，申请一块相同用途的新内存并复制内容。
4. 把 Redis 内部指向旧地址的引用改为新地址。
5. 释放旧内存块。

最关键的是第四步。若复制后漏改一个指针，旧地址释放后就会形成悬空指针；若某块内存存在 Redis 无法安全识别或修复的引用，它就不能按同样方式迁移。

因此，主动碎片整理不是扫描整个地址空间后执行一次通用 `memcpy`。Redis 必须按对象结构分别处理：顶层键和值、字典及其条目、字符串、列表、集合、有序集合、流等结构都有不同的内部指针。模块若希望自己的数据参与整理，也需要通过模块 API 描述如何迁移相关分配。Redis 8 的模块 API 仍明确把整理描述为“申请新块、复制内容”，并对引用计数等不可安全迁移的情况设置限制。

迁移也不保证每次都成功。分配器可能判断当前地址没有搬迁价值，Redis 也可能因为对象状态或时间预算跳过它。`active_defrag_hits`、`active_defrag_misses` 以及键级别的对应指标，记录的正是成功重分配与跳过等结果，而不是一次整理必然完成的承诺。

## 搬到哪里，为什么会更整齐

若只是随便申请一个新地址，再释放旧地址，碎片可能从一个地方搬到另一个地方。主动整理之所以有效，依赖 jemalloc 对自身页面利用情况的了解。

jemalloc 按大小等级组织小分配，同一等级的对象更容易被放进合适的 slab。Redis 随源码携带的 jemalloc 提供了主动整理所需的提示能力：对于给定地址，分配器可以根据该地址所在区域的利用情况判断迁移是否可能有益。Redis 不需要、也不应该自行猜测分配器的全部内部布局。

可以仍用公寓来理解：物业比住户更清楚哪些楼层最空，Redis 则知道怎样通知住户、搬运行李并修改门牌记录。双方协作后，住户从低利用率楼层迁往更合适的位置，原楼层才有机会全部腾空。

这也解释了主动整理为何依赖特定的 jemalloc 能力。使用 libc malloc、tcmalloc 或不含对应支持的 jemalloc 构建时，Redis 不能假定自己拥有同样的候选判断和迁移行为。`INFO memory` 的 `mem_allocator` 可以说明实例实际使用的分配器。

## Redis 为什么一点一点地整理

对象搬迁会申请内存、复制字节、修改指针并释放旧块。这些工作消耗 CPU 和内存带宽；迁移过程中，新旧分配还会短暂共存。若 Redis 为了整理碎片长时间占住主线程，请求延迟可能比节省下来的内存更先成为问题。

因此，主动整理采用渐进式工作方式。Redis 先根据分配器的 `allocated` 与 `active` 统计估算可整理的外部碎片：前者表示已经分配给对象的空间，后者表示承载这些分配的活跃页面空间，两者之差近似反映活跃页面中的空洞。只有碎片比例和浪费字节数同时越过下限，整理才值得启动。这样可以避免在实例很小、比值看起来很高但绝对只浪费几 MB 时频繁工作。

开始以后，Redis 会把扫描与迁移拆成许多小段，并为单段工作设置时间边界。Redis 7.x 的实现把整理嵌入周期性维护过程；当前主线实现进一步明确地把工作组织为分阶段任务，并向每个阶段传入结束时间，以限制单次整理造成的延迟。具体调度结构在版本间会变化，但原则没有变化：每次只做有限工作，保存扫描进度，随后继续。

整理强度也不是简单的开关。配置中的下阈值表示从何种碎片程度开始投入最低努力，上阈值表示何时提升到最大努力；处于两者之间时，目标 CPU 比例随碎片程度增加。`active-defrag-cycle-min` 和 `active-defrag-cycle-max` 给出努力范围，`active_defrag_running` 报告当前计划投入的 CPU 百分比，而不是“已经整理了多少百分比”。

截至 Redis 7.4 的示例配置，主动整理默认关闭；默认要求至少约 100 MB 的碎片浪费且碎片比例达到下阈值 10% 才开始考虑整理，努力范围为 1% 到 25%。这些是默认策略，不是普适的最佳值，也不应掩盖本文更重要的结论：两个门槛约束“值不值得做”，动态努力约束“现在做多快”。

## 碎片率为什么经常骗人

最常见的指标 `mem_fragmentation_ratio` 定义为：

$$
R_{process}=\frac{used\_memory\_rss}{used\_memory}
$$

其中，$used\_memory\_rss$ 是进程常驻内存，单位为字节；$used\_memory$ 是 Redis 通过分配器记账的已分配内存，同样以字节计。这个比值没有单位。

它适合回答“进程驻留内存比 Redis 记账内存大多少”，却不等于分配器的纯外部碎片率。分子还含有代码、共享库、栈等进程开销；分母也包含单次分配内部的向上取整。数据集很小时，几 MB 固定开销就能把比值显著抬高。经历过内存峰值后，RSS 的下降又可能落后于 `used_memory`，使比值暂时很大。

要观察分配器内部的层次，更有用的是三组数：

| 指标 | 含义 | 主要差额 |
| --- | --- | --- |
| `allocator_allocated` | 分配器交给 Redis 的内存，包含内部碎片 | 与 `used_memory` 通常接近 |
| `allocator_active` | 承载当前分配的活跃页面 | 减去 `allocated`，近似活跃页面中的外部碎片 |
| `allocator_resident` | 分配器当前驻留的内存 | 减去 `active`，表示分配器保留、可能可清理的页面 |

由此可以得到两个比值：

$$
R_{frag}=\frac{allocator\_active}{allocator\_allocated}
$$

$$
R_{rss}=\frac{allocator\_resident}{allocator\_active}
$$

$R_{frag}$ 更接近 Redis 官方所称的“真正的外部碎片指标”；$R_{rss}$ 较高，则更多意味着分配器已经拥有不再活跃、可能随后归还给操作系统的页面。最后，`used_memory_rss / allocator_resident` 的差异才指向堆外的进程 RSS 开销。

所以，分析内存不应只问“总比值是否超过 1.5”，而应沿链条追问：浪费发生在活跃页面内部，还是页面已经空闲但仍由分配器保留，抑或根本不属于主分配器？比值还必须和差额字节数一起看。比例很高但只差几 MB，通常不构成与大型实例相同的问题。

## 主动整理与页面回收不是同一个动作

主动整理解决的是“空闲块过于分散”：它搬迁存活对象，使一些页面更接近完全空闲。

页面回收解决的是“页面已经不再活跃，但还驻留着”：jemalloc 可以在后台清理这类页面，Redis 的示例配置默认启用 `jemalloc-bg-thread`；`MEMORY PURGE` 则请求分配器主动释放脏页。官方文档也明确指出，`MEMORY PURGE` 只在分配器支持时生效。

二者不能互相替代。若每个页面仍有一个活对象，执行页面清理不会凭空把对象挪走；若整理已经腾出页面，但分配器尚未清理，RSS 也不一定在整理结束的瞬间下降。可以把完整过程概括为：

```mermaid
flowchart LR
    A["随机删除后产生零散空洞"] --> B["分配器优先复用空闲块"]
    B --> C{"外部碎片仍值得处理？"}
    C -- "否" --> B
    C -- "是" --> D["Redis 迁移存活对象并修复指针"]
    D --> E["部分页面变为非活跃或可释放"]
    E --> F["jemalloc 后台清理或 MEMORY PURGE"]
    F --> G["操作系统侧 RSS 有机会下降"]
```

图中的“有机会”很重要。RSS 是操作系统视角的结果，不是 Redis 对每一次释放的同步确认。

## 这套机制做不到什么

主动碎片整理不是免费的内存压缩，也不能保证 RSS 与数据量同步变化。

首先，它主要降低可迁移分配造成的外部碎片，不能消除大小等级带来的全部内部浪费。Redis 无法安全识别或修复的分配、模块未配合描述的数据，以及某些具有特殊引用关系的对象，也可能无法整理。

其次，整理需要复制存活数据。碎片越严重、需要检查的对象越多，CPU 与内存带宽成本越明显；单个复杂键还可能需要跨多轮扫描。渐进调度降低的是延迟风险，不是把成本变成零。

再次，内存峰值留下的 RSS 不一定都是可整理碎片。分配器待清理页面、进程栈、共享库、持久化或复制期间的临时开销，都可能影响观察值。仅凭 `mem_fragmentation_ratio` 很高就打开最大整理强度，可能在错误的层次解决问题。

最后，碎片本身也有时间维度。空闲块若很快会被同等级对象复用，保留它们可能比立即回收更经济。Redis 的阈值、绝对字节门槛和渐进努力，本质上都是在空间收益与运行时成本之间作选择。

## 结语

Redis 管理内存碎片，不是定期把整个内存区域“压紧”一次，而是三个层次的协作：

1. 分配器保留并复用已经释放的块，避免无谓地反复向操作系统申请内存。
2. 当活跃页面中的空洞既多又大时，Redis 借助 jemalloc 的提示选择候选对象，复制内容并修复自己掌握的指针，让空闲空间趋于集中。
3. 页面具备释放条件以后，由 jemalloc 的清理机制或显式 purge 推动驻留内存回落。

这也给出了开头那个现象的答案：删除键只完成了第一层语义上的释放。之后的空间能否复用、能否集中成完整页面、何时不再驻留，分别由不同机制决定。看懂 Redis 的碎片管理，关键不是记住一个“安全碎片率”，而是知道眼前的差额属于哪一本账。
