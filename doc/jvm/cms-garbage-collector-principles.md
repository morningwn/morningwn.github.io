# CMS 垃圾回收器原理与实现方式

CMS 的全称是 Concurrent Mark Sweep。它是 HotSpot 里一类以“缩短老年代停顿”为首要目标的垃圾回收器。它的典型适用场景不是吞吐量优先的离线任务，而是对响应时间比较敏感、又不想每次回收老年代都停很久的服务端应用。

先给出一句主线：

- CMS 尽量把“找出哪些对象还活着”和“回收哪些对象已经死了”这两件事放到和用户线程并发执行。
- 但为了做到这一点，它放弃了默认整理内存，于是换来了更短的停顿，也带来了碎片、浮动垃圾和失败回退等问题。

如果只用一句话概括 CMS 的本质，那就是：

- 它是一个面向老年代、以并发标记和并发清除为核心、以更低停顿换取更多运行期开销的收集器。

需要先说明一点：CMS 已经在较新的 JDK 里退出主流，JDK 9 开始被废弃，JDK 14 起从 HotSpot 中移除。但它仍然非常值得学，因为很多并发 GC 的基础思想，都是在 CMS 这一代方案里被清晰暴露出来的。

## 一、先看 CMS 想解决什么问题

在 CMS 之前，老年代回收更常见的做法是：

- 要么单线程做标记和整理，停顿时间长。
- 要么虽然并行，但仍然要在 Stop-The-World 期间完成大部分老年代工作。

堆一旦变大，老年代回收通常就会成为停顿的大头。对 Web 服务这类程序来说，这种长时间停顿往往比吞吐量损失更难接受。

CMS 的设计重点因此很明确：

- 尽量缩短老年代回收时的停顿。
- 允许 GC 线程和业务线程同时工作。
- 把必须停顿的阶段压缩到很短的两个点上。

它不是“总体成本更低”的收集器，而是“把成本从集中停顿挪到并发执行”的收集器。

## 二、CMS 在 HotSpot 里的定位

理解 CMS，先要知道它在 JVM 里负责哪一块。

### 1. CMS 主要负责老年代

CMS 不是一个全堆统一收集器。它主要负责老年代，年轻代通常配合 ParNew 一起工作。

这意味着典型的 CMS 组合更像这样：

- 年轻代：ParNew，复制算法，Stop-The-World。
- 老年代：CMS，标记-清除，大部分阶段与用户线程并发。

所以 CMS 的低停顿，主要说的是：

- 老年代回收的停顿尽量短。

而不是：

- 整个 JVM 从此就没有明显停顿。

年轻代 Minor GC 仍然会暂停应用线程，只是一般比老年代 Full GC 短得多。

### 2. CMS 默认不做整理

CMS 的名字里没有 compact 或 evacuate，这不是偶然。

它的正常工作路径是：

- 标记出存活对象。
- 清除未标记对象占用的空间。
- 把空闲块挂回可分配结构。

也就是说，CMS 通常不搬运老年代存活对象，不做整体压缩。这一点直接决定了它的特征：

- 好处是停顿更短，因为不需要大量移动对象。
- 代价是会产生内存碎片。

## 三、CMS 的核心思路可以拆成 4 句话

如果暂时不看细节，可以先把 CMS 记成下面四条：

- 它先在很短的停顿里抓住一批初始根对象。
- 然后并发地把存活对象图尽量遍历完。
- 再在第二次短停顿里修正并发期间被业务线程改动过的那部分引用关系。
- 最后并发清除死亡对象，把空间还给空闲链表。

这四步背后对应的正是 CMS 的两大核心：

- 并发标记。
- 并发清除。

## 四、CMS 为什么能并发标记，但又不能完全不暂停

这部分是 CMS 最关键的原理。

### 1. 标记的本质是找出“从 GC Roots 出发还能到达的对象”

GC 要回收老年代，第一步不是“删垃圾”，而是“先确认谁还活着”。最经典的做法是可达性分析：

- 从线程栈、静态字段、JNI 引用等 GC Roots 出发。
- 沿着对象引用一路向下遍历。
- 能到达的对象就是存活对象，不能到达的对象才可能被回收。

如果应用线程完全停住，这件事最好做，因为对象图不会变化。

但 CMS 的目标恰恰是：

- 标记阶段尽量不要长时间停住应用线程。

所以 CMS 需要在“对象图会继续变化”的前提下完成标记。

### 2. 一边标记，一边业务线程还在改引用，天然会有一致性问题

假设 GC 线程正在并发扫描对象图，业务线程同时执行类似下面的赋值：

```java
a.field = b;
```

这时就会出现两个风险：

- 某条新引用被建立，但 GC 线程还没看到。
- 某条旧引用被断开，导致对象图和“标记开始时的状态”不再一致。

如果没有额外机制，并发标记就可能漏掉本该存活的对象，最终造成误回收，这是绝对不能接受的。

CMS 为了解决这个问题，并不是去维持一个完全实时、完全精确的全堆引用图，而是采用了更便宜的策略：

- 允许并发期间对象图变化。
- 但把“发生变化的位置”记录下来。
- 在后续阶段重新扫描这些可能受影响的位置。

这就是 CMS 正确性的关键。

## 五、CMS 的底层实现依赖哪些关键结构

### 1. 标记位图：记录对象是否被认为存活

CMS 并发标记时，需要有一套数据结构表示：

- 某个对象是否已经被标记为存活。
- 某个对象是否还需要继续向外遍历引用。

HotSpot 内部会使用标记位图和相关工作队列来推进这个过程。可以把它理解成：

- 位图负责记“这个对象活不活”。
- 工作队列负责记“这个对象的引用我还没扫完”。

### 2. Card Table：按更小粒度记录引用修改

GC 不会对每次引用写入都立刻重建完整引用图，那样开销太大。HotSpot 会把堆再划成更小的 card。

某个 card 上一旦发生引用字段写入，就可以把这个 card 标记为脏。这样 CMS 后续就知道：

- 这里的对象引用关系最近发生过变化，需要重点关注。

这个机制在分代收集器里本来就很重要，因为它能帮助记录跨代引用；对 CMS 来说，它还承担了并发标记期间“变更线索”的来源。

### 3. 脏卡重扫描集合：把变化聚焦到少量区域

CMS 不会在 remark 阶段重新扫整个老年代，否则停顿又会变长。它会借助脏 card 信息，把注意力集中到：

- 并发标记期间被修改过的那部分内存区域。

在 HotSpot 的实现里，这些脏 card 会被整理成供 CMS 重扫的数据结构，常见资料里会提到 Mod Union Table 一类概念。你不必死记内部名称，但要知道它解决的问题是：

- 把“并发期间哪里发生过引用变更”这件事压缩成一份可快速重扫的集合。

### 4. Free List：老年代空间不是线性推进分配，而是从空闲块中取

因为 CMS 默认不压缩老年代，所以清除以后得到的是很多离散空闲块。它们不能像连续内存那样只靠一个指针顺序分配，而是需要维护空闲链表或按大小分组的空闲块结构。

这意味着 CMS 的老年代分配更像：

- 从一堆空闲块里找一个够大的块。
- 分给即将晋升或直接进入老年代的对象。

这也是后面碎片问题的根源。

## 六、CMS 用的是“增量更新”而不是 SATB

这点很容易和 G1 搞混，但两者实现思路不一样。

### 1. 先看三色标记的基本约束

并发标记常用三色抽象：

- 白色：还没被发现的对象。
- 灰色：已经发现，但它的出边还没扫描完。
- 黑色：对象已经扫描完，且被认为存活。

为了保证正确性，经典三色标记有一个核心约束：

- 不能让黑色对象直接指向白色对象且这个变化永久逃过 GC 的视线。

否则就可能漏标白色对象。

### 2. CMS 的做法是记录“谁被改过”，稍后重扫它

CMS 使用的是增量更新思路。它关注的不是“被覆盖掉的旧引用值”，而是：

- 哪些对象所在区域在并发标记期间发生过引用修改。

当业务线程把某个对象字段改掉时，写屏障会把对应的 card 标脏。这样到了 preclean 或 remark 阶段，GC 就能重新扫描这些被改动过的区域。

你可以把它理解成：

- G1 更像是在保留“标记开始时的快照”。
- CMS 更像是在说“并发期间谁动过，我最后再查一遍谁动过”。

### 3. 这也是 CMS remark 阶段仍然不可省略的原因

如果没有 remark，CMS 只能看到“并发标记的大体结果”，却无法最终修补并发期间发生的引用变更。这会直接影响存活性判断。

所以 CMS 的并发标记不是完全独立完成的，它必须依赖：

- 一个收尾的 Stop-The-World remark。

## 七、CMS 的完整回收周期是怎么走的

从一次完整的老年代 CMS 周期来看，通常可以分为下面几个阶段。

### 1. Initial Mark：初始标记，Stop-The-World

这一步会短暂停顿应用线程，做两件事：

- 枚举 GC Roots。
- 标记从这些 Roots 直接可达的那一小层对象。

为什么这一步一定要停顿？因为根集合必须有一个一致视图。线程栈、寄存器、静态引用等如果在枚举过程中继续变化，后续并发标记的起点就不可靠。

这一步通常很快，因为它只抓“起点”，不做全图遍历。

### 2. Concurrent Mark：并发标记

初始标记完成后，应用线程恢复运行，CMS 线程开始并发地做可达性遍历：

- 从初始标记得到的对象出发，继续扫描整个老年代可达对象图。
- 把发现的存活对象记到标记位图里。
- 通过工作队列逐步把灰色对象处理成黑色对象。

这一步是 CMS 最核心的并发阶段，也是总耗时最长的一段。但因为它与用户线程并发，所以用户感受到的是：

- GC 在吃 CPU，而不是应用完全停住。

### 3. Concurrent Preclean：并发预清理

并发标记期间，业务线程一直在改对象引用，于是会不断产生脏 card。Preclean 的目标是：

- 在不暂停应用线程的前提下，先把已经积累的一部分脏 card 提前处理掉。
- 尽量减小 remark 阶段真正需要做的工作量。

它本质上是在“提前还债”。

### 4. Concurrent Abortable Preclean：可中断的预清理

这一步可以看成 preclean 的延长版。CMS 会边跑边看条件，例如：

- 年轻代是否快要触发 Minor GC。
- 预清理收益是否还值得继续。
- 停顿预算是否需要尽快进入 remark。

如果继续预清理的收益不高，CMS 就会主动结束这一步，进入后续收尾阶段。

这一步的意义是：

- 尽量把更多脏区域在并发期解决掉。
- 但不无限期拖延整个周期。

### 5. Remark：重新标记，Stop-The-World

Remark 是 CMS 最重要的一次停顿。它会在应用线程暂停的前提下，完成下面这些收尾动作：

- 重新扫描并发期间发生过引用变更的脏 card。
- 修正并发标记遗漏的那部分可达对象。
- 把最终存活对象集合确定下来。

这一步通常比 initial mark 更重，因为它要兜底并发期间的变化。但只要 preclean 做得足够好，remark 仍然会比传统老年代整段停顿短很多。

### 6. Concurrent Sweep：并发清除

当最终存活集合确定后，CMS 开始并发清除：

- 遍历老年代空间。
- 找出未标记对象占据的内存块。
- 把这些块回收到 free list。
- 必要时合并相邻空闲块，减缓碎片恶化速度。

因为这一阶段不需要移动存活对象，所以它可以和应用线程并发执行。

### 7. Concurrent Reset：并发重置

一次回收结束后，还要把标记位图和相关状态清理干净，为下一轮 CMS 周期做准备。这一步同样可以并发执行。

## 八、为什么 CMS 停顿短，但吞吐量不一定更好

CMS 的优势从来不是“GC 工作更少”，而是“GC 工作被摊开了”。因此它会带来几类额外成本。

### 1. GC 线程会和业务线程争 CPU

并发标记和并发清除都要消耗 CPU。如果机器核数不多，或者应用本来就接近满负荷，CMS 线程很容易和业务线程抢算力。

结果通常是：

- 单次停顿变短了。
- 但总吞吐量可能下降。

### 2. 写屏障和脏卡处理带来额外运行时开销

为了让并发标记保持正确，应用线程每次修改某些引用时，都需要顺手维护脏 card 信息。这个成本虽然比全量同步维护引用图低很多，但毕竟不是零。

### 3. 浮动垃圾不可避免

CMS 并发标记和并发清除时，应用线程还在继续分配和释放对象。于是会出现这样一类对象：

- 它在本轮标记开始时还被认为存活。
- 但在 CMS 还没结束时已经变成垃圾。

这类对象往往来不及在本轮被清掉，只能等下一轮，这就是浮动垃圾。

所以 CMS 不能等到老年代几乎满了才启动，它必须预留一段安全空间，让自己有时间并发跑完。

## 九、CMS 为什么容易产生碎片

这是 CMS 最典型的副作用。

### 1. 清除只回收空间，不搬动存活对象

标记-清除的结果是：

- 死对象被回收。
- 活对象还留在原地。

如果死亡对象分布在很多位置，清掉以后留下的就是很多不连续的小洞。

### 2. 总空闲很多，不代表能分配大对象

因为 CMS 老年代依赖 free list，从理论上看：

- 空闲总量够，不等于存在一个足够大的连续空闲块。

于是可能出现一种很典型的现象：

- 老年代看起来还有不少剩余空间。
- 但某个大对象、或者一次年轻代晋升，需要更大的连续块。
- 结果分配失败。

这就是碎片真正带来的业务后果。

### 3. CMS 的正常路径无法根治碎片

只要 CMS 继续按“标记-清除、不整理”的方式运行，碎片就只会被缓解，不会被彻底消除。

HotSpot 的做法通常是：

- 正常情况下继续使用 CMS。
- 一旦出现严重分配失败或回收赶不上分配，就退回一次带压缩能力的 Full GC 来兜底。

而这次兜底停顿通常就会非常长。

## 十、最常见的两个失败场景

### 1. Concurrent Mode Failure

这是 CMS 最著名的问题之一。它的含义是：

- CMS 这一轮并发回收还没跑完。
- 老年代已经先被用得差不多了。
- JVM 只能临时切到一次 Stop-The-World 的后备回收来救场。

为什么会发生？

- CMS 启动得太晚。
- 业务分配速度太快。
- 浮动垃圾太多。
- CPU 紧张导致并发阶段推进得太慢。

它的实际后果是：

- 本来想避免长停顿，结果反而触发一次更重的停顿。

### 2. Promotion Failure

年轻代回收时，存活对象可能要晋升到老年代。如果老年代虽然总空间还有，但找不到合适的连续空闲块，就可能出现晋升失败。

本质原因通常是：

- 老年代碎片化太严重。
- CMS 没有及时回收到足够可用的块。
- 或者对象晋升峰值过高。

这和 concurrent mode failure 不完全一样，但它们都指向 CMS 的核心弱点：

- CMS 需要足够的“可用连续空间”，而不仅仅是“账面空闲”。

## 十一、CMS 何时启动，为什么必须提前启动

因为 CMS 是并发收集器，不是“堆满再一把清”的收集器，所以它必须在老年代还留有余量时就启动。

直觉上可以这样理解：

- 串行 Full GC 可以在空间快耗尽时再暂停所有线程狠狠干一轮。
- CMS 不行，因为它很多工作是在应用继续运行时慢慢完成的。

因此 CMS 一般会根据老年代占用比例提前启动。典型调优项包括：

```text
-XX:+UseConcMarkSweepGC
-XX:CMSInitiatingOccupancyFraction=<percent>
-XX:+UseCMSInitiatingOccupancyOnly
```

这些参数的含义可以概括成一句话：

- 不要等老年代太满才开始 CMS，而要给并发标记和并发清除留足跑完的时间。

如果启动阈值过高，concurrent mode failure 的概率就会上升。

## 十二、CMS 的正确性到底靠什么保证

很多人知道 CMS 是“并发标记-清除”，但容易忽略一个问题：

- 业务线程一直在改对象图，CMS 凭什么还能保证不把活对象当垃圾回收？

从实现角度看，关键是下面三层配合。

### 1. 初始标记拿到可靠起点

通过短暂停顿，CMS 拿到一个一致的 Roots 快照，不至于连起点都不稳定。

### 2. 并发标记尽量覆盖大部分存活图

GC 线程在业务线程运行的同时做大头工作，把绝大多数可达对象先找出来。

### 3. 写屏障加 remark 修补并发期间的变化

这一步才是并发 GC 真正的安全阀。

当业务线程修改引用时，CMS 并不强求“立即得到最终正确图”，而是通过 card 标脏把风险位置记录下来。到了 remark，所有这些可能受影响的区域都会被重新检查。

所以 CMS 不是依赖“并发期完全精确”，而是依赖：

- 并发期先近似完成大头。
- 停顿期再用增量更新线索把误差收回来。

## 十三、CMS 与 G1 的差别，抓 4 点就够

如果你已经看过 G1，会发现两者都追求低停顿，但思路并不一样。

### 1. CMS 主要是老年代收集器，G1 是面向整个堆的分区收集器

CMS 的世界里，年轻代和老年代职责分得更开。G1 则把整个堆拆成 Region，再按收益挑选回收集。

### 2. CMS 正常路径不压缩，G1 正常路径会复制整理

这决定了：

- CMS 更容易碎片化。
- G1 更容易维持可分配的连续空间。

### 3. CMS 依赖增量更新，G1 依赖 SATB

两者都是为了解决并发标记时对象图变化的问题，但实现策略不同。

### 4. CMS 调优重点是“别失败”，G1 调优重点是“控制暂停模型”

CMS 很怕 concurrent mode failure 和碎片，而 G1 更强调预测每轮回收成本、按停顿目标选 Region。

## 十四、为什么 CMS 已经退出主流，但仍然值得学

CMS 从工程演进上看已经是“上一代低停顿收集器”。它后来被 G1、ZGC、Shenandoah 这类更现代的方案替代，主要原因正是：

- CMS 无法很好地处理碎片。
- 对大堆和高分配速率场景不够稳。
- remark、promotion failure、concurrent mode failure 等问题让调优成本偏高。

HotSpot 也在较新的 JDK 版本里废弃并移除了 CMS。

但 CMS 依然值得学，因为它几乎把并发 GC 的几个基本矛盾暴露得非常清楚：

- 怎样在对象图持续变化时做可达性分析。
- 为什么写屏障是并发 GC 的基础设施。
- 为什么“不整理内存”可以换来低停顿，也会带来碎片。
- 为什么并发回收必须提前启动，并且需要给失败留后路。

很多后续收集器，都是在这些问题上给出更强实现，而不是完全换了一个世界。

## 十五、最后总结

如果把 CMS 的原理压缩成最核心的几句话，可以记成下面这些结论：

- CMS 的目标是降低老年代回收停顿，而不是追求最高吞吐量。
- 它通过 initial mark 和 remark 两次较短停顿，加上中间的并发标记与并发清除，来减少长时间 Stop-The-World。
- 它依赖 card table、写屏障和增量更新来修补并发标记期间对象图的变化。
- 它默认不整理老年代，所以会出现浮动垃圾、碎片、promotion failure 和 concurrent mode failure。
- 它代表了 HotSpot 低停顿 GC 的重要历史阶段，也为理解 G1、ZGC、Shenandoah 这类后续方案打下基础。

如果你只保留一句最关键的话，那么就是：

- CMS 用“并发标记 + 并发清除”把老年代回收的停顿压短了，但它用 CPU 开销、浮动垃圾和碎片问题为这件事付了账。
