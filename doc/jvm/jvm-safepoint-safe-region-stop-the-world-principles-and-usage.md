# JVM 中的 Safepoint、Safe Region 与 Stop-The-World 机制

> 在学习 JVM 垃圾回收或排查停顿问题时，经常会遇到三个概念：
> - Safepoint。
> - Safe Region。
> - Stop-The-World。
>
> 很多资料会把它们混在一起说，甚至直接等同。但实际上，它们各自描述的是不同层面的事情：
> - Safepoint 是线程执行流中的一个特定位置。
> - Safe Region 是一段代码区域。
> - Stop-The-World 是一种全局暂停状态。
>
> 真正需要理解的主线是：
> - JVM 在执行某些全局操作（如 GC）之前，必须确保所有线程都处于安全状态。
> - 为了达到这个安全状态，JVM 依赖 Safepoint 和 Safe Region 这两种机制来协调线程。
> - 当所有线程都到达安全状态后，JVM 就进入了 Stop-The-World 阶段。

## 一、先看前提：JVM 为什么需要让线程停下来

在理解这三个概念之前，需要先搞清楚一个更基础的问题：

- JVM 为什么不能让线程一直跑，然后直接做垃圾回收？

原因在于，垃圾回收器在分析堆中对象时，需要操作一组非常关键的数据结构：

- 对象头中的 Mark Word。
- 类元数据（Klass）。
- 各种 GC 数据结构（如卡表、记忆集等）。

如果线程还在运行，就可能出现这些问题：

1. **对象引用在变动**。线程正在修改某个引用字段，GC 同时去扫描这个引用，就可能读到不一致的状态。
2. **对象布局在变动**。JVM 在做某些优化（如偏向锁撤销、类去优化）时，需要修改对象头或类元数据。如果线程还在访问这些数据，就会产生冲突。
3. **GC 需要移动对象**。像 G1、ZGC 这类收集器在回收过程中会移动对象。如果线程还在使用旧地址访问对象，就会访问到错误的数据。

因此，JVM 必须有一种机制，能够：

- 让所有线程在合适的时机暂停执行。
- 确保暂停时，线程持有的状态是一致的、可分析的。

这就是 Safepoint 和 Safe Region 存在的根本原因。

## 二、Safepoint 是什么

### 1. 定义

Safepoint 直译过来就是"安全点"。

在 JVM 中，Safepoint 指的是：

- 线程执行流中的一个特定位置。
- 在这个位置上，线程不持有任何会被 GC 或其他全局操作修改的数据的引用。
- 线程的所有寄存器状态和栈帧信息都是完整且一致的。

简单说：

- 当线程停在 Safepoint 时，JVM 可以安全地对其进行全局操作，而不会出现数据不一致的问题。

### 2. Safepoint 通常出现在哪些位置

在 HotSpot JVM 中，Safepoint 通常被插入在以下位置：

- **方法返回处**。方法调用结束、准备返回调用方时。
- **循环回边处**。循环体执行完一轮、准备回到循环头部继续下一轮迭代之前（这是最常见的 Safepoint 位置，也是"未到达 Safepoint"问题的常见来源）。
- **方法调用指令之后**。从被调用方法返回后，调用方会在继续执行前检查是否有 Safepoint 请求。
- **异常处理路径中**。某些异常抛出和捕获的位置也会插入 Safepoint。

这里有一个关键点：

- Safepoint 不是任意位置都能插入的。
- 它必须出现在线程状态完整、没有中间操作未完成的地方。

比如，如果线程正在执行一段对多个字段的原子性修改（虽然 Java 层面没有真正的多字段原子操作，但在 JIT 编译后可能有一系列连续的内存写入），那么在这段操作的中间就不能插入 Safepoint。

### 3. 轮询机制：线程怎么知道自己该停了

线程并不是靠"被通知"来停在 Safepoint 的。

实际上，HotSpot 采用的是一种**轮询机制**：

1. JVM 在代码中插入 Safepoint 时，会同时插入一段轮询代码。
2. 这段轮询代码会检查一个全局的内存页（Safepoint Polling Page）。
3. 正常情况下，这个内存页是可访问的，轮询不会触发任何动作。
4. 当 JVM 需要所有线程到达 Safepoint 时（比如要开始 GC），它会将这个内存页设为不可访问。
5. 线程执行到下一个 Safepoint 轮询点时，访问这个不可访问的内存页，就会触发一个信号（SIGSEGV）。
6. JVM 的信号处理器捕获这个信号后，让线程进入等待状态。

这个设计的优点是：

- 不需要在每个 Safepoint 处都做一次函数调用或条件判断。
- 轮询的开销非常小，通常只是一次内存读取。
- 只有在真正需要暂停时，才会产生信号处理的开销。

### 4. 轮询的两种实现方式

HotSpot 中 Safepoint 轮询有两种常见实现：

- **基于内存页的轮询**。也就是上面描述的，通过修改内存页的可访问性来触发信号（在 Linux 上为 SIGSEGV）。JIT 编译的代码中插入一条从固定内存地址读取的指令，正常时该地址可读，需要暂停时将该页设为不可访问。这种方式在"不需要暂停"时的开销极小（仅一次内存读取），是目前主流平台上的默认实现。
- **基于显式条件判断的轮询**。在某些不支持内存页保护的平台上，JVM 会在 Safepoint 处插入一条显式的条件判断指令，检查全局标志位。如果标志位被设置，线程就跳转到等待例程。这种方式每次经过 Safepoint 都要执行一次分支判断，相对开销更大，但实现更简单。

## 三、Safe Region 是什么

### 1. 为什么需要 Safe Region

Safepoint 机制有一个前提：

- 线程必须在执行流到达 Safepoint 位置时才会停下来。

但有些情况下，线程可能长时间不会到达 Safepoint：

- 线程正在执行一段很长的、没有 Safepoint 插入的本地代码（JNI 代码）。
- 线程正在执行 JIT 编译后的某段代码，而这段代码由于优化原因没有插入 Safepoint 轮询。

如果线程一直不到达 Safepoint，JVM 就无法完成全局暂停。

这就引出了 Safe Region 的概念。

### 2. 定义

Safe Region 直译过来就是"安全区域"。

它指的是：

- 代码中的一段区域。
- 在这段区域内，线程不会修改任何会被 GC 或其他全局操作访问的数据。
- 线程在这段区域内的任何位置暂停，状态都是一致的、安全的。

与 Safepoint 的一个重要区别在于协作方式：

- Safepoint 是**被动轮询**：JVM 设置标志位，线程执行到 Safepoint 时检测到标志，然后停下来。
- Safe Region 是**主动声明**：线程在进入该区域时，主动将自己标记为"处于安全区域"；JVM 发起全局暂停时，会将已处于 Safe Region 的线程直接视为安全，无需等待其到达某个代码位置。当线程准备离开 Safe Region 时，会检查全局暂停是否仍在进行，若是则等待直到暂停结束。

与 Safepoint 的区别还在于：

- Safepoint 是一个**点**，线程必须精确到达这个位置才能安全暂停。
- Safe Region 是一个**区域**，线程主动声明进入后，JVM 即可将其视为已安全暂停。

### 3. Safe Region 的典型场景

Safe Region 最典型的应用场景是：

- **线程从 Safepoint 不可达的代码区域退出时**。

比如，一个线程正在执行一段 JNI 本地代码。这段代码中没有 Safepoint 轮询，JVM 无法通过常规方式让线程停下来。

但这段本地代码在执行过程中，可能会进入某些"安全区域"——在这些区域中，线程不持有任何对堆中对象的引用，或者已经将所有引用都保存到了 GC 可识别的位置（如栈帧或全局引用表）。

当线程处于 Safe Region 时，即使它没有到达 Safepoint，JVM 也可以认为它是安全的，可以将其视为已暂停。

### 4. Safe Region 与 Safepoint 的关系

可以把两者的关系理解为：

- Safepoint 是"精确位置"的安全。
- Safe Region 是"一段范围"的安全。
- 两者都是为了让 JVM 确认线程处于可安全暂停的状态。

在实际实现中：

- 大多数线程通过 Safepoint 机制暂停。
- 少数无法到达 Safepoint 的线程（如正在执行特定本地代码的线程），通过 Safe Region 机制来声明自己的安全状态。

## 四、Stop-The-World 是什么

### 1. 定义

Stop-The-World（STW）直译过来就是"停止整个世界"。

它指的是：

- JVM 中的一种全局暂停状态。
- 在这个状态下，所有 Java 应用线程都被暂停。
- 只有 GC 线程或 JVM 内部的特定管理线程还在运行。

Stop-The-World 不是一个具体的技术或机制，而是一种**状态描述**。

它描述的是：

- 所有应用线程都已经到达 Safepoint（或处于 Safe Region）。
- JVM 现在可以安全地执行需要全局一致性的操作。

### 2. Stop-The-World 通常发生在什么时候

STW 通常发生在以下场景：

- **垃圾回收开始前**。大多数 GC 算法在真正开始回收之前，都需要先暂停所有应用线程，以确保堆中的对象图不会在分析过程中发生变化。
- **类卸载时**。JVM 在卸载一个类之前，需要确保没有任何线程正在使用这个类。
- **偏向锁撤销时**。当偏向锁需要升级为重量级锁时，JVM 可能需要暂停所有线程来安全地修改对象头。（注意：偏向锁从 Java 15 起已被标记为废弃，Java 21 中已彻底移除，因此在较新 JVM 版本中此场景不再适用。）
- **代码去优化时**。JIT 编译器发现某段编译后的代码不再适用，需要回退到解释执行时，可能需要暂停线程。
- **线程 Dump 生成时**。执行 `jstack` 或触发 Thread Dump 时，JVM 需要暂停所有线程以获取一致的线程快照。
- **堆 Dump 生成时**。执行 `jmap -dump` 或通过 JMX 触发 Heap Dump 时，通常也需要全局暂停来保证堆快照的一致性。

### 3. STW 的代价

Stop-The-World 的代价非常直接：

- 在 STW 期间，所有应用线程都停止了。
- 应用完全无法处理请求。
- 用户感知到的就是"卡顿"或"停顿"。

因此，STW 的持续时间是衡量 JVM 性能的一个重要指标。

不同的垃圾回收器在 STW 方面的表现差异很大：

| 回收器 | STW 特点 |
|--------|----------|
| Serial GC | 单线程回收，STW 时间通常最长 |
| Parallel GC | 多线程并行回收，STW 时间较短，但仍然是全暂停 |
| CMS GC | 大部分阶段并发执行，但初始标记和最终标记仍需 STW。**注意：Java 9 起标记为废弃，Java 14 起已移除** |
| G1 GC | 混合回收，大部分阶段并发，但部分阶段仍需 STW（如初始标记、混合回收中的根扫描等） |
| ZGC | 几乎所有阶段都并发执行，STW 时间极短（通常 < 1ms），且 STW 时间不随堆大小或对象数量增长 |
| Shenandoah GC | 与 ZGC 类似，目标是最小化 STW 时间，同样做到 STW 时间与堆大小无关 |

## 五、三者的关系：从线程暂停到全局操作

把 Safepoint、Safe Region、Stop-The-World 放在一起，它们的关系可以概括为：

1. JVM 需要执行某个全局操作（如 GC）。
2. JVM 发出 Safepoint 请求，将所有 Safepoint 轮询页设为不可访问。
3. 各线程在执行到下一个 Safepoint 时，触发信号并进入等待状态。
4. 对于当前处于 Safe Region 的线程（如正在执行 JNI 本地代码的线程），JVM 直接将其视为已到达安全状态，无需等待其到达 Safepoint。
5. 当所有线程都已到达 Safepoint 或处于 Safe Region 时，JVM 进入 Stop-The-World 状态。
6. JVM 执行全局操作。
7. 全局操作完成后，JVM 恢复 Safepoint 轮询页的可访问性，所有线程继续执行。

用一张简化的流程图来表示：

```
JVM 发起全局操作请求
        │
        ▼
  设置 Safepoint 轮询页为不可访问
        │
        ▼
  ┌─────────────────────────────┐
  │ 各线程执行到 Safepoint 位置  │
  │ 或进入 Safe Region          │
  └─────────────────────────────┘
        │
        ▼
  所有线程确认安全
        │
        ▼
  进入 Stop-The-World 状态
        │
        ▼
  执行全局操作（如 GC）
        │
        ▼
  恢复轮询页，线程继续执行
```

## 六、Safepoint 停顿时间过长的问题

在实际生产中，Safepoint 机制本身也可能成为性能问题的来源。

### 1. 常见问题：Safepoint 到达时间不均匀

当 JVM 发起 STW 请求后，不同线程到达 Safepoint 的时间可能差异很大：

- 大部分线程可能很快就能到达下一个 Safepoint。
- 但某个线程可能正在执行一段很长的循环，或者正在执行一段没有 Safepoint 的本地代码。

这时，整个 STW 的等待时间就取决于最慢的那个线程。

### 2. 排查手段

HotSpot 提供了一些 JVM 参数来帮助排查 Safepoint 相关问题：

- `-XX:+PrintSafepointStatistics`。打印 Safepoint 统计信息，包括每次 STW 的耗时、各线程到达 Safepoint 的时间等。
- `-XX:PrintSafepointStatisticsCount=<N>`。控制打印最近 N 次 Safepoint 的统计信息。
- `-XX:+SafepointTimeout`。当线程到达 Safepoint 超时，打印警告信息。
- `-XX:SafepointTimeoutDelay=<milliseconds>`。设置 Safepoint 超时阈值。

### 3. 常见优化方向

- **确保长循环中包含 Safepoint 检查**。JIT 编译器在优化计数循环（counted loop）时，可能将 Safepoint 轮询从循环体内提升出去，导致线程在长循环中长时间无法到达 Safepoint。可通过参数 `-XX:+UseCountedLoopSafepoints` 强制在计数循环的每次迭代中保留 Safepoint 检查。此外，如果循环内调用了方法，方法返回处通常会有 Safepoint，也能缓解此问题。
- **减少 JNI 调用中的长耗时操作**。避免线程长时间处于无法到达 Safepoint 的状态。
- **合理选择垃圾回收器**。如果对停顿时间敏感，可以选择 ZGC 或 Shenandoah 这类低延迟回收器，它们的设计目标就是将 STW 时间控制在毫秒级以内且不随堆大小增长。

## 七、现代改进：Thread-Local Handshakes

Java 10 引入了一项重要改进——Thread-Local Handshakes（JEP 312），它改变了传统"全局 Safepoint"的工作方式。

### 1. 传统方式的局限

在传统 Safepoint 机制下，即使 JVM 只需要操作某一个线程（例如对该线程执行栈追踪），也必须：

1. 发起一个全局 Safepoint 请求。
2. 等待**所有**线程到达 Safepoint。
3. 对目标线程执行操作。
4. 恢复所有线程。

这意味着单个线程的操作也要"连累"所有线程一起暂停，造成了不必要的停顿。

### 2. Thread-Local Handshakes 的改进

Thread-Local Handshakes 允许 JVM 对**单个线程**或**一组线程**单独发起"握手"，而无需全局暂停。具体做法是：

- JVM 向目标线程发送一个握手请求。
- 目标线程在执行到下一个 Safepoint 轮询点时，单独停下来处理该请求。
- 其他线程完全不受影响，继续正常运行。

### 3. 应用场景

Thread-Local Handshakes 被用于以下操作，使它们不再需要全局 STW：

- **获取单个线程的栈追踪**（`jstack` 的一部分操作）。
- **线程的偏向锁撤销**（在偏向锁被移除前）。
- **JVM TI 的某些线程级操作**。
- **ZGC 的部分线程级屏障操作**。

### 4. 注意事项

Thread-Local Handshakes 减少了不必要的全局暂停，但它并没有替代全局 Safepoint。对于真正需要全局一致性的操作（如 GC 的根扫描阶段），全局 STW 仍然是必需的。

## 八、总结

回到最核心的三个概念：

| 概念 | 本质 | 作用 |
|------|------|------|
| Safepoint | 执行流中的一个特定位置 | 线程在此位置暂停时，状态一致且安全 |
| Safe Region | 代码中的一段区域 | 线程在此区域内任何位置暂停都是安全的 |
| Stop-The-World | 一种全局暂停状态 | 所有线程都已安全暂停，JVM 可执行全局操作 |

它们之间的关系是：

- Safepoint 和 Safe Region 是**手段**。
- Stop-The-World 是**结果**。
- JVM 通过 Safepoint 和 Safe Region 机制，让所有线程达到安全状态，从而实现 Stop-The-World。
- 在 Stop-The-World 状态下，JVM 才能安全地执行垃圾回收等全局操作。

理解这三个概念，对于排查 JVM 停顿问题、选择合适的垃圾回收器、以及深入理解 JVM 运行时行为，都有重要的帮助。
