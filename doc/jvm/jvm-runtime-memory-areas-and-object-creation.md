# JVM 运行时内存区域与对象创建流程：从线程私有到对象落地

理解 JVM，最容易混淆的两条线通常是：

- 运行时内存到底分成哪些区域，每个区域放什么。
- Java 里一个 `new` 对象，底层到底经历了什么。

这两个问题其实是连在一起的。因为对象创建不是一个孤立动作，它一定发生在 JVM 的运行时数据区之中，类元数据、线程执行栈、堆内存、对象头、构造方法调用，都会参与进来。

如果先用一句话概括全文主线，可以这样理解：

- JVM 先把运行时内存划分为线程私有区域和线程共享区域。
- 程序执行时，字节码指令沿着程序计数器和虚拟机栈推进。
- 当执行到 `new` 指令，JVM 会先确认类是否可用，再在堆上为对象分配空间。
- 随后完成零值初始化、对象头设置和实例初始化，一个真正可用的对象才算创建完成。

这篇文章按两部分展开：

- 先把 JVM 运行时内存区域讲清楚，建立整体坐标系。
- 再沿着一次对象创建过程，串起这些区域之间的协作关系。

## 一、先建立整体视角：JVM 运行时内存区域怎么划分

从 JVM 规范角度看，运行时数据区通常可以分成两类：

- 线程私有
- 线程共享

这个划分很重要，因为它直接决定了数据的生命周期、并发访问方式，以及常见异常会出现在什么地方。

### 1. 线程私有区域

线程私有区域会随着线程创建而创建，随着线程结束而销毁。不同线程之间互不共享，主要包括：

- 程序计数器
- Java 虚拟机栈
- 本地方法栈

### 2. 线程共享区域

线程共享区域是所有线程共同使用的内存区域，通常包括：

- 堆
- 方法区
- 运行时常量池

如果从 HotSpot 这种常见实现再往前走一步，通常还会接触到：

- 直接内存

严格来说，直接内存不属于 JVM 规范定义的运行时数据区，但在实际排查内存问题时，它经常要和堆、方法区一起看。

## 二、程序计数器：线程下一条要执行什么指令

程序计数器可以理解成当前线程所执行字节码的行号指示器。

它的核心职责只有一个：

- 记录当前线程下一条将要执行的字节码指令地址。

为什么它必须是线程私有的？因为 CPU 在任意时刻通常只会执行一个线程中的一段指令，线程切换后要能恢复到正确执行位置，所以每个线程都需要自己的程序计数器。

这里有两个关键点：

- 如果线程执行的是 Java 方法，程序计数器记录的是正在执行的字节码指令地址。
- 如果线程执行的是 Native 方法，程序计数器的值通常是未定义的。

程序计数器是 JVM 规范中唯一一个没有规定任何 `OutOfMemoryError` 情况的区域。因为它只需要很小的一块空间，却对线程切换和字节码解释执行非常关键。

## 三、Java 虚拟机栈：方法调用的主战场

虚拟机栈描述的是 Java 方法执行的内存模型。每当一个方法被调用，就会创建一个栈帧并压入虚拟机栈；方法执行结束后，栈帧再出栈。

一个栈帧通常会包含这些核心内容：

- 局部变量表
- 操作数栈
- 动态链接
- 方法返回地址
- 一些附加信息

可以把它理解成：

- 局部变量表负责放参数和局部变量。
- 操作数栈负责配合字节码指令做入栈、出栈和中间结果计算。
- 动态链接负责把符号引用关联到具体方法。
- 返回地址负责方法结束后回到调用点继续执行。

例如下面这段代码：

```java
public User createUser() {
    User user = new User();
    return user;
}
```

执行时会发生几件事：

- `createUser()` 方法对应的栈帧入栈。
- 执行 `new` 指令后，在堆中创建对象。
- 引用地址会先进入操作数栈，再写入局部变量表里的 `user` 槽位。
- 返回时，把对象引用返回给上层调用者。

所以要注意：

- 对象实例通常在堆上。
- 对象引用经常先出现在虚拟机栈的局部变量表或操作数栈中。

虚拟机栈可能抛出两类典型异常：

- `StackOverflowError`：线程请求的栈深度超过虚拟机允许的深度。
- `OutOfMemoryError`：如果栈可以动态扩展，但扩展时无法申请到足够内存。

## 四、本地方法栈：给 Native 方法使用的栈空间

本地方法栈和 Java 虚拟机栈的角色很像，只不过服务对象不同：

- 虚拟机栈服务 Java 方法。
- 本地方法栈服务 Native 方法。

例如一些底层依赖操作系统能力或 JNI 的调用，执行过程中就可能使用本地方法栈。

在很多 JVM 实现里，虚拟机栈和本地方法栈的实现边界可能没有你想象得那么强，甚至可能合并管理。但从理解模型上，仍然应该把它们区分开：

- 一个面向 Java 字节码执行。
- 一个面向本地方法调用。

## 五、堆：对象实例和数组最主要的存放区域

堆是 JVM 中最核心、最常被讨论的一块内存区域。它是线程共享的，并且通常也是垃圾收集器最关注的区域。

如果只记一个结论，可以记住：

- 几乎所有对象实例和数组都在堆上分配。

之所以说“几乎所有”，是因为随着 JIT 优化的发展，某些对象在特定场景下可能发生标量替换或栈上分配等优化，不一定真的落到传统意义上的堆里。但从常规理解和绝大多数场景出发，把堆看成对象实例的主要落地区域是完全正确的。

### 1. 堆为什么要做分代或分区

从 GC 视角看，堆通常不会被简单看成一整块平面空间，而是会进一步划分，以提升回收效率。不同垃圾收集器的实现细节不一样，但核心动机类似：

- 不同对象的生命周期差异很大。
- 让“朝生夕死”的对象和“长期存活”的对象分开管理，回收成本更低。

在常见认知中，堆通常会被联系到这些区域概念：

- 新生代
- 老年代
- Eden 区
- Survivor 区

这些是 HotSpot 中很常见的堆管理视角。理解对象创建流程时，它们尤其重要，因为新对象往往优先分配在 Eden 区。

### 2. 堆上最常见的问题是什么

堆最典型的问题是：

- 对象太多，回收不及时，最终导致 `OutOfMemoryError: Java heap space`

因此很多线上性能问题，最后都会落到堆对象数量、对象生命周期和 GC 行为分析上。

## 六、方法区：类元数据、静态变量和运行时常量池的宿主

方法区也是线程共享区域，用来存放已被 JVM 加载的类信息，以及和类相关的结构化数据。

通常可以把方法区理解为主要承载这些内容：

- 类元数据
- 字段和方法信息
- 方法字节码相关结构
- 静态变量
- 运行时常量池

这里有一个非常常见的误区需要单独纠正：

- `static` 变量不是随着对象实例放在对象里。
- 它属于类级别数据，通常和类元数据一起由方法区侧管理。

在 HotSpot 发展过程中，方法区的具体实现形态经历过变化，例如永久代、元空间等概念，很多文章容易把它们混为一谈。更稳妥的理解方式是：

- 方法区是 JVM 规范层面的抽象。
- 永久代、元空间是具体虚拟机实现方式。

也就是说：

- 不要把“方法区”简单等同于“永久代”。
- 在现代 HotSpot 里，更常见的实现概念是元空间。
> **补充说明**：从 JVM 规范角度，静态变量和运行时常量池属于方法区管辖。但在 HotSpot JDK 7 及以上版本中，这两者实际上被移动到了 Java 堆中（与对应的 `java.lang.Class` 对象一起存放），而类元数据在 JDK 8 之后移入本地内存中的元空间。这个细节在排查内存问题时很重要——静态变量引用的对象走的是正常的堆 GC，不会被元空间回收。
## 七、运行时常量池：类加载后的符号表与常量表

运行时常量池是方法区的一部分（JVM 规范定义），它来源于 Class 文件中的常量池表。类加载后，编译期常量、符号引用等信息会进入运行时常量池。

> **HotSpot 实现细节**：在 HotSpot JDK 7 及以上版本中，运行时常量池实际被移到了 Java 堆中，不再位于方法区的物理实现（永久代或元空间）内。但从逻辑归属上，它仍是方法区的一部分。

这里面通常包含：

- 字面量
- 类和接口的符号引用
- 字段引用
- 方法引用
- 接口方法引用

为什么它重要？因为很多“编译时知道名字，运行时再定位目标”的动作，都要依赖它。例如：

- 方法调用时解析符号引用。
- 字符串常量相关行为。
- 动态链接过程中的引用定位。

运行时常量池也不是无限的，如果常量池无法再申请到内存，同样可能抛出 `OutOfMemoryError`。

## 八、直接内存：不在堆里，但经常和堆一起出问题

直接内存不属于 JVM 规范定义的运行时数据区，但在 NIO、大文件读写、网络框架中很常见。

它的特点是：

- 内存不直接分配在 Java 堆上。
- 通常由本地函数库直接分配。
- Java 里通过 `DirectByteBuffer` 等方式间接使用。

它的价值主要在于：

- 某些场景下可以减少 Java 堆和 Native 堆之间的数据复制。
- 对高性能 I/O 更友好。

但如果直接内存使用过量，同样可能出现内存溢出问题。所以排查内存故障时，不能只盯着 Java 堆。

## 九、把这些区域串起来：一次方法执行时到底发生了什么

只看单个区域容易碎片化，真正重要的是把它们串起来。

例如执行下面这段代码：

```java
public class OrderService {
    private static final String PREFIX = "ORD";

    public Order create() {
        Order order = new Order();
        return order;
    }
}
```

从运行时角度可以这样理解：

- `OrderService` 的类信息、字段信息、常量池内容进入方法区。
- `PREFIX` 这类类级别信息和类结构关联管理。
- 线程执行 `create()` 方法时，会为该方法创建栈帧，放入虚拟机栈。
- 程序计数器记录当前线程执行到哪条字节码指令。
- 执行 `new Order()` 时，在堆上为 `Order` 对象分配空间。
- 对象引用先在操作数栈和局部变量表之间流转。
- 方法执行完成后，栈帧出栈；如果堆上的对象仍然被引用，就继续存活，否则未来某次 GC 可能回收它。

一旦按这个视角去看，对象创建流程就会更容易理解。

## 十、对象创建流程：从一条 new 指令开始

Java 代码里最常见的对象创建写法是：

```java
User user = new User();
```

看起来只有一行代码，但 JVM 在底层至少要完成一整套动作。按主线拆开，可以分成下面几个步骤。

### 1. 检查类是否已经加载、解析并初始化

当 JVM 执行到 `new` 指令时，第一件事不是马上分配内存，而是先检查这个指令的参数能否在常量池中定位到对应的类符号引用，并确认该类是否已经完成必要的类加载流程。

如果还没有，JVM 会先触发对应的类加载过程，包括：

- 加载
- 验证
- 准备
- 解析
- 初始化

这一步的意义很直接：

- JVM 不会为一个“还不可用的类”直接创建实例。
- 对象创建一定建立在类已经可被正常使用的前提之上。

### 2. 为新对象分配内存

类信息确认完毕后，JVM 才会根据该类实例对象所需大小，在堆上划出一块内存。

对象所需大小在类加载完成后通常已经可以确定，因为：

- 实例字段数量和类型已经明确。
- 对象头大小是已知的。
- 对齐填充规则也是确定的。

> **注意**：以上针对的是普通对象。对于数组对象，所需空间还取决于运行时指定的数组长度，因此只能在创建时才能确切计算。不过数组中单个元素的类型信息同样来自类元数据，所以每个元素占多少空间是已知的。

在 HotSpot 中，常见的内存分配方式可以概括成两类：

- 指针碰撞
- 空闲列表

它们分别适用于不同的堆组织状态：

- 如果堆内存是规整的，已用和未用区域边界清晰，可以通过移动指针完成分配，这就是指针碰撞。
- 如果堆内存不是规整的，而是存在很多碎片，就需要通过空闲列表找到一块足够大的可用空间。

使用哪一种方式，通常取决于当前垃圾收集器以及堆是否规整。

### 3. 处理并发分配安全

对象创建并不是单线程专属动作，多线程环境下会有很多线程同时申请堆内存，因此分配过程必须保证线程安全。

常见做法包括：

- 通过 CAS 等并发原语保证更新分配指针时的原子性。
- 为线程预先分配一小块线程本地分配缓冲区，也就是 TLAB。

TLAB 可以理解成：

- 先从大堆里切一小块给某个线程独占使用。
- 这个线程后续创建小对象时，优先在自己的 TLAB 中分配。
- 只有 TLAB 不够时，才再回到全局堆上竞争。

这样做的好处是：

- 减少全局同步竞争。
- 提高高并发对象分配的吞吐量。

### 4. 将分配到的内存初始化为零值

内存分配完成后，JVM 会把对象实例数据区域初始化为零值，不包括对象头。

例如：

- `int` 字段初始化为 `0`
- `boolean` 字段初始化为 `false`
- 引用字段初始化为 `null`

这一步很关键，因为它保证了：

- 即使 Java 代码里没有显式给字段赋初值，对象字段也能拿到类型安全的默认值。

注意这里仍然不是构造方法逻辑，只是 JVM 层面的默认初始化。

### 5. 设置对象头

接下来，JVM 会对对象头进行设置。对象头并不是业务字段，但它对 JVM 管理对象非常重要。

在 HotSpot 中，对象头由两部分组成：

- **Mark Word**：存储对象自身的运行时数据，例如哈希码（实际上在第一次调用 `hashCode()` 时才懒计算并缓存）、GC 分代年龄、锁状态标记、偏向锁线程 ID 等。Mark Word 是一块被动态复用的空间——对象处于不同锁状态时，其内部各 bit 的含义会不同。
- **Klass Pointer**：类型指针，指向方法区中该对象所属类的元数据，JVM 通过它确定对象是哪个类的实例。

如果是数组对象，对象头中还会额外记录：

- 数组长度

对象头的存在决定了 JVM 后续可以知道：

- 这个对象是什么类型。
- 它当前处于什么锁状态。
- GC 应该如何识别和管理它。

### 6. 执行 init，对对象进行真正的实例初始化

完成上面步骤后，从 JVM 角度看，一个“可被引用的对象”基本已经存在了，但还没有执行 Java 程序员写在构造方法里的初始化逻辑。

接下来会执行对象的实例初始化方法，也就是 `<init>()`，本质上对应构造方法链。

例如：

```java
public class User {
    private int age = 18;

    public User() {
        this.age = 20;
    }
}
```

这时才会发生你代码层面真正关心的初始化动作，例如：

- 显式实例字段赋值
- 构造方法体执行
- 父类构造链调用

到这里，一个符合 Java 语义的对象才算真正创建完成。

## 十一、对象创建完成后，内存里到底长什么样

从 HotSpot 常见视角出发，一个对象在内存中通常可以分成三部分：

- 对象头
- 实例数据
- 对齐填充

### 1. 对象头

在 HotSpot 中，对象头又可以细分为两部分：

- **Mark Word**：存储运行时动态数据，如哈希码（懒计算）、GC 分代年龄、锁状态标记、偏向线程 ID 等。Mark Word 在不同锁状态下会复用同一块空间来存储不同内容，是一种空间换灵活性的设计。
- **Klass Pointer**：类型指针，指向方法区中的类元数据，用于确定对象所属类型。

如果是数组对象，对象头中还会包含一个记录数组长度的字段。

### 2. 实例数据

实例数据就是程序真正定义的字段内容，例如：

- 基本类型字段
- 引用类型字段
- 从父类继承下来的实例字段

### 3. 对齐填充

对齐填充不一定有实际业务含义，它更多是为了满足虚拟机对内存地址对齐的要求。

## 十二、再区分一次：对象本身、对象引用、类信息分别在哪

这个问题特别容易混，所以值得单独总结一次。

### 1. 对象本身在哪

- 通常在堆上。

### 2. 对象引用在哪

- 可能在虚拟机栈的局部变量表中。
- 也可能在操作数栈中。
- 也可能作为某个对象字段继续存在于另一个堆对象中。

### 3. 类信息在哪

- 通常由方法区侧管理。

### 4. 静态变量在哪

- 它属于类级别数据，不属于某个对象实例。
- 从 JVM 规范角度，静态变量在方法区中。但在 HotSpot JDK 7 及以上版本中，静态变量实际存储在 Java 堆中，与 `Class` 对象一起管理。

把这几个概念分清，很多内存问题就不会再被混成一团。

## 十三、常见面试与实践误区

### 1. “栈里放对象，堆里放基本类型”这种说法不对

更准确的说法应该是：

- 局部变量表里可以放基本类型值，也可以放对象引用。
- 对象实例本身通常在堆上。

### 2. 方法区不是永久代的同义词

- 方法区是规范概念。
- 永久代、元空间是 HotSpot 不同时期的实现方式。

### 3. 不是所有内存问题都等于堆溢出

常见内存问题还可能来自：

- 栈过深导致 `StackOverflowError`
- 元空间不足
- 直接内存耗尽

### 4. 对象创建不等于只做了一次 malloc

从 JVM 语义上看，对象创建至少包括：

- 类检查
- 内存分配
- 零值初始化
- 对象头设置
- 构造方法执行

只有把这些步骤连起来，才能真正理解 `new` 的含义。

## 十四、最后收束成一条完整主线

如果把全文压缩成一条最重要的理解链路，可以这样记：

- 程序计数器决定线程当前执行到哪条指令。
- 虚拟机栈承载方法调用过程中的局部变量、操作数栈和返回信息。
- 方法区负责保存类元数据、静态变量和运行时常量池。
- 堆负责承载绝大多数对象实例和数组。
- 当执行 `new` 指令时，JVM 会先确认类已可用，再在堆上分配对象空间。
- 随后完成零值初始化、对象头设置，并执行构造方法。
- 最终，一个符合 Java 语义的对象才真正可用。

理解这条主线后，再去看 GC、类加载、锁优化、逃逸分析、对象布局或线上内存问题，整体会顺很多。因为这些问题本质上都绕不开同一个前提：

- JVM 是如何组织内存的。
- 对象又是如何在这套内存结构里被创建、使用和回收的。
