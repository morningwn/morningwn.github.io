# JVM 垃圾回收中的可达性分析是什么

> 在理解 JVM 垃圾回收时，很多人会先接触到这样一句话：
> - 从 GC Roots 出发能找到的对象，就是存活对象。
> - 找不到的对象，才有可能被回收。
> 
> 这句话说的其实就是 JVM 中最核心的一种对象存活判定方法：可达性分析。 
> 
> 如果只记结论，概念很容易停留在“知道名字，但不清楚它到底在做什么”。真正要理解的主线是下面这几步：
>
> - 垃圾回收首先要回答“哪些对象还活着”。
> - 仅靠对象之间互相引用，不能准确判断对象是否还可用。
> - JVM 需要找到一批可靠的起点。
> - 再从这些起点沿着引用关系向下遍历整个对象图。
> - 最终能遍历到的对象被认为仍然存活。
>
> 这套判定过程，就是可达性分析。

## 一、为什么 JVM 需要可达性分析

在讨论可达性分析之前，先看一个更基础的问题：

- JVM 怎么判断一个对象是不是垃圾？

最容易想到的方法，是引用计数。

它的思路很直观：

- 一个对象每多一个地方引用它，计数就加一。
- 每少一个地方引用它，计数就减一。
- 当计数变成零时，就说明这个对象没人使用了，可以回收。

这种方法简单，但它有一个明显缺陷：无法解决循环引用。

例如：

```java
class NodeA {
    NodeB b;
}

class NodeB {
    NodeA a;
}
```

如果：

- 一个 NodeA 对象引用了一个 NodeB 对象。
- 这个 NodeB 对象又反过来引用了 NodeA。
- 但程序中已经没有任何其他地方能访问这两个对象。

那么结果会是：

- NodeA 的引用计数不是零。
- NodeB 的引用计数也不是零。
- 但它们事实上已经不可能再被业务代码使用。

也就是说，引用计数只能说明“有没有对象互相指着”，却不能说明“这个对象还能不能从程序正在使用的上下文中被访问到”。

JVM 要解决的正是后一个问题。

因此，主流 JVM 没有依赖引用计数来完成垃圾对象判定，而是采用可达性分析。

## 二、先看结论：可达性分析到底是什么

可以先把可达性分析记成一句话：

- 可达性分析，是 JVM 通过一组根引用出发，遍历对象引用链，从而判断对象是否仍然可访问的过程。

这里有三个关键点。

### 1. 它是在判断“是否可访问”

可达性分析关注的不是：

- 一个对象被引用了几次。
- 一个对象创建了多久。
- 一个对象占了多少内存。

它关注的是：

- 这个对象还能不能从程序当前有效的入口走到。

只要还能走到，它就被认为是活对象。

### 2. 它一定要有起点

如果把整个堆里的对象关系看成一张图，那么图上的每个对象都可能通过字段、数组元素、静态变量等方式引用其他对象。

这时 JVM 不可能凭空判断“哪个对象更重要”，它必须先选定一批遍历入口。

这批入口就是 GC Roots。

### 3. 它的本质是一次图遍历

从实现思路上看，可达性分析很像图搜索：

- 从若干个根节点出发。
- 沿着引用边不断向下访问。
- 被访问到的节点都标记为可达。
- 遍历结束后，仍然没有被访问到的节点就是不可达对象。

所以，可达性分析本质上是在回答：

- 某个对象是否位于“从 GC Roots 可以到达的对象子图”中。

## 三、GC Roots 和可达性分析是什么关系

很多人学到这里时，会把 GC Roots 和可达性分析当成两个分开的知识点。实际上，两者是同一条链路上的前后关系。

可以这样理解：

- GC Roots 决定“从哪里开始找”。
- 可达性分析决定“怎么找，以及找到以后怎么判断对象是否存活”。

没有 GC Roots，可达性分析就没有起点。

没有可达性分析，GC Roots 也只是一些静态概念，无法真正完成对象存活判定。

因此，两者通常是一起出现的：

- 先枚举 GC Roots。
- 再基于 GC Roots 做可达性分析。

如果只看一句最简洁的描述，就是：

- 可达性分析是方法，GC Roots 是起点。

## 四、可达性分析具体是怎么做的

从流程上看，一次可达性分析可以粗略拆成下面几个步骤。

### 1. 枚举根对象

JVM 会先找出一批根引用，也就是 GC Roots。常见来源包括：

- 线程栈帧中的局部变量引用。
- 方法区中类静态属性持有的引用。
- JNI 本地方法持有的引用。
- JVM 运行时内部保留的系统级引用。

这些引用之所以能成为起点，是因为它们代表了程序当前仍然有效、仍然可能继续访问对象的入口。

### 2. 从根对象出发向下扫描

当根集合确定后，垃圾回收器会沿着引用关系继续访问对象。

例如：

- Root1 指向对象 A。
- A 指向 B。
- B 指向 C。

那么在遍历过程中：

- A 会被标记为可达。
- B 会被标记为可达。
- C 也会被标记为可达。

只要引用链不断开，这条链上的对象都会被视为仍然存活。

### 3. 标记所有能到达的对象

遍历过程中，垃圾回收器通常会给已经访问到的对象打上标记，表示它们已经被证明是可达的。

这样做有两个目的：

- 防止重复扫描同一个对象。
- 在遍历结束后快速区分“可达对象”和“不可达对象”。

### 4. 处理无法到达的对象

当整个遍历完成后，仍然没有被标记到的对象，就被认为是不可达对象。

但这里要特别注意：

- 不可达，不等于立刻回收。

不可达对象通常意味着它已经失去正常访问路径，但 JVM 在真正释放内存前，还可能结合具体收集器策略、引用类型、终结机制等再做一步处理。

不过从“对象是否已经脱离可用对象图”这个问题来看，可达性分析到这里已经完成了核心判定。

## 五、一个简单例子看懂可达与不可达

下面用一个简化的对象关系来说明。

假设当前堆中有这些关系：

- 栈中的局部变量 root 引用了对象 A。
- A 引用了 B。
- B 引用了 C。
- 还有两个对象 D 和 E，它们互相引用。
- 但是没有任何 GC Roots 能连接到 D 或 E。

如果画成关系，可以理解成：

```text
GC Root -> A -> B -> C

D <-> E
```

执行可达性分析后：

- A 可达。
- B 可达。
- C 可达。
- D 不可达。
- E 不可达。

这里最关键的点在于：

- D 和 E 虽然互相引用，但它们依然可能是垃圾。

这正是可达性分析相比引用计数更可靠的地方。

它判断的不是“有没有引用”，而是“能不能从根走到”。

## 六、为什么说可达性分析本质上解决了循环引用问题

循环引用之所以难处理，是因为对象之间可以彼此形成闭环。

如果只看对象内部的引用关系，就会出现这种情况：

- A 引用 B。
- B 引用 A。
- 看起来两边都还有引用，所以谁都不像垃圾。

但站在程序整体的角度，真正有意义的问题不是“它们之间还指不指向彼此”，而是：

- 当前程序还能不能从有效执行上下文访问到它们。

如果答案是否定的，那么这个闭环再完整，也只是一个脱离根节点的孤岛。

可达性分析正好能识别这种“孤岛对象群”：

- 只要这个闭环和 GC Roots 之间没有路径相连。
- 整个闭环就会被统一判定为不可达。

因此，从原理上说，可达性分析天然能够处理循环引用问题。

## 七、对象不可达以后，会立即被回收吗

严格来说，不一定。

这是因为“可达性分析判定不可达”与“内存真正被释放”之间，并不是完全等号关系。

中间还可能受到几个因素影响。

### 1. 垃圾回收器的执行时机

对象就算已经不可达，也要等到后续某次垃圾回收真正处理到它所在区域，内存才会被回收。

也就是说：

- 不可达是逻辑判定结果。
- 回收是后续收集动作。

### 2. 特殊引用类型的影响

可达性分析标记的是"从 GC Roots 沿强引用能走通的路径"，但 Java 中还存在其他引用类型，它们会构成不同的**可达性等级**。

从最强到最弱，Java 的引用类型如下：

- **强引用**：最常见的引用方式（`Object obj = new Object()`）。只要强引用关系还在，对象就不会被回收。
- **软引用**（`SoftReference`）：描述仍有用但非必需的对象。在内存不足（即将 OOM）时，GC 会回收软可达对象。
- **弱引用**（`WeakReference`）：描述非必需对象，只能存活到下一次 GC 发生。一旦 GC 执行，弱可达对象就会被回收。
- **虚引用**（`PhantomReference`）：最弱的引用关系，无法通过虚引用获取对象实例。其作用是在对象被回收时收到通知，用于堆外内存清理等场景。

这四种引用类型对应着四种可达性等级——强可达、软可达、弱可达、虚可达。GC 对不同等级的处理策略不同，因此对象是否最终被清理，不仅取决于是否可达，还取决于
**以哪种方式可达**。

### 3. 与终结机制（finalize）相关的处理

如果一个类覆写了 `Object.finalize()` 方法（该方法已在 Java 9 中标记为废弃），且方法体非空，那么该对象在被判定为不可达后，不会立即被回收。JVM
的处理流程如下：

- 将对象放入 **F-Queue** 队列。
- 由一个专用的 **Finalizer 线程**串行执行其 `finalize()` 方法。
- 在 `finalize()` 执行期间，对象有可能**自救（resurrection）**——即重新与某个 GC Roots 建立引用链，变回可达对象。
- 如果自救成功，该对象将暂时存活，不会在这次 GC 中被回收。
- 如果自救失败或未覆写 `finalize()`，对象才会在**下一次** GC 中真正被回收。

因此，不可达对象的回收时间可能被延迟至少一次 GC 周期，并且不能保证 `finalize()` 一定会在有限时间内执行完毕。

不过从日常理解角度来说，可以先抓住主线：

- 可达性分析负责判定对象是否已经失去正常访问路径。
- 真正何时释放内存，则由具体 GC 执行过程决定。

## 八、可达性分析在不同垃圾回收器里有什么意义

虽然不同垃圾回收器的实现细节差异很大，比如 Serial、Parallel、CMS、G1、ZGC 在停顿方式、并发阶段、屏障机制上都不一样，但它们都需要回答同一个基础问题：

- 哪些对象还活着？

而可达性分析正是这个问题的基础。

也就是说：

- 回收器之间差异很大。
- 但“基于根集合判定对象是否可达”这件事，是现代 JVM 垃圾回收的核心前提之一。

不同收集器的区别通常不在于“要不要做可达性分析”，而在于：

- 什么时候做。
- 是否并发做。
- 如何减少停顿。
- 如何维护遍历期间对象引用变化带来的正确性。

例如在并发标记型收集器中，应用线程和标记线程可能同时运行，这就要求 JVM 借助额外机制保证可达性分析结果仍然正确。

所以，可达性分析既是一个概念，也是一切标记类垃圾回收算法的基础工作。

## 九、理解可达性分析时最容易混淆的几个点

### 1. 被引用，不一定代表对象可达

这是最常见误区。

一个对象只要还被另一个对象引用，并不代表它一定存活。关键要看这条引用链最终能不能追溯到 GC Roots。

如果不能，那么即使对象之间互相引用，它们仍然可能一起成为垃圾。

### 2. 可达对象，不等于永远不会回收

对象在当前这次分析中可达，只说明它此刻仍然存活。

后续如果根引用断开，它在下一次 GC 中就可能变成不可达对象。

所以可达性分析给出的结论，始终是某个时刻的存活快照。

### 3. GC Roots 不是固定的一小类对象

GC Roots 不是业务层面上某些“特殊对象”，而是垃圾回收器在当前时刻选定的根引用集合。

例如局部变量引用在方法执行期间可能是根，但方法结束、栈帧出栈后，它就不再属于根集合。

### 4. 不可达，不代表业务一定马上感知到异常

有些对象即使已经不可达，业务代码也未必能立刻察觉，因为它本身已经不再被访问。真正的变化通常体现在后续 GC 释放内存之后。

这也是为什么分析内存泄漏时，不能只看“对象有没有互相引用”，而要看“它为什么还能从根对象一路被找到”。

## 十、在实际开发中，理解可达性分析有什么用

这个问题很重要，因为如果只把可达性分析停留在面试概念层面，价值会比较有限。

在实际开发里，它至少有三个直接作用。

### 1. 帮助理解内存泄漏的本质

很多 Java 内存泄漏并不是“对象没人引用了却没回收”，而是：

- 某些不该长期存在的引用，还挂在 GC Roots 可达链路上。

例如：

- 静态集合忘记清理对象。
- ThreadLocal 使用后未及时 remove。
- 长生命周期缓存持有大量短生命周期对象。

这些问题都可以从“为什么对象仍然可达”这个角度分析。

### 2. 帮助读懂 GC 日志和堆分析工具结论

无论是 MAT 这类内存分析工具，还是一些堆转储报告，都会反复出现一个核心视角：

- 某对象是通过哪条引用链连到 GC Roots 的。

如果理解了可达性分析，就能更快看懂这些工具为什么要强调 Root Path。

### 3. 帮助建立更准确的 GC 思维模型

很多人误以为“对象设为 null 就一定立刻释放”，或者“两个对象互相引用就一定回收不了”。这些误解本质上都是因为没有从可达性分析角度理解对象存活。

一旦建立正确模型，就能更准确地判断：

- 哪些引用真的会阻止回收。
- 哪些对象只是暂时还没被 GC 处理。
- 哪些场景可能形成长期可达链路。

## 十一、总结

把整件事压缩成一条主线，可达性分析就是：

- JVM 从 GC Roots 出发，沿对象引用关系遍历整个对象图。
- 能被遍历到的对象是可达对象，也就是当前存活对象。
- 无法被遍历到的对象是不可达对象，后续才有可能被垃圾回收。

它解决的核心问题不是“对象之间有没有互相引用”，而是：

- 对象是否仍然处在程序可访问的范围内。

也正因为如此，可达性分析成为 JVM 垃圾回收判定对象生死的基础方法。理解了它，再去看 GC Roots、分代回收、并发标记、内存泄漏分析，整体逻辑都会清晰很多。
