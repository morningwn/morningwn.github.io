本文以 JDK 25 的 64 位 HotSpot JVM 为主要版本范围，并以 x64、AArch64 和默认 8 字节对象对齐为基本前提，解释压缩普通对象指针、压缩类指针与紧凑对象头。JDK 24 首次以实验特性提供紧凑对象头，JDK 25 将其升级为产品特性，但仍然默认关闭。

## 三种机制分别压缩什么

“压缩指针”和“对象头压缩”经常被当成同一个概念，实际对应三个不同的存储位置：

| 机制 | HotSpot 选项 | 压缩的内容 | 主要影响 |
| --- | --- | --- | --- |
| 压缩普通对象指针 | `UseCompressedOops` | Java 堆中的对象引用 | 引用字段和引用数组元素通常由 8 字节降为 4 字节 |
| 压缩类指针 | `UseCompressedClassPointers` | 对象头中指向 `Klass` 元数据的类指针 | 传统对象头中的 Class Word 由 8 字节降为 4 字节 |
| 紧凑对象头 | `UseCompactObjectHeaders` | Mark Word 与类信息组成的整体布局 | 在 64 位平台上把 12 或 16 字节的头部压缩为 8 字节 |

这里的 oop 是 ordinary object pointer 的缩写，即 HotSpot 对 Java 对象引用的称呼。`Klass` 则是 HotSpot 在原生内存中表示 Java 类型的内部元数据，不是堆里的 `java.lang.Class` 对象。

三种机制可以组合，但不能相互替代。`UseCompressedOops` 不会直接缩短 Class Word；`UseCompressedClassPointers` 也不会把业务对象的引用字段变成 4 字节。紧凑对象头依赖压缩类指针，却不要求业务对象之间的普通引用也必须压缩。

## 传统 HotSpot 对象头的布局

一个尚未经过逃逸分析消除的普通堆对象，可以把内存布局概括为：

```text
+----------------+----------------+----------------+----------------+
| Mark Word      | Class Word     | 实例字段       | 对齐填充       |
+----------------+----------------+----------------+----------------+
```

Mark Word 在 64 位 HotSpot 中占 8 字节，用于承载对象的运行时状态，包括身份哈希、GC 年龄和锁状态标签。某些锁实现或垃圾回收阶段还可能把它临时解释为指针。

Class Word 用于定位对象所属类型的 `Klass` 元数据：

- 开启压缩类指针时，Class Word 为 4 字节，普通对象头共 12 字节；
- 关闭压缩类指针时，Class Word 为 8 字节，普通对象头共 16 字节。

数组在对象头之后还需要一个 4 字节的长度字段。因此，开启压缩类指针时，传统数组的 Mark Word、Class Word 和长度字段合计为 16 字节。数组元素随后排列，最终大小仍需满足对象对齐要求。

对象实际占用空间不能只把各部分相加。默认情况下，HotSpot 把对象起始地址和对象大小按 8 字节对齐，不足的部分用填充补齐：

```text
对象大小 = 向上对齐(对象头 + 实例数据或数组数据, 对齐粒度)
```

这条规则会直接影响压缩后的实际收益。头部减少 4 字节，最终对象大小可能不变，也可能一次减少 8 字节。

## 压缩普通对象指针如何工作

### 32 位值表示的不是完整地址

64 位进程的原生地址宽度是 64 位，但 Java 堆通常只占虚拟地址空间中的一段连续区域。HotSpot 不必在每个引用字段中保存完整地址，可以保存对象地址相对于堆基址的偏移量。

设窄指针为 $n$，堆基址为 $base$，缩放位数为 $shift$，概念上的解码关系是：

$$
\operatorname{decode}(n)=
\begin{cases}
\mathrm{null}, & n=0 \\
base+(n \ll shift), & n\ne 0
\end{cases}
$$

其中：

- $n$ 是存入对象字段或引用数组元素的 32 位无符号值；
- $base$ 是 HotSpot 为当前堆选择的基址；
- $shift$ 是左移位数，单位是位；
- $n \ll shift$ 得到相对于基址的字节偏移量。

编码是相反过程：先从对象地址中减去基址，再右移 $shift$ 位，得到 32 位窄指针。`0` 保留给 `null`，因此带基址模式下不能简单地把所有值都无条件代入加法公式。

### 对象对齐为什么能扩大寻址范围

默认 8 字节对齐意味着合法对象地址的最低 3 位恒为 `0`。窄指针不必保存这三个没有信息量的位，解码时统一左移 3 位即可恢复字节偏移量。

32 位无符号数共有 $2^{32}$ 种编码。按 8 字节缩放时，理论覆盖范围为：

$$
2^{32} \times 8\ \text{bytes}=32\ \text{GiB}
$$

这就是常见“压缩指针支持约 32 GiB 堆”的来源。它不是因为 32 位值直接保存了 32 位虚拟地址，而是因为一个编码单位代表 8 字节。

如果把对象对齐提高到 16 字节，`shift` 可以变为 4，理论范围随之扩大到 64 GiB。代价是更多对象可能产生内部填充，实际是否节省内存必须按目标对象分布测量。具体可用堆上限还受 HotSpot 版本、平台、GC 和虚拟地址空间布局约束，不能只按上述理论范围配置生产堆。

### 零基址与带基址模式

HotSpot 会尝试把堆放到便于解码的虚拟地址范围内：

- **零基址模式**：`base` 为 `0`，解码只需缩放窄指针；
- **带基址模式**：堆不能采用合适的零基址布局时，解码还需要加上堆基址；
- **不缩放模式**：堆足够小且布局合适时，可以令 `shift` 为 `0`，32 位值直接表示字节偏移。

这是虚拟地址编码，不是把对象搬到 32 位地址空间。CPU 真正访问对象之前，解释器或编译后的机器代码仍会把窄指针解码成当前平台可使用的地址；寄存器、JNI 句柄和 HotSpot 内部结构也不保证都以 32 位形式保存引用。

### 哪些位置会变小

开启 `UseCompressedOops` 后，受影响的主要是 Java 堆中的引用型数据：

- 对象的引用字段；
- `Object[]` 等引用数组的元素；
- HotSpot 选择以窄 oop 形式保存的部分堆内数据。

`int`、`long` 等基本类型字段不会因此改变宽度。Java 方法中的局部引用也不能直接按 4 字节计算，它们可能位于解释器栈槽、编译栈帧或机器寄存器中，属于执行状态而不是对象布局。

## 压缩类指针如何工作

每个对象都必须能确定自己的运行时类型。传统对象头通过 Class Word 保存 `Klass` 指针，虚方法调用、类型检查、反射以及对象大小计算都会使用相应的类型元数据。

压缩类指针同样利用“基址、偏移和缩放”编码：对象头只保存 32 位 narrow klass，HotSpot 在使用时将它解码为原生 `Klass*`。它与压缩普通对象指针的编码思想相同，但地址空间和被指向对象完全不同：

| 对比项 | 压缩普通对象指针 | 压缩类指针 |
| --- | --- | --- |
| 指向目标 | Java 堆对象 | 原生内存中的 `Klass` 元数据 |
| 窄值常见位置 | 引用字段、引用数组元素 | 传统对象头的 Class Word |
| 基址所属区域 | Java 堆 | 压缩类空间及相关类元数据地址范围 |
| 主要容量约束 | 可编码的 Java 堆范围 | 可编码的类元数据范围 |

启用压缩类指针时，HotSpot 会为可压缩的 `Klass` 元数据保留压缩类空间。JDK 25 的默认 `CompressedClassSpaceSize` 为 1 GiB，这部分是原生内存中的保留区域，按需提交，不属于 Java 堆。该选项只限制相应的 `Klass` 元数据，不等于整个 Metaspace 的上限；`MaxMetaspaceSize` 才作用于已提交的压缩类空间和其他 Metaspace 元数据之和。

早期 HotSpot 要求压缩类指针依赖压缩普通对象指针。JDK 15 起，两者在主要 64 位平台上已经解耦。因此，关闭 `UseCompressedOops` 不等于 Class Word 必然恢复到 8 字节，判断对象头宽度时必须分别检查两个选项。

## 压缩后对象究竟能小多少

以下计算假定 64 位 HotSpot、8 字节对象对齐，不考虑字段布局被其他 JVM 实现重新安排的情况。

### 空对象

传统布局开启压缩类指针时，空对象由 12 字节头部和 4 字节对齐填充组成，共 16 字节。紧凑对象头只有 8 字节，空对象最终也是 8 字节。

```text
传统压缩类指针：12 字节头部 + 4 字节填充 = 16 字节
紧凑对象头：     8 字节头部                 =  8 字节
```

头部只减少 4 字节，空对象的最终大小却减少 8 字节，因为原来的 4 字节填充也随之消失。

### 只有一个 `int` 字段的对象

传统压缩类指针布局为 `12 + 4 = 16` 字节；紧凑对象头布局为 `8 + 4 = 12` 字节，但仍需向上对齐到 16 字节。两者最终都占 16 字节。

这个例子说明，紧凑对象头并不保证每个对象都实际变小。省出的空间可能被末尾对齐填充抵消。

### 包含两个引用字段的对象

```java
final class Pair {
    Object left;
    Object right;
}
```

同时开启压缩普通对象指针和压缩类指针时，传统布局为 `12 + 4 + 4 = 20` 字节，对齐后为 24 字节。开启紧凑对象头后为 `8 + 4 + 4 = 16` 字节，最终减少 8 字节。

如果关闭压缩普通对象指针，两个引用字段各占 8 字节。即使仍使用紧凑对象头，该对象也需要 `8 + 8 + 8 = 24` 字节。这再次说明，对象头压缩和引用字段压缩解决的是不同部分。

### 长度为 3 的引用数组

开启两种传统压缩指针时，`Object[3]` 的布局可以按 `12 字节对象头 + 4 字节长度 + 3 × 4 字节元素` 计算，合计 28 字节，对齐后为 32 字节。使用紧凑对象头后为 `8 + 4 + 3 × 4 = 24` 字节。

这些例子可以归纳为：紧凑对象头把传统压缩类指针布局的头部从 12 字节降到 8 字节，但最终对象大小的差值由字段宽度、数组长度和对齐共同决定，不能固定写成“每个对象节省 4 字节”。

## 紧凑对象头如何把信息装入 64 位

传统对象头把 Mark Word 和 Class Word 分开存放。紧凑对象头不再保留独立的 Class Word，而是把压缩后的类信息并入 Mark Word，使整个头部固定为 64 位：

```text
63                    42 41                            11 10       7 6    3 2 1  0
+-----------------------+--------------------------------+----------+------+---+----+
| 22 位压缩类信息       | 31 位身份哈希                  | 预留 4 位| 年龄 | S | 标签|
+-----------------------+--------------------------------+----------+------+---+----+
```

其中：

- 22 位压缩类信息用于定位对象的 `Klass`；
- 31 位身份哈希在计算后保存 `System.identityHashCode()` 所需的稳定值；
- 4 位为 Project Valhalla 预留；
- 4 位记录对象年龄；
- `S` 是 GC 使用的自转发标记；
- 最低 2 位表示锁等运行时状态。

压缩的关键不只是“删掉 4 字节”，而是改变多种运行时子系统访问对象头的协议。类信息必须在对象被锁定或移动时仍然可取得，否则 JVM 连对象类型和大小都无法确定。

### 锁不能再覆盖整个对象头

传统的栈锁实现会把原 Mark Word 复制到线程栈中的锁记录，再用指向锁记录的指针覆盖对象头。这与紧凑对象头不兼容，因为被覆盖的 64 位中已经包含唯一的类信息。

紧凑对象头使用的轻量级锁只原子修改低位状态标签；需要膨胀为监视器锁时，监视器保存在独立数据结构中，对象头仍保留类信息。JEP 450 因而明确要求避免使用会覆盖整个头部的旧栈锁模式。

### GC 转发也必须保留类信息

移动式垃圾回收需要记录对象的新地址。传统实现可以临时把转发指针写进 Mark Word，因为 Class Word 仍然独立存在。紧凑布局把类信息合并进同一个 64 位头部后，GC 不能再无条件覆盖整个头部。

HotSpot 为此调整了转发编码：上部的压缩类信息需要保持可访问，低位空间承担部分转发状态，并使用独立的自转发标记处理对象转发到自身的情况。JEP 450 中用于滑动压缩的转发编码可覆盖至多 8 TiB 堆；使用非 ZGC 收集器且堆超过这个范围时，紧凑对象头会受到限制。

### 更短的类信息带来类数量边界

传统压缩类指针在 Class Word 中有 32 位，紧凑对象头只分配 22 位。JDK 25 文档因此把可加载类的数量上限描述为约 400 万个。一般应用距离该限制很远，但大量动态生成类型的系统必须在目标负载下检查类数量，不能只依据 Java 堆大小判断是否适合开启。

## JDK 24 与 JDK 25 的启用方式

JDK 24 中，紧凑对象头属于实验特性，需要同时解锁实验选项：

```bash
java -XX:+UnlockExperimentalVMOptions \
     -XX:+UseCompactObjectHeaders \
     -version
```

JDK 25 中它已经是产品特性，不再需要解锁，但仍默认关闭：

```bash
java -XX:+UseCompactObjectHeaders -version
```

压缩普通对象指针和压缩类指针通常由 HotSpot 根据平台、最大堆和其他参数自动决定。不要只根据默认值推测当前进程，可以直接检查最终参数：

```bash
java -XX:+PrintFlagsFinal -version 2>&1 \
  | grep -E 'UseCompressedOops|UseCompressedClassPointers|UseCompactObjectHeaders|ObjectAlignmentInBytes'
```

`PrintFlagsFinal` 输出还会标明参数值来自默认、自动决策还是命令行。观察对象的最终字段偏移、头部和填充时，可以使用 OpenJDK 的 JOL：

```bash
java -jar jol-cli.jar internals java.lang.Integer
java -jar jol-cli.jar internals java.util.HashMap
```

JOL 输出依赖运行它的 JVM 配置。同一个类在不同 JDK、GC、最大堆、对象对齐或压缩选项下可能得到不同结果，因此测量时必须记录完整启动参数。

## 是否应该手动调整这些选项

压缩普通对象指针和压缩类指针通常保留 HotSpot 的自动决策即可。手动关闭它们会扩大引用字段或对象头，可能增加堆占用、GC 工作量和缓存访问量；只有明确的兼容性、容量限制或可复现性能证据，才构成改变默认行为的依据。

紧凑对象头在 JDK 25 中已经是产品特性，但仍是可选布局。评估时应同时比较：

- 相同业务数据下的已用堆与存活集大小；
- 分配速率和 GC 次数；
- 吞吐量、平均延迟与尾延迟；
- 已加载类数量，以及所用 GC、JIT、诊断工具和原生代理的兼容性。

不能把基准测试中的头部节省比例直接当成业务收益。对象越小、数量越多，头部在总堆中的占比通常越高；如果堆主要由大型基本类型数组或大块数据承载对象组成，减少每个对象头的收益占比会更低。

## 结论

压缩普通对象指针利用堆基址、对象对齐和偏移编码，把堆内引用通常从 64 位缩短为 32 位。压缩类指针对 `Klass` 元数据地址采用相似思想，把传统对象头中的 Class Word 从 8 字节缩短为 4 字节。二者指向不同地址空间，从 JDK 15 起也可以独立启用。

紧凑对象头进一步取消独立的 Class Word，把 22 位类信息、31 位身份哈希以及锁和 GC 状态合并进一个 64 位头部。它节省的是每个对象的固定元数据，不会改变基本类型字段宽度，也不会自动压缩业务对象之间的引用。

分析对象内存占用时，应按“头部宽度、引用宽度、实例或数组数据、对齐填充”四部分计算。只看到头部从 12 字节降到 8 字节，不能推出每个对象一定减少 4 字节；最终差值必须由实际布局和对齐结果决定。
