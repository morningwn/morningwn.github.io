# JVM 如何实现虚拟线程：原理、使用方式与注意事项

虚拟线程是 Java 并发模型近些年最重要的变化之一。它的目标不是让单个任务执行得更快，而是让 Java 在保持“一个任务一个线程”这种直观编程方式的同时，支持非常高的并发量。

很多人第一次看到虚拟线程，会把它简单理解成“更轻量的线程”或者“Java 版协程”。这两种说法都不算错，但都不够准确。更精确地说：

- 虚拟线程仍然是 `java.lang.Thread`。
- 它依然保留了线程的顺序执行、阻塞等待、异常传播和栈跟踪语义。
- 但它不再和一个操作系统线程永久绑定，而是由 Java 运行时在少量平台线程之上进行调度。

如果只先记一条主线，可以把虚拟线程理解成下面这句话：

- 平台线程是“线程对象 = OS 线程”。
- 虚拟线程是“线程对象 != 固定 OS 线程”，而是由 JVM 运行时按需挂载到平台线程上执行。

这篇文章会从三个层面展开：

- JVM 和 JDK 运行时到底是如何把虚拟线程实现出来的。
- 在 Java 里应该如何创建、使用和迁移到虚拟线程。
- 在真实项目中，哪些习惯会让虚拟线程收益变差，甚至把它用废。

## 一、先说清楚：虚拟线程严格来说是谁实现的

标题里说“JVM 如何实现虚拟线程”，这在工程语境里是成立的，但严格一点讲，虚拟线程并不是单靠 JVM 规范层面就能讲清的能力。

更准确的说法是：

- Java 语言和标准库暴露了虚拟线程 API。
- JDK 运行时提供线程调度、阻塞适配、调试支持和工具链支持。
- HotSpot 这样的 JVM 实现负责把这些语义真正落到解释器、JIT、GC、栈表示和本地运行时上。

也就是说，虚拟线程不是“Java 语法糖”，也不是某个框架的线程池技巧，而是 Java 平台运行时能力的一部分。

在 JDK 21 中，虚拟线程已经正式发布，对应的是 JEP 444。

## 二、为什么 Java 需要虚拟线程

理解虚拟线程，先要理解传统平台线程的瓶颈。

### 1. 平台线程为什么贵

传统 Java 线程本质上是对 OS 线程的一层封装。一个平台线程通常意味着：

- 一个独立的 OS 线程。
- 一块较重的线程栈和内核资源。
- 线程创建、切换、销毁都需要较高成本。

所以传统 Java 服务通常不敢创建太多线程，只能：

- 用线程池复用线程。
- 控制线程数。
- 用异步回调、事件循环、响应式编程去绕开“线程太贵”这个事实。

问题是，这种异步风格虽然能提高吞吐，但会带来另外一类成本：

- 业务逻辑被拆碎。
- 调用链不再线性。
- 堆栈可读性变差。
- 调试和排障成本显著上升。

Java 一直很擅长写同步阻塞代码。如果为了吞吐被迫全面异步化，本质上是在为了适应昂贵的线程实现而牺牲编程模型。

### 2. 虚拟线程想解决什么问题

虚拟线程的目标不是替代所有并发模型，而是尽量保住 Java 最擅长的那种写法：

- 一个请求一个线程。
- 在线程内用顺序代码写业务。
- 遇到 I/O 就阻塞等待。
- 出问题时直接看线程栈。

它解决的核心矛盾是：

- 我们想继续用阻塞式代码编程。
- 但我们不想让每个阻塞请求都独占一个 OS 线程。

所以虚拟线程的设计方向不是“消灭阻塞”，而是：

- 允许代码在语义上继续阻塞。
- 但在运行时实现上，不让这种阻塞长期占住底层平台线程。

## 三、虚拟线程的核心模型：M:N 调度

这是虚拟线程最关键的基础。

### 1. 平台线程是 1:1

传统平台线程是：

- 1 个 Java 线程，对应 1 个 OS 线程。

线程对象的生命周期，基本就和底层内核线程绑死了。

### 2. 虚拟线程是 M:N

虚拟线程采用的是 M:N 调度：

- M 个虚拟线程。
- 调度到 N 个平台线程上执行。

这里的平台线程有个专门名字，叫 carrier thread，也就是承载线程。

可以把它想成：

- 虚拟线程是大量轻量任务单元。
- carrier thread 是有限的真实执行载体。
- Java 运行时调度器把虚拟线程轮流挂到 carrier thread 上运行。

所以，虚拟线程并不是“不用 OS 线程”，而是“不再和某个固定 OS 线程终身绑定”。

### 3. 这和早年 green thread 有什么区别

Java 早年也有过 green thread，但那更接近 M:1：

- 很多用户态线程，最终都落在同一个 OS 线程上。

这种方式在多核时代很难充分利用硬件。虚拟线程不是回退，而是进化：

- 它仍然是用户态调度。
- 但最终会映射到多个平台线程上。
- 因此既保留轻量性，又能利用多核 CPU。

## 四、JVM 运行时到底怎么执行一个虚拟线程

要理解“JVM 如何实现虚拟线程”，关键要理解四个动作：

- 创建。
- 调度。
- 挂载与卸载。
- 阻塞与恢复。

### 1. 创建出来的仍然是 Thread 对象

从应用视角看，虚拟线程仍然是 `Thread`：

```java
Thread thread = Thread.ofVirtual().start(() -> {
    System.out.println("hello virtual thread");
});

thread.join();
```

这一步不会直接创建一个传统意义上的重量级 OS 线程。它创建的是：

- 一个虚拟线程对象。
- 一份由 Java 运行时管理的执行状态。
- 一套可被调度、可暂停、可恢复的栈与续体状态信息。

这里最重要的一点是：

- `Thread.currentThread()` 在虚拟线程里返回的仍然是当前虚拟线程本身，而不是 carrier thread。

也就是说，Java 代码层面仍然保留“我正在一个线程里执行”的语义一致性。

### 2. 调度器会把虚拟线程分配给 carrier thread

JDK 的虚拟线程调度器是一个专用的 work-stealing `ForkJoinPool`，工作模式偏向 FIFO（不同于 common pool 常见的 LIFO 倾向）。

它负责：

- 维护就绪的虚拟线程队列。
- 把可运行的虚拟线程挂载到某个 carrier thread 上。
- 在虚拟线程阻塞后回收 carrier thread。
- 在阻塞条件满足后重新调度这个虚拟线程继续运行。

默认情况下，调度器并行度通常接近可用 CPU 核数，可通过 `-Djdk.virtualThreadScheduler.parallelism` 调整；调度器可使用的平台线程上限可通过 `-Djdk.virtualThreadScheduler.maxPoolSize` 调整。

这里要特别注意：

- carrier thread 不等于业务线程池。
- 它是虚拟线程运行时内部的执行载体。
- 一个虚拟线程在生命周期中可以先后运行在不同的 carrier thread 上。

因此，虚拟线程和底层平台线程之间没有线程亲和性保证。

### 3. mount 和 unmount：虚拟线程最关键的运行机制

虚拟线程执行时，并不是永久“粘”在某个 carrier thread 上，而是会不断发生挂载和卸载：

- mount：把虚拟线程挂到某个 carrier thread 上执行。
- unmount：把虚拟线程从 carrier thread 上摘下来，carrier thread 立刻可以去执行别的虚拟线程。

这是虚拟线程能“便宜”的根本原因。

如果没有 unmount，那么虚拟线程只是换了个名字的平台线程，根本谈不上高并发。

### 4. 阻塞 I/O 时为什么不会白占 OS 线程

虚拟线程最典型的使用场景，是大量任务在等待网络、数据库、磁盘或队列。

在平台线程模型里，如果代码执行：

```java
try (var in = url.openStream()) {
    String body = new String(in.readAllBytes(), java.nio.charset.StandardCharsets.UTF_8);
}
```

那么这个线程等待 I/O 的整段时间里，底层 OS 线程通常都被占住。

但在虚拟线程模型里，JDK 会尽可能把很多阻塞操作改造成下面这个运行时行为：

- 虚拟线程发起阻塞操作。
- 运行时识别这是可协作的阻塞点。
- 虚拟线程从 carrier thread 上 unmount。
- carrier thread 去执行别的虚拟线程。
- I/O 就绪后，这个虚拟线程再被重新提交到调度器。
- 调度器把它 mount 到某个 carrier thread 上继续执行。

这就是为什么虚拟线程适合高并发 I/O 场景：

- 不是因为 I/O 不阻塞了。
- 而是因为阻塞的是虚拟线程语义，不再长期占住稀缺的 OS 线程资源。

## 五、JVM 如何保存虚拟线程的执行栈

这部分是虚拟线程实现里最容易被忽视，但也最关键的一层。

### 1. 平台线程的栈通常是 OS 管理的连续栈

传统平台线程的调用栈通常和底层 OS 线程强绑定，表现得像一块较大的连续线程栈内存。

这有两个问题：

- 数量多了很占内存。
- 很难在阻塞时把整套执行上下文轻量地搬来搬去。

### 2. 虚拟线程的栈由堆上的 stack chunk 表示

虚拟线程的调用栈不是直接依附在固定 OS 线程栈上，而是由 JVM 运行时以 stack chunk 的形式保存在 Java 堆中。

可以先把它理解成：

- 平台线程的栈更像“固定绑定在线程上的一大段本地栈空间”。
- 虚拟线程的栈更像“可增长、可收缩、可序列化管理的分块栈状态”。

这带来几个直接效果：

- 虚拟线程挂起时，可以把执行状态保留下来。
- 恢复时，再把这些状态重新接回执行流程。
- 栈空间按需增长，而不是一开始就给每个线程准备一大块。

这就是为什么一个 JVM 进程可以容纳远多于平台线程数量的虚拟线程。

### 3. 为什么这和 GC 也有关系

因为虚拟线程栈放在堆上，所以它天然会和垃圾回收器发生交互。

这和传统平台线程很不一样。传统线程栈一般不是堆对象，不会以同样方式被 GC 管理。

对于虚拟线程来说：

- 栈帧相关对象在堆中表示。
- 栈的增长、收缩会影响堆占用。
- 大量虚拟线程意味着更多堆对象和更多 GC 参与度。

不过这不意味着虚拟线程天然更耗内存。真实对比通常要和异步编程做对照：

- 异步风格会把跨阶段状态拆成更多堆对象。
- 虚拟线程则把这些状态保留在线程栈语义里。

两者最终的堆压力，往往比很多人直觉上更接近。

### 4. 一个实现边界：栈很深时仍然不是无限的

虚拟线程并不代表“栈无限”。

在 HotSpot 的现有实现下，虚拟线程栈以 chunk 形式存在，仍然有实现边界。比如在当前实现中，G1 对 humongous stack chunk 有限制；在较小 region 配置下，极深调用栈可能更早触发 `StackOverflowError`。

所以虚拟线程的优势是：

- 更适合海量并发、浅到中等深度、经常阻塞等待的任务。

它并不意味着：

- 你可以放心写无限递归。

## 六、哪些阻塞会释放 carrier thread，哪些不会

这是理解虚拟线程收益的关键。

### 1. 大多数 JDK 内建阻塞点都能友好配合虚拟线程

JDK 为虚拟线程专门适配了很多阻塞操作，尤其是：

- 网络 I/O。
- `LockSupport.park()`。
- 基于 `java.util.concurrent` 的很多同步器。
- 一部分阻塞队列、锁和等待原语。

这意味着：

- `Semaphore.acquire()`。
- `BlockingQueue.take()`。
- 很多 socket 阻塞读写。

在虚拟线程中通常都能以“阻塞语义 + 不长期占住 carrier”这种方式运行。

### 2. 但不是所有阻塞都能 unmount

有些阻塞由于操作系统或 JDK 内部实现限制，仍然可能直接把 carrier thread 一起卡住。

典型包括：

- 某些文件系统操作。
- 某些 native 调用。
- 某些 JVM 内部无法安全拆开的阻塞路径。
- `Object.wait()` 这一类受历史语义限制的路径。

对于其中一部分“非 pinning 但不可卸载”的阻塞路径，调度器会临时扩容 carrier thread 数量，尽量降低影响。但这不是万能补偿机制。

还要注意：如果问题属于下一节的 pinning，调度器并不会通过这种方式补偿。

所以要记住：

- 虚拟线程对“阻塞友好”，不等于“所有阻塞都零成本”。

## 七、pinning：虚拟线程最重要的注意事项

如果只记一个使用风险，那就是 pinning。

### 1. 什么叫 pinning

pinning 指的是：

- 虚拟线程本来应该在阻塞点 unmount。
- 但由于某些条件，它不能卸载，只能继续绑在当前 carrier thread 上。

一旦此时又发生阻塞，那么被卡住的不只是虚拟线程，还有底层 carrier thread 和对应 OS 线程。

这会直接损害扩展性。

### 2. 哪些情况会触发 pinning

最常见的是两类：

- 虚拟线程在 `synchronized` 代码块或同步方法内发生阻塞。
- 虚拟线程执行 `native` 方法或 foreign function 时发生阻塞。

比如：

```java
synchronized (lock) {
    socket.getInputStream().read();
}
```

这段代码的问题不是 `synchronized` 本身，而是：

- 你在持有 monitor 的时候执行了可能长时间阻塞的 I/O。

此时虚拟线程不能安全地从 carrier thread 上摘下来，于是 carrier 也被一起卡住。

### 3. pinning 什么时候严重，什么时候不严重

不是所有 `synchronized` 都要立刻替换。

下面这种情况通常问题不大：

- 很少执行。
- 临界区很短。
- 只保护内存中的快速读写。

真正危险的是：

- 高频路径。
- 临界区内有网络、数据库、文件或队列等待。
- 阻塞时间长。
- 并发量大。

这时 pinning 会把虚拟线程的收益大幅吞掉。

还要注意一个关键边界：与上一节提到的“非 pinning 不可卸载阻塞”不同，调度器不会因为 pinning 自动扩容 carrier thread。出现频繁 pinning 时，最有效的手段仍然是改掉对应的同步与阻塞路径。

### 4. 遇到 pinning 应该怎么改

最常见的思路不是“全局禁用 synchronized”，而是：

- 只改那些高频且长阻塞的同步路径。
- 把长时间阻塞 I/O 移出 `synchronized` 临界区。
- 必要时用 `ReentrantLock` 代替 monitor，以减少 pinning 影响。

例如：

```java
private final ReentrantLock lock = new ReentrantLock();

void doWork() throws IOException {
    lock.lock();
    try {
        prepareState();
    } finally {
        lock.unlock();
    }

    callRemoteService();
}
```

这里的关键不是“Lock 一定比 synchronized 高级”，而是：

- 不要在可能长期阻塞的地方把虚拟线程钉死在 carrier 上。

### 5. 如何排查 pinning

JDK 提供了直接诊断手段：

- 开启 JFR 事件 `jdk.VirtualThreadPinned`。
- 使用 `-Djdk.tracePinnedThreads=short` 或 `-Djdk.tracePinnedThreads=full`。

这些工具可以直接告诉你：

- 哪个虚拟线程在什么栈上发生了 pinned blocking。
- 哪些 monitor 或 native frame 是问题来源。

## 八、JVM 对虚拟线程的调度不是“抢占式时间片神话”

很多人会下意识地把虚拟线程想成“用户态线程 + 任意切换 + 非常灵活的抢占”。这并不准确。

### 1. 虚拟线程不是手写协程 yield 模型

虚拟线程不是那种要求你显式 `yield` 或显式交回控制权的协程 API。

Java 代码通常不用手动配合调度器。你还是按普通阻塞式线程方式写代码。

### 2. 调度切换主要发生在合适的阻塞点

虚拟线程真正获得高复用效果，主要依赖：

- I/O 阻塞。
- park/unpark。
- 可配合的同步原语。
- 当前实现下，调度器并不会对虚拟线程做强制时间片抢占（time sharing）。

也就是说，它最擅长的是“等待很多”的工作负载。

这并不表示 CPU 密集任务完全不切换：OS 仍会调度 carrier thread。但如果一个虚拟线程长时间不遇到阻塞或 park，它在虚拟线程层面的卸载机会会明显变少。

### 3. 它不是 CPU 密集任务加速器

如果任务是下面这种：

- 纯 CPU 计算。
- 很少阻塞。
- 每个任务都长时间吃满核心。

那么虚拟线程通常不会比平台线程更快。因为这时瓶颈根本不是线程数量，而是 CPU 核数。

所以有一句非常重要的话：

- 虚拟线程提升的是 scale，也就是并发承载与吞吐。
- 它不直接提升 speed，也就是单任务执行速度或延迟下界。

## 九、如何使用虚拟线程

虚拟线程从 API 上看非常直接。Java 21 中常见写法主要有两类。

### 1. 直接创建单个虚拟线程

适合非常简单、明确的线程场景：

```java
Thread thread = Thread.ofVirtual().name("fetch-user").start(() -> {
    String result = callRemoteService();
    System.out.println(result);
});

thread.join();
```

也可以用便捷方法：

```java
Thread thread = Thread.startVirtualThread(() -> {
    doTask();
});

thread.join();
```

### 2. 用每任务一个虚拟线程的执行器

这是最推荐、也最常见的生产用法：

```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    Future<String> f1 = executor.submit(() -> fetchOrder());
    Future<String> f2 = executor.submit(() -> fetchUser());

    String result = f1.get() + " / " + f2.get();
    System.out.println(result);
}
```

这个 API 的关键语义是：

- 每提交一个任务，就创建一个新的虚拟线程。
- 它不是固定大小线程池。
- `close()` 会等待已提交任务完成。

这和传统线程池思维非常不同。

### 3. 服务端最典型的写法

虚拟线程最适合的典型模式是 thread-per-request：

```java
void handleRequest(Request request, Response response) {
    try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
        Future<User> user = executor.submit(() -> userService.load(request.userId()));
        Future<Order> order = executor.submit(() -> orderService.load(request.orderId()));

        response.write(render(user.get(), order.get()));
    } catch (Exception ex) {
        response.fail(ex);
    }
}
```

这里的收益在于：

- 代码仍然是同步、阻塞、线性的。
- 但底层能承受更高并发等待量。
- 排错时栈跟踪仍然天然可读。

### 4. 别忽略中断与取消语义

虚拟线程支持中断语义，但取消依然是协作式的，不是“强制终止”。

- 对 `Future` 调用 `cancel(true)`，会中断正在执行该任务的虚拟线程。
- 在虚拟线程中，很多阻塞 I/O 可被中断唤醒；例如 socket 相关阻塞调用会在中断时被唤醒并关闭底层 socket。
- 如果代码吞掉 `InterruptedException` 或长期不检查中断标记，取消仍然会变慢甚至失效。

最重要的实践仍然是：

- 捕获 `InterruptedException` 后，按语义处理并恢复中断标记（如需要继续向上层传播）。
- 给长任务设计明确的可中断点。

### 5. 进阶：结构化并发（Structured Concurrency）

在 fan-out 场景（一个请求并发调用多个下游）中，`StructuredTaskScope` 往往比手写 `Future` 编排更稳健：失败传播、取消和收束点都更清晰。

```java
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Supplier<User> user = scope.fork(() -> userService.load(request.userId()));
    Supplier<Order> order = scope.fork(() -> orderService.load(request.orderId()));

    scope.join().throwIfFailed();
    response.write(render(user.get(), order.get()));
}
```

需要注意版本状态：

- `StructuredTaskScope` 在 JDK 21 属于预览特性（JEP 453）。
- 使用时需要在编译和运行阶段开启 `--enable-preview`。

## 十、使用虚拟线程时最容易犯的几个错误

### 1. 把虚拟线程继续拿去做线程池复用

这是最常见误区。

很多人会想：

- 平台线程要放在线程池里。
- 那虚拟线程是不是也要搞个固定池、缓存池、共享池？

结论是：

- 不要池化虚拟线程。

原因不是“不能”，而是“没有意义，而且经常有害”。

线程池存在的根本原因，是平台线程昂贵，需要复用。而虚拟线程本来就便宜，正确模型应该是：

- 一个任务一个虚拟线程。

如果你只是把原来 200 个平台线程换成 200 个虚拟线程，收益通常非常有限，因为你并没有改变任务建模方式。

### 2. 想用线程池大小去限制并发

这也是从旧习惯迁移来的误区。

很多项目过去会这样做：

- 开一个大小为 20 的线程池。
- 用它限制某个下游服务最多 20 个并发请求。

在虚拟线程模型下，不应该靠线程池限流，而应该用真正的并发控制原语，例如 `Semaphore`：

```java
Semaphore semaphore = new Semaphore(20);

String call() throws InterruptedException {
    semaphore.acquire();
    try {
        return callRemoteService();
    } finally {
        semaphore.release();
    }
}
```

这才是“任务很多，但某个资源访问要限流”的正确表达。

### 3. 在线程本地变量里缓存昂贵对象

这个问题非常重要。

虚拟线程支持 `ThreadLocal`，这保证了很多旧代码可以直接运行。但“能用”和“应该滥用”不是一回事。

下面这种平台线程时代常见的写法，在虚拟线程时代要特别警惕：

```java
static final ThreadLocal<SimpleDateFormat> FORMATTER =
        ThreadLocal.withInitial(SimpleDateFormat::new);
```

为什么以前这招常见：

- 平台线程数量有限。
- 线程池里的线程会被反复复用。
- 一个昂贵对象放在线程本地变量里，相当于“每个池线程缓存一个”。

但到了虚拟线程时代：

- 每个任务通常都有自己的虚拟线程。
- 线程不会像平台线程池那样被反复复用。
- 大量虚拟线程会把这些本地缓存放大成巨大的内存成本。

所以：

- 可以用 `ThreadLocal` 存上下文。
- 不要轻易用 `ThreadLocal` 缓存昂贵可复用对象。

更合适的做法通常是：

- 用不可变共享对象。
- 用显式对象池或连接池。
- 在上下文传递场景下可评估 Scoped Value（JDK 21 为预览特性）。

### 4. 以为所有异步框架都能自动从虚拟线程中获益

不一定。

虚拟线程最适合的是：

- 线程即任务。
- 阻塞式 I/O。
- 顺序写业务逻辑。

如果你的系统已经是强异步、事件驱动、回调链式模型，直接切成虚拟线程未必自动带来收益。尤其是当框架内部已经：

- 自己管理事件循环。
- 自己维护少量工作线程。
- 大量依赖线程本地缓存与共享线程假设。

那么混用时反而可能让行为更复杂。

### 5. 误把虚拟线程当成“无限免费资源”

虚拟线程虽然便宜，但不是零成本：

- 需要线程对象。
- 需要堆上的栈 chunk。
- 需要调度。
- 需要更大的堆和更合理的 GC 观测。

你当然可以创建几十万甚至上百万虚拟线程，但前提是：

- 这些任务的生命周期、阻塞特征和内存占用真的支持这种规模。

如果每个任务都绑定大量上下文、大对象和 ThreadLocal，虚拟线程一样会把系统拖垮。

## 十一、虚拟线程适合什么场景，不适合什么场景

### 1. 适合的场景

最适合的是下面这类任务：

- 高并发请求处理。
- 请求生命周期里有大量网络 I/O。
- 数据库查询、RPC、HTTP 调用很多。
- 单个任务逻辑希望保持同步线性结构。
- 希望提升吞吐，同时保留良好的调试与排障体验。

典型例子：

- Web 服务。
- API 聚合服务。
- 网关后的业务编排服务。
- 大量外部接口调用型应用。

### 2. 不适合或收益有限的场景

下面这些场景收益通常有限：

- 纯 CPU 密集型批处理。
- 并发量不高的简单应用。
- 任务几乎不阻塞，只是长时间计算。
- 已经高度优化的事件循环模型，而且瓶颈不在线程数量上。

判断方法可以很直接：

- 如果系统真正卡在“线程太贵、线程数不够、同步阻塞代码扩展性差”，虚拟线程很可能有效。
- 如果系统真正卡在 CPU、数据库、网络带宽或外部服务限流，虚拟线程不能替你消除这些硬瓶颈。

## 十二、迁移到虚拟线程时应该怎么思考

迁移重点不是“把所有线程 API 改个名字”，而是先检查你的并发模型。

### 1. 第一类迁移：把线程池任务模型改成每任务一个虚拟线程

如果你现有代码是：

- 大量 `ExecutorService`。
- 大量平台线程池。
- 任务主要是阻塞式 I/O。

那么最自然的迁移方式通常是：

- 先把任务提交入口改为 `Executors.newVirtualThreadPerTaskExecutor()`。
- 观察吞吐、内存、pinning 和下游压力。

### 2. 第二类迁移：把过度异步化的业务逻辑改回同步风格

很多系统过去为了性能被迫写成：

- `CompletableFuture` 链。
- 回调套回调。
- 业务状态在多个 lambda 之间传递。

在虚拟线程时代，可以重新评估这件事：

- 如果异步化只是为了绕开平台线程成本，那么很多逻辑可以改回更直白的阻塞式写法。

这通常会带来很大的可维护性提升。

### 3. 第三类迁移：检查所有旧时代线程习惯

尤其要检查下面这些点：

- 是否依赖固定大小线程池来限流。
- 是否在 `ThreadLocal` 里缓存昂贵对象。
- 是否有吞掉 `InterruptedException` 或忽略中断标记的代码。
- 是否假设“调用取消 API 就会立刻停下来”，但任务本身缺少可中断点。
- 是否在 `synchronized` 内做长时间 I/O。
- 是否依赖某个线程恒定不变的身份。
- 是否调用大量 native 库并在其中阻塞。

虚拟线程最大的迁移成本，往往不是 API，而是心智模型。

## 十三、JVM 工具链如何观察虚拟线程

虚拟线程不是“看不见的黑盒”，JDK 已经给了相当多可观测能力。

### 1. 调试器仍然能按线程看它

因为虚拟线程仍然是 `Thread`，所以：

- 调试器可以单步。
- 可以看调用栈。
- 可以看线程内局部变量。

这是它相对异步回调模型的巨大优势。

### 2. JFR 可以观测关键事件

重点关注：

- `jdk.VirtualThreadStart`
- `jdk.VirtualThreadEnd`
- `jdk.VirtualThreadPinned`
- `jdk.VirtualThreadSubmitFailed`

其中最常用的是 `jdk.VirtualThreadPinned`，它能直接帮助排查扩展性问题。

### 3. jcmd 提供了新的线程转储方式

可以使用新的线程 dump 方式导出虚拟线程信息，例如：

```bash
jcmd <PID> Thread.dump_to_file -format=json threads.json
```

这类转储更适合大量虚拟线程场景，因为传统平铺式线程栈列表在几十万线程面前可读性会非常差。

### 4. 监控口径上的一个边界

迁移后还要留意老监控口径：

- `ThreadMXBean` 主要面向平台线程，不会完整反映虚拟线程状态。
- `Thread.getAllStackTraces()` 返回的是平台线程集合，不适合再用来估算“系统总线程量”。

因此在虚拟线程场景下，建议把 `jcmd` 新线程转储、JFR 事件与应用级指标（请求数、排队时间、超时率）一起看。

## 十四、几个经常被问到的问题

### 1. 虚拟线程是不是协程

从效果和目标上看，它和很多语言里的协程、用户态线程有相似之处，但 Java 暴露给开发者的抽象仍然是 `Thread`，而不是一套全新协程语法。

所以更准确的说法是：

- 它是一种由 JVM/JDK 运行时实现的轻量级用户态线程。

### 2. 虚拟线程是不是一定比线程池快

不一定。

如果你的任务主要在等 I/O，而且并发很高，它通常能显著提升吞吐。

但如果你的任务主要是 CPU 计算，或者并发本来就不高，那么收益可能很有限。

### 3. 可以把所有代码都无脑切成虚拟线程吗

不应该无脑切。

最需要先评估的是：

- 你的阻塞类型。
- 你的同步策略。
- 你的 ThreadLocal 使用方式。
- 你的 native 依赖。

否则你可能只是把旧问题从平台线程时代原样搬过去。

### 4. 虚拟线程会不会取代线程池

更准确地说：

- 它会显著减少“为了复用线程而存在的线程池”的必要性。

但下面这些能力仍然需要：

- 限流。
- 背压。
- 资源隔离。
- 任务编排。

只是这些问题不该再默认用“固定大小线程池”去表达。

### 5. 虚拟线程和 StructuredTaskScope 是一回事吗

不是。

- 虚拟线程是执行单元（线程实现）。
- `StructuredTaskScope` 是并发编排与生命周期收束 API。

两者常一起使用：前者负责“线程很便宜”，后者负责“并发关系有结构、可取消、易观测”。

## 十五、总结：应该怎样理解 JVM 对虚拟线程的实现

把整篇文章压缩成一条主线，可以这样概括：

- 虚拟线程仍然保留了 Java 线程模型的使用方式。
- JVM 与 JDK 运行时把线程的执行状态从固定 OS 线程上解耦出来。
- 大量虚拟线程通过 M:N 调度运行在少量 carrier thread 上。
- 当虚拟线程在可协作的阻塞点等待时，它会 unmount，释放 carrier。
- 它的栈由堆上的 stack chunk 表示，因此可以被轻量保存与恢复。
- 取消与失败传播仍然依赖中断协作和并发结构设计，不存在“强制自动终止”的魔法。
- 真正影响扩展性的核心风险是 pinning、错误的线程池思维和 ThreadLocal 滥用。

所以，虚拟线程最本质的价值不是“线程更多了”，而是：

- Java 终于可以在大量阻塞式并发任务上，同时保住高吞吐和直观编程模型。

如果再进一步压缩成一句工程结论，那就是：

- 对高并发 I/O 型系统，虚拟线程让“写同步代码”重新变成一种既简单又可扩展的默认选择。
