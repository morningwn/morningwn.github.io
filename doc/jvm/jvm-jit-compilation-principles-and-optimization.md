# JVM JIT 即时编译：原理、分层编译与优化机制

很多人知道 Java 是“先编译成字节码，再交给 JVM 执行”，但真正决定程序运行速度的，往往不是 `javac`，而是运行时的 JIT。

JIT，全称 Just-In-Time Compiler，也就是即时编译器。它不是在你写代码时工作，也不是在构建阶段工作，而是在程序运行过程中，一边观察代码真实的执行情况，一边把热点代码编译成本地机器码。

如果只先记一条主线，可以把 JIT 理解成下面这句话：

- Java 代码先被 `javac` 编译成字节码。
- JVM 启动后通常先解释执行，保证启动快、适应性强。
- 当某些方法或循环被反复执行，JVM 会把它们识别成热点代码。
- JIT 再基于真实运行时数据，把这些热点代码编译并优化成本地机器码。
- 所以很多 Java 程序不是一开始最快，而是运行一段时间后越来越快。

这篇文章会按四条主线展开：

- JIT 为什么存在，它到底解决了什么问题。
- JVM 是如何发现热点代码，并决定什么时候编译的。
- HotSpot 的分层编译模型，以及常见优化手段是什么。
- 为什么 JIT 已经编译好的代码还会失效，甚至退回解释执行。

先补一句边界说明：JIT 是 JVM 的运行时编译能力，但不同 JVM 实现的具体策略并不完全一样。下面为了便于理解，主要以 HotSpot 的典型实现为主线展开，比如方法计数、回边计数、C1/C2 和分层编译这些说法，默认都以 HotSpot 为参照。

## 一、先说清楚：JIT 在 JVM 里到底负责什么

理解 JIT，先要区分三个阶段：

- `javac`：把 `.java` 编译成平台无关的字节码。
- 解释器：逐条解释执行字节码，让程序可以立刻跑起来。
- JIT：把运行过程中真正热的字节码编译成当前 CPU 可以直接执行的机器码。

这三者不是互相替代的关系，而是分工协作的关系。

很多初学者会误以为“Java 是编译型语言，所以启动后就应该直接跑机器码”。这并不准确。Java 的第一次编译只是把源码变成字节码，它保留了跨平台能力，但并没有针对当前机器、当前负载、当前分支行为做优化。

JIT 的价值就在这里：

- 它知道当前程序真正跑在什么 CPU 上。
- 它能看到哪些方法最热，哪些分支最常走。
- 它能根据真实类型分布和调用频率做更激进的优化。

换句话说，`javac` 更像“通用翻译”，而 JIT 更像“现场优化师”。

## 二、为什么 JVM 不一开始就把所有代码都编译成本地机器码

这个问题很关键。既然机器码更快，为什么不在程序启动时一次性全部编译完？

因为这样做的成本非常高，而且很多时候并不划算。

### 1. 全量预编译会拖慢启动

如果 JVM 启动时就把所有类、所有方法都编译成高质量机器码，那么：

- 启动时间会显著变长。
- 内存占用会明显上升。
- 很多根本不会执行到的代码，也白白花了编译成本。

对大多数服务来说，真正高频的代码只占整体代码的一小部分。JIT 只优化热路径，投入和收益更匹配。

### 2. 运行时信息只有跑起来之后才知道

很多优化不是“看源码就能决定”的，而是强依赖运行时数据，比如：

- 某个方法到底被调用了多少次。
- 某个虚方法实际常见的接收者类型是什么。
- 某个 `if` 分支在生产流量下是 99% 进入还是 1% 进入。
- 某个对象是否真的逃逸到方法外部。

这些信息在构建阶段通常并不完整，只有程序运行起来以后，JIT 才能据此做针对性优化。

### 3. JVM 需要在启动速度和峰值性能之间做平衡

这也是为什么 HotSpot 没有简单地选“纯解释执行”或“纯预编译”，而是采用了混合模式：

- 冷代码先解释执行，减少启动时延。
- 热代码再进入编译流程，换取峰值性能。

这也是“HotSpot”这个名字的直观含义：

- 不试图把所有地方都优化。
- 只聚焦真正的热点区域。

## 三、JIT 的基本工作流：从解释执行到本地机器码

可以把 JIT 的工作流程理解成下面五步：

- 先解释执行。
- 收集运行时画像。
- 判断哪些代码足够热。
- 编译并安装本地代码。
- 后续优先执行编译后的机器码。

下面按顺序展开。

### 1. 解释器先让程序跑起来

程序启动后，JVM 通常不会立刻对所有方法做复杂编译，而是先由解释器执行字节码。

解释执行的优点很明显：

- 启动快。
- 不需要先付出较大的编译成本。
- 可以边执行边观察真实行为。

缺点也很明显：

- 每次执行都要做字节码分派和语义解释。
- 相比本地机器码，执行效率更低。

因此，解释器的价值不在于“跑得最快”，而在于“尽快启动，并为后续优化提供数据”。

### 2. JVM 会统计方法和循环的热度

JIT 不是凭感觉决定编译谁，而是靠热点探测。

以 HotSpot 为例，常见的热点判断依据包括：

- 方法调用次数。
- 循环回边执行次数。

这里可以把它们理解成两类热点：

- 热方法：整个方法被频繁调用。
- 热循环：方法本身不一定很热，但某个循环执行了大量次。

为什么循环要单独统计？因为很多性能消耗都集中在长时间运行的循环体里。即使一个方法只被调用几次，只要单次调用里有巨大循环，它也值得被编译优化。

### 3. 收集的不只是次数，还有“运行画像”

JIT 真正厉害的地方，不只是“知道谁热”，还在于“知道它是怎么热的”。

典型画像信息包括：

- 哪个调用点大多数时候只看到一种具体类型。
- 哪个条件分支几乎总是走同一条路径。
- 哪些异常路径几乎从不发生。
- 哪些对象只在当前方法内部短暂存在。

这些信息让 JIT 可以做出带有推测性质的优化。也就是说，它不是只做保守优化，而是会在“当前大概率成立”的前提下，生成更激进、更快的机器码。

### 4. 达到阈值后，JIT 开始编译

当某段代码的热度和画像信息积累到一定程度，JVM 会把它交给即时编译器处理。

编译完成后，JVM 会把生成的机器码安装到运行时，后续再执行到这段代码时，就可以直接走本地指令，而不是回到逐条解释模式。

这也是为什么 Java 程序常见下面这种现象：

- 第一次执行不快。
- 运行一段时间后吞吐明显上升。
- 再继续稳定运行，延迟和 CPU 利用率会逐步进入更平稳的状态。

这整个过程通常就被称为预热，也就是 warm-up。

## 四、HotSpot 的分层编译：为什么不是“解释器编一次就结束”

现代 HotSpot 默认采用 Tiered Compilation，也就是分层编译。这里说的是 HotSpot 的典型实现路径，它不是简单地在“解释执行”和“最终优化代码”之间二选一，而是把编译拆成多个层次，兼顾启动速度和最终性能。

如果从工程理解角度简化，可以先抓住三层：

- 解释器：启动最快，但执行最慢。
- C1 编译器：编译速度快，优化相对轻量。
- C2 编译器：编译成本更高，但优化能力更强。

### 1. C1 的目标是尽快把热点代码提速

C1 也常被叫作 Client Compiler。它的特点是：

- 编译速度较快。
- 能较早接管热点代码。
- 优化力度适中。

它更像一个快速响应层，先把最明显的解释执行成本拿掉。

### 2. C2 的目标是追求更高的峰值性能

C2 也常被叫作 Server Compiler。它会使用更复杂的优化策略，例如更激进的内联、循环优化、逃逸分析等。

它的特点是：

- 编译耗时更长。
- 需要更充分的运行画像。
- 生成代码质量更高。

所以很多热点代码并不是“一热就直接进 C2”，而是先进入较低层级，再逐步升级。

### 3. 分层编译本质是在平衡三件事

- 启动速度。
- 编译开销。
- 峰值性能。

如果只有解释器，启动快但长期性能差。

如果一上来只做重度优化编译，长期性能可能高，但启动时延和编译开销都太大。

分层编译的好处就在于：

- 冷代码不浪费资源。
- 稍热代码尽快受益。
- 真正核心的热点路径再交给更强的优化器深挖。

## 五、JIT 常见会做哪些优化

JIT 的优化手段很多，但理解时不用一开始就陷进实现细节。先抓住几个最重要、最常见的方向就够了。

### 1. 方法内联

这是最关键的一类优化之一。

如果一个方法非常短、调用又非常频繁，那么“调用本身”的开销就可能不小。JIT 会尝试把被调方法的逻辑直接展开到调用点。

方法内联的价值不只是少一次调用跳转，更重要的是：

- 调用边界消失后，优化器能看到更大范围的代码。
- 后续的常量折叠、死代码删除、分支消除会更容易发生。

很多后续优化，其实都建立在“先内联成功”这个前提上。

### 2. 去虚拟化与类型特化

Java 大量依赖多态调用，但多态本身会让目标方法在编译期不容易确定。

这里先要区分一个容易混淆的点：这一节说的不是云计算、容器或虚拟机语境里的“虚拟化”，而是面向对象方法调用里的“虚调用”。

更准确地说：

- 虚调用：指方法真正要执行哪个实现，要到运行时才能根据对象实际类型决定。
- 去虚拟化：指 JIT 尽量把这种“运行时再决定目标”的调用，优化成“当前已经可以直接确定目标”的调用。
- 类型特化：指在已经掌握类型信息的前提下，针对某一种或少数几种高频类型生成更有针对性的机器码。

先看一个最常见的多态例子：

```java
interface Animal {
	void speak();
}

class Dog implements Animal {
	@Override
	public void speak() {
		System.out.println("wang");
	}
}

class Cat implements Animal {
	@Override
	public void speak() {
		System.out.println("miao");
	}
}

void call(Animal animal) {
	animal.speak();
}
```

在这个例子里，`animal.speak()` 可以把它理解成一个广义上的动态分派调用。这里为了便于说明，沿用“虚调用”这个更常见的工程说法；如果落到更具体的字节码层面，它是接口调用语义，因为：

- 变量静态类型只是 `Animal`。
- 真正执行 `Dog.speak()` 还是 `Cat.speak()`，要看运行时传进来的对象类型。
- 这一步动态分派虽然灵活，但会增加调用成本，也会阻碍后续优化。

如果 JIT 发现某个调用点在运行时几乎总是同一种接收者类型，它就可能：

- 推测这个调用点是单态的。
- 直接按具体实现生成更快的调用路径。

这就是去虚拟化最核心的意思：

- 原本这次调用要先做一次“你到底是谁”的动态判断。
- 现在 JIT 根据运行画像认为“这里基本上一直都是 `Dog`”。
- 那它就可以直接朝 `Dog.speak()` 这条路径生成代码，而不是每次都保留完整的动态分派成本。

而类型特化可以理解成在此基础上更进一步：

- 不只是确定“这里大概率是 `Dog`”。
- 还会围绕 `Dog` 的具体布局、具体实现、具体分支行为去组织更高效的机器码。

如果把它说得更直白一些：

- 去虚拟化关注的是“调用目标能不能先确定下来”。
- 类型特化关注的是“既然类型已经基本确定，能不能按这个具体类型把代码继续做窄、做深、做快”。

这类优化通常还会和方法内联连在一起发生：

- 先通过类型画像把虚调用去虚拟化。
- 再把目标方法内联到调用点。
- 内联后，围绕具体类型继续做常量折叠、分支消除甚至对象访问优化。

当然，这种优化很多时候都带有推测性质。也就是说，JIT 不是在规范层面证明“这里只可能是 `Dog`”，而是根据当前运行时画像认为“这里几乎总是 `Dog`”。

因此一旦后续运行中出现新的类型分布，例如这个调用点开始频繁收到 `Cat`，那么：

- 先前基于 `Dog` 做的去虚拟化或类型特化代码就可能不再适合。
- JVM 可能触发去优化，回退后重新收集画像，再生成新的代码。

这类优化本质上依赖运行时类型画像，因此非常符合 JIT 的优势。

### 3. 常量折叠与死代码删除

如果某些值在运行时已经可以确定，JIT 会直接把计算结果折叠掉，而不是保留原始表达式。

同理，如果某段分支在当前优化上下文里已经不可能走到，或者其结果对外不可见，那么对应代码也可能被删除。

这类优化看起来基础，但在热点路径上很常见，也很有效。

### 4. 循环优化

热点往往集中在循环里，因此循环相关优化非常重要，例如：

- 减少循环体内重复计算。
- 把可以提前的表达式挪到循环外。
- 优化边界检查。
- 让循环体更利于 CPU 指令流水和缓存命中。

JIT 对长时间运行循环的关注度很高，这也是为什么热循环会被单独统计。

### 5. 逃逸分析与标量替换

如果一个对象只在当前方法或当前线程内部短暂使用，没有“逃逸”到外部，那么 JIT 可能进一步做优化，比如：

- 消除不必要的同步。
- 把对象拆成若干标量值处理，而不是保留完整对象分配。

很多人会把这类能力笼统地称为“栈上分配”，但更准确地说，JIT 能做的是基于逃逸分析减少对象分配及相关开销，具体呈现形式由实现决定。

## 六、为什么 JIT 编出来的代码还会失效：去优化是什么

JIT 并不是一旦编译成功，就永远正确且最优。因为它很多时候依赖的是“当前大概率成立”的推测。

只要推测条件变化，之前生成的机器码就可能不再适合。

这时 JVM 就会触发去优化，也就是 deoptimization。

### 1. 去优化不是失败，而是 JIT 设计的一部分

例如某个调用点之前几乎只看到一种类型，因此 JIT 把它按单态调用优化了。但后来系统上线新模块、动态加载新实现类，或者流量模式变化，导致这个调用点不再满足原先假设。

这时 JVM 可以：

- 让已经编译好的机器码失效。
- 回退到解释执行或较低层级编译代码。
- 重新收集画像，再做新的编译决策。

所以，JIT 不是“只做绝对安全的静态优化”，而是：

- 在保证语义正确的前提下，允许自己先大胆优化。
- 一旦前提不成立，再安全回退。

这也是它为什么能同时做到“激进”和“正确”。

### 2. 去优化和性能波动的关系

在真实系统里，如果代码路径、类加载情况、数据分布变化较大，JIT 编译与去优化会带来一定的性能波动。

因此看 Java 程序性能，不能只盯一两次请求或单次方法耗时，更要关注：

- 是否已经完成预热。
- 当前流量模型是否稳定。
- 是否存在频繁去优化或代码缓存压力。

## 七、OSR：为什么长循环不用等下次调用才变快

还有一个非常关键但常被忽略的机制，叫 OSR，也就是 On-Stack Replacement，栈上替换。

它解决的是这样一个问题：

- 某个方法已经进入执行。
- 但方法内部有个很长的循环。
- 如果必须等整个方法执行完，下次再走编译代码，收益就太晚了。

OSR 的意义就在于：

- 让 JVM 可以在方法执行到一半时，直接把热点循环切换到编译后的机器码继续跑。

这使得 JIT 不仅能优化“频繁调用的方法”，也能及时优化“单次执行很久的循环”。

## 八、为什么做 Java 性能测试一定要考虑预热

这和 JIT 直接相关。

如果你只执行一次方法就统计耗时，测出来的往往混杂了很多因素：

- 类加载开销。
- 解释执行开销。
- JIT 尚未触发。
- 编译过程本身的扰动。

所以判断 Java 代码性能，必须区分：

- 冷启动性能。
- 预热过程表现。
- 稳态吞吐与稳态延迟。

这也是为什么严肃的 Java 微基准通常要用 JMH。它的核心价值之一，就是帮助你规避 JIT 预热不足、死代码消除、常量折叠误导等常见陷阱。

## 九、JIT 和 AOT 的区别是什么

JIT 和 AOT 不是简单的“谁先进谁落后”，而是面向不同目标的两种策略。

JIT 的特点是：

- 启动时不必完成全量优化。
- 可以基于真实运行时画像做动态优化。
- 峰值性能通常更强。

AOT，也就是 Ahead-Of-Time 编译，更偏向：

- 提前产出本地代码。
- 降低启动阶段解释或即时编译的成本。
- 用更确定的构建产物换取更短启动时间。

两者的关键差异不在于“是否生成机器码”，而在于：

- AOT 的优化时机在运行前。
- JIT 的优化时机在运行中。

因此，JIT 更擅长利用现场信息，AOT 更擅长控制启动时间和部署形态。

## 十、理解 JIT 时最容易出现的几个误区

### 1. 误区一：Java 慢，是因为它一直在解释执行

不准确。现代 Java 服务在稳定运行后，大量核心热点代码通常早已进入 JIT 编译状态。真正需要关注的是：

- 你的热点是否真的足够稳定，能被有效优化。
- 是否存在大量阻塞、锁竞争、对象分配或缓存未命中。
- 是否把冷启动问题误判成了长期吞吐问题。

### 2. 误区二：JIT 优化一定稳定不变

也不准确。JIT 优化依赖热点和画像，运行环境变化后可能重新编译，也可能去优化回退。

### 3. 误区三：只要打开更多 JVM 参数，JIT 就会更快

大多数场景下，不应该先靠手调参数解决问题，而应该先确认：

- 基准测试是否可靠。
- 性能瓶颈是否真的在 CPU 执行层。
- 代码结构是否阻碍了 JIT 做优化。

很多时候，写出更稳定、更容易内联、更少逃逸、更少无效抽象的代码，比盲目调参数更有效。

## 十一、总结：JIT 的核心价值到底是什么

把整篇文章压缩成一句话，JIT 的本质是：

- 让 JVM 不必在启动时为所有代码付出昂贵优化成本。
- 而是在程序运行过程中，只针对真正的热点代码，结合真实现场信息生成更快的本地机器码。

因此，JIT 的关键不是“把字节码翻译成机器码”这么简单，而是：

- 先解释执行，快速启动。
- 再探测热点，积累画像。
- 用分层编译逐步提升代码质量。
- 借助内联、逃逸分析、循环优化等手段逼近本地程序性能。
- 在假设失效时通过去优化安全回退。

理解了这条主线，你就更容易看清很多 Java 性能现象背后的原因，比如：

- 为什么程序会越跑越快。
- 为什么压测前必须预热。
- 为什么某些抽象写法会影响 JIT 优化空间。
- 为什么“已经编译过的代码”仍然可能再次变化。

如果把类加载解决的是“类怎么进 JVM”，GC 解决的是“对象怎么回收”，那么 JIT 解决的就是另一个核心问题：

- 字节码怎样在真实运行现场里，被逐步打磨成更高效的执行路径。
