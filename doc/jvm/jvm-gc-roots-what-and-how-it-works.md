# JVM 垃圾回收中的 GC Roots 是什么

> 在学习 JVM 垃圾回收时，GC Roots 几乎是绕不过去的概念。很多资料会直接说：
> - GC Roots 是一组根对象。
> - 从这些根出发能到达的对象，就是存活对象。
> - 到达不了的对象，才有可能被回收。
> 
> 这几句话没有错，但只记住这个结论，通常还是会觉得抽象。 
> 
> 真正需要理解的是下面这条主线：
> - JVM 不是靠引用计数判断对象是否存活。
> - 它更常用的是可达性分析。
> - 可达性分析必须先找到一批起点。
> - 这批起点，就是 GC Roots。 
> 
> 所以，GC Roots 本质上不是一种特殊对象类型，而是垃圾回收在做对象存活判定时所选择的起点集合。

## 一、为什么 JVM 需要 GC Roots

先从一个更基础的问题开始：

- JVM 到底怎么判断一个对象是不是垃圾？

最直观的想法是引用计数，也就是给每个对象记一个数字：

- 多一个地方引用它，计数加一。
- 少一个地方引用它，计数减一。
- 计数变成零，就说明没人用了，可以回收。

这种方法听起来简单，但有一个非常致命的问题：循环引用。

比如下面这种情况：

```java
class A {
    B b;
}

class B {
    A a;
}
```

如果 A 和 B 互相引用，但外部已经没有任何地方再引用它们，那么：

- A 的引用计数不是零。
- B 的引用计数也不是零。
- 但这两个对象其实已经不可能再被程序使用。

这时，单纯靠引用计数就无法正确回收。

因此，主流 JVM 更常用的是可达性分析。它的判断思路是：

- 不去看一个对象被引用了几次。
- 而是去看这个对象能不能从某些“根起点”一路走到。

如果能走到，说明它仍然处在程序可使用的对象图里；如果走不到，说明它已经脱离了业务可访问范围。

而这些“根起点”，就是 GC Roots。

## 二、先看结论：GC Roots 到底是什么

可以先把 GC Roots 记成一句话：

- GC Roots 是垃圾回收器进行可达性分析时，用来遍历对象图的一组起始引用。

这里有两个关键词。

### 1. 起始引用

GC Roots 不是“整个堆里最老的对象”，也不是“永远不会被回收的对象”。

它强调的是：

- 回收器从哪里开始找活对象。

也就是说，GC Roots 更像遍历图结构时的入口，而不是某种业务语义上的特殊实例。

### 2. 一组，而不是一个

垃圾回收不是只从某一个对象往下看，而是会从多个来源同时出发，比如：

- 正在执行的方法栈帧里保存的引用。
- 类静态属性持有的引用。
- JNI 代码持有的引用。
- 某些 JVM 内部保留的系统对象引用。

这些来源共同组成 GC Roots 集合。

## 三、GC Roots 和普通引用的区别是什么

这个问题很重要，因为很多人会把“被引用”和“是 GC Roots”混在一起。

普通引用的意义是：

- 一个对象字段、数组元素、局部变量或其他位置，指向了另一个对象。

GC Roots 的意义则是：

- 这些引用本身处在分析起点的位置。

可以把整个堆里的对象关系想象成一张图。

- 普通引用是图中的边。
- 普通对象是图中的节点。
- GC Roots 是遍历这张图时的入口集合。

所以，一个对象是不是 GC Roots，不取决于它“重不重要”，而取决于它当前是否位于垃圾回收器认可的根位置上。

## 四、JVM 中常见的 GC Roots 有哪些

这是最常见，也最容易考察的一部分。不同资料表达方式略有差异，但核心范围基本一致。HotSpot 实现中，根集合的具体来源和扫描方式会随垃圾回收器而有所不同。

### 1. 虚拟机栈中的引用

这是最常见的一类。

当一个线程正在执行某个方法时，这个方法对应的栈帧里会保存局部变量表和操作数栈。局部变量表或操作数栈中存放的对象引用，都会被视为 GC Roots。

例如：

```java
public void process() {
    User user = new User();
    user.name = "Tom";
}
```

在 process 方法还没有执行结束之前：

- 局部变量 user 持有对 User 对象的引用。
- 这个引用位于当前线程栈帧中。
- 因此它会被当作 GC Roots 的一部分。

一旦方法执行结束，栈帧出栈，这个引用也就不再属于根集合。

所以很多对象能否被回收，和方法调用是否结束有直接关系。

### 2. 本地方法栈与 JNI 引用

如果 Java 代码调用了本地方法，JNI 层也可能持有 Java 对象引用。

- JNI local references 存放在本地引用表中，通常只在本地方法调用期间有效。
- JNI global references、weak global references 则可以跨本地方法保存更长时间。

只要这些引用仍然有效，JVM 就必须把对应对象视为存活对象，否则本地层继续使用时，对象可能被错误回收。

因此：

- 本地方法栈以及 JNI 引用表中的对象引用，
- 也会被当作 GC Roots。

### 3. 类元数据中的静态字段引用

类变量是跟类本身绑定的，不依赖某个对象实例存在。在 HotSpot 中，这类信息属于类元数据（也可以理解为方法区/元空间）的一部分。

例如：

```java
class CacheHolder {
    static Map<String, Object> CACHE = new HashMap<>();
}
```

只要这个类还处于已加载且可用的状态，那么：

- 静态字段 CACHE 持有的对象引用，
- 就会作为 GC Roots 来源之一。

这也是为什么不恰当地使用 static 容器，很容易导致对象长期无法释放。

### 4. 运行时常量池中的引用

运行时常量池中的某些常量，也可能关联对象引用。

比如字符串常量、符号引用解析后的对象引用，在 JVM 内部可能形成一部分根可达关系。

这类内容在业务开发中感知不如栈和静态字段强，但从原理上说，它们也属于常见根来源之一。

### 5. 锁对象和线程内部结构持有的引用

如果一个对象正被 synchronized 关联的监视器使用，或者被线程内部的相关数据结构引用，那么它也会被可达性分析保留。

更准确的说法是：

- 对象本身不是因为“被锁住”而单独成为根，
- 而是通过线程相关的内部引用链被访问到。

因此，持有锁的对象通常会被认为可达，而不是独立于线程栈之外的特殊根。

### 6. JVM 内部运行时与系统结构引用

除了应用代码能直接看到的引用，JVM 自身还会维护一些运行时内部引用，例如：

- 线程对象、类加载器对象；
- JNI 全局引用、反射缓存；
- 异常对象、类元数据；
- JIT 编译器、运行时服务使用的内部结构。

这些引用也会作为 GC Roots 或根扫描的一部分来源。

所以 GC Roots 不只是“你写出来的代码里有哪些引用”，还包含 JVM 为保证运行时正确性必须保留的那些系统级引用。

## 五、GC 是如何利用 GC Roots 判断对象存活的

理解这一步，GC Roots 才真正从概念变成流程。

垃圾回收器做可达性分析时，可以粗略理解为下面几个步骤：

1. 先枚举所有 GC Roots。
2. 从每个 Root 出发，沿着引用关系向下遍历。
3. 所有能被遍历到的对象，都标记为可达。
4. 遍历结束后，仍然没有被标记到的对象，就被视为不可达对象。

可以把这个过程想象成从多个入口做图搜索。

例如对象关系如下：

- 栈变量 rootA 指向对象 A。
- A 指向 B。
- B 指向 C。
- 另一个对象 D 和 E 互相引用。
- 但没有任何 GC Roots 能走到 D 或 E。

那么最终结果会是：

- A、B、C 是可达对象。
- D、E 即使互相引用，也仍然是不可达对象。

这正是可达性分析能解决循环引用问题的根本原因。

## 六、对象不可达以后，是不是一定马上回收

不一定。

这是另一个常见误区。

对象对 GC Roots 不可达，意味着它在可达性分析中已经被判定为“可以回收的候选对象”，但这不等于它会立刻从内存中消失。

中间还会受到很多因素影响，比如：

- 当前采用的垃圾回收器实现。
- 本轮 GC 是 Minor GC、Major GC 还是 Mixed GC。
- 回收器是否选择并发清理。
- 对象是否涉及终结机制。

尤其是带有 finalizer 的对象，历史上还会经历额外判定流程。虽然现代开发中不推荐依赖这套机制，但从原理上说：

- 不可达，不等于立刻释放。
- 不可达的核心含义是：它已经不再被认为是业务可用对象图的一部分。

## 七、GC Roots 枚举为什么很重要

很多人会把重点全放在“标记和清理”上，但真实实现里，GC Roots 枚举本身就是一次很关键的工作。

原因很简单：

- 如果根枚举漏掉了一个本该存在的引用，那么本来还活着的对象就可能被错误回收。
- 如果根枚举把不该保留的对象链保留住了，那么垃圾对象就可能继续留在堆中。

也就是说，根枚举直接决定了可达性分析的边界是否正确。

因此在 HotSpot 中，GC Roots 枚举通常要求：

- 结果必须准确。
- 成本尽量可控。
- 在停顿时间上尽量短。

这也是为什么很多 GC 算法在设计时，都非常关注根扫描阶段的优化。

## 八、为什么 GC Roots 枚举常常需要 Stop-The-World

这部分很容易和并发标记混淆。

很多回收器虽然能做到“并发标记”或者“并发清理”，但在某些关键阶段仍然要暂停用户线程，其中一个重要原因就是根枚举。

原因在于：

- 线程的栈帧在不断变化。
- 局部变量引用关系也在实时变化。
- 如果枚举根的时候应用线程还在随意修改这些状态，就很难得到一个一致的起点集合。

所以通常会在某个短暂停顿点：

- 先把线程状态稳定下来。
- 快速枚举根集合。
- 再基于这个相对稳定的视图继续后续工作。

不同回收器会通过写屏障、读屏障、快照算法等方式降低整体停顿，但“先得到一个可靠的根视图”始终是核心要求。

## 九、GC Roots 会不会被回收

这个问题要分开看。

如果问的是“作为根位置的引用会不会消失”，答案当然是会。

例如：

- 方法执行完毕，局部变量出栈。
- 静态字段被重新赋值为 null。
- JNI 不再持有该对象引用。

这些情况下，对应的根关系都会消失。

但如果问的是“被当作 GC Roots 的对象是不是永远不能回收”，答案是否定的。

关键不在对象本身，而在它当前是否还能通过根位置被访问到。

也就是说：

- 某个对象这一刻可能因为栈变量引用而成为根可达链上的一部分。
- 下一刻方法执行结束，它就可能不再可达。
- 后续自然也可能被 GC 回收。

因此，不要把 GC Roots 理解成“永久存活对象名单”。

## 十、业务开发里最容易遇到的几个 GC Roots 相关问题

理解 GC Roots 的价值，不只是为了面试，更是为了定位内存问题。

### 1. 静态集合导致对象无法释放

最典型的是：

- 把对象放进 static Map 或 static List。
- 后续忘记删除。

由于静态字段属于根来源之一，对象即使业务上已经没用了，仍然能从 GC Roots 走到，因此不会被回收。

### 2. 线程长期存活，ThreadLocal 对象残留

线程对象本身往往属于 JVM 重点维护对象。如果线程生命周期很长，而 ThreadLocal 使用后没有及时 remove，那么相关对象就可能沿着线程关联结构长期存活。

这类问题本质上也是：

- 根链没有断。
- 所以对象仍然可达。

### 3. 局部变量作用域比想象中更长

有些对象明明“后面不用了”，但方法还没结束，局部变量槽位里可能仍然保留引用，于是在这一轮 GC 里对象还是可达的。

虽然 JIT 和编译器会做很多优化，但从原理理解上，这仍然是分析对象为何未回收的重要视角。

### 4. 类加载器泄漏

如果某个类加载器无法释放，那么它加载的类、静态字段、常量池关联内容等都可能一起被保留，最终形成更复杂的内存泄漏链路。

这类问题在容器、插件化框架、热部署场景里尤其需要关注。

## 十一、如何正确理解 GC Roots 在排查问题中的作用

当你在内存分析工具里看到某个对象没有被回收时，真正要追的问题通常不是：

- 为什么 GC 没有工作？

而是：

- 为什么这个对象还能从 GC Roots 走到？

也就是说，排查内存泄漏时，重点是找“引用链”而不是只看“对象数量”。

常见分析路径通常是：

1. 先找到占用较高的对象。
2. 查看它到 GC Roots 的引用路径。
3. 找到是哪一个根来源把它继续挂住。
4. 再回到业务代码判断这条引用链是否合理。

这也是为什么很多堆分析工具都会提供一项非常核心的能力：

- Path to GC Roots。

因为只要根链还在，对象就不是垃圾。

## 十二、总结

把整篇文章收束成几条最关键的结论：

- GC Roots 是垃圾回收器做可达性分析时的一组起始引用。
- JVM 判断对象存活，核心不是引用计数，而是看对象能否从 GC Roots 到达。
- 常见的 GC Roots 包括栈中的局部变量引用、JNI 引用、静态字段引用、常量引用以及 JVM 内部保留引用。
- 只要对象仍然能沿着根链被访问到，它就不会被判定为垃圾。
- 排查内存泄漏时，真正重要的是对象到 GC Roots 的引用路径。

如果把 JVM 垃圾回收浓缩成一句最核心的话，可以这样记：

- GC 不是在问“这个对象有没有被谁引用过”，而是在问“从 GC Roots 出发，现在还能不能走到它”。

理解了这一点，后面再看分代回收、并发标记、G1、ZGC，很多实现细节都会更容易串起来。
