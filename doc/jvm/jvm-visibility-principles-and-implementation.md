# JVM 如何实现可见性：原理与实现方式

在并发编程里，可见性指的是：一个线程对共享变量的修改，另一个线程能够在符合语义约束的时间点观察到。

很多人会把这个问题简单理解成“CPU 缓存导致线程看不到最新值”，这只说对了一部分。严格来说，Java 中的可见性不是某一层单独解决的，而是下面几层共同完成的：

- Java 内存模型（JMM）定义什么叫“必须可见”。
- JVM 解释器与 JIT 编译器负责把这些语义翻译成具体的读写约束。
- 运行时和底层 CPU 通过缓存一致性协议、内存屏障和锁原语，让这些约束真的落到硬件上。

所以，“JVM 如何实现可见性”更准确的表述应该是：

- JMM 规定可见性语义。
- HotSpot 之类的 JVM 实现通过 volatile、锁、final 语义、线程同步原语和内存屏障来兑现这些语义。

这篇文章会从问题根源开始，逐层解释 JVM 是如何把“变量更新对其他线程可见”这件事做出来的。

## 一、可见性问题到底从哪里来

如果程序只有一个线程，那么变量写入后再读取，通常不会有“看不到”的问题。可一旦进入多线程场景，就会同时出现三类现象：

- 编译器为了优化性能，会调整指令顺序。
- CPU 为了提高吞吐，会使用寄存器、缓存和写缓冲区，不会每次都直接访问主内存。
- 多核 CPU 上，每个核心看到内存变化的时机并不天然一致。

这意味着下面这个程序在多线程下可能永远不结束：

```java
class VisibilityDemo {
    static boolean running = true;

    public static void main(String[] args) {
        new Thread(() -> {
            while (running) {
                // busy spin
            }
            System.out.println("stopped");
        }).start();

        running = false;
    }
}
```

从源码直觉看，主线程已经把 `running` 改成了 `false`，循环线程应该退出。但实际上，如果没有任何同步手段，JMM 不保证第二个线程什么时候能看到这个新值，甚至不保证它一定按你的预期重新读取。

这里至少有几种可能：

- 读线程把 `running` 的值缓存到了寄存器或核心缓存里。
- JIT 发现循环体里没有同步动作，可能把读取外提，减少重复加载。
- 写线程虽然写入了新值，但这个写入还停留在本核的写缓冲区，没有在目标线程观察点上形成可见效果。

所以，可见性问题的本质不是“值没有改”，而是“另一个线程没有被语义上强制看到这个改动”。

## 二、JMM：Java 先定义什么叫“可见”

JVM 不能直接依赖某一款 CPU 的行为，因为 Java 程序要跨平台运行。因此 Java 先定义了一层抽象规范：Java Memory Model，也就是
JMM。

JMM 不直接规定某个字段一定放在哪一级缓存里，也不要求所有实现都采用同样的机器指令。它规定的是：

- 哪些操作之间允许重排序。
- 哪些写入必须对后续读操作可见。
- 哪些同步动作会建立线程之间的先行发生关系。

JMM 里常见的一个描述是“主内存”和“工作内存”：

- 主内存可以理解为共享变量的逻辑存储位置。
- 每个线程有自己的工作内存，里面保存了共享变量的使用副本。

这不是说 JVM 一定真的划出了两块这样的物理内存，而是一个抽象模型。它的作用是解释：线程对共享变量的操作，很多时候并不是直接对全局唯一的一份值反复读写，而是可能先基于局部副本执行。

也正因为如此，JMM 才需要告诉 JVM：在什么时机必须把线程内的写入“发布”出去，在什么时机必须让线程重新“获取”最新值。

## 三、happens-before：JMM 用什么描述可见性

JMM 里最核心的概念不是缓存，而是 happens-before。

可以把它理解成一个语义规则：

- 如果 A happens-before B，那么 A 的结果对 B 可见。
- 同时，A 的执行顺序也不能在语义上跑到 B 后面去。

这一定义非常关键，因为它把“可见性”和“有序性”绑在了一起。很多同步原语本质上都是通过建立 happens-before 来解决可见性。

JMM 规定了一些重要的 happens-before 规则。

### 1. 程序次序规则

同一个线程内，按照程序顺序，前面的操作 happens-before 后面的操作。

这只是单线程语义，不足以解决线程之间的可见性。

### 2. volatile 变量规则

对一个 volatile 变量的写，happens-before 后续任意线程对这个变量的读。

这是 volatile 能解决可见性的直接原因。

### 3. 监视器锁规则

对同一个锁对象的 unlock，happens-before 后续对这个锁对象的 lock。

这就是 synchronized 能保证可见性的根本原因。

### 4. 线程启动规则

线程 A 调用线程 B 的 `start()` 之前的操作，happens-before 线程 B 中的任意操作。

### 5. 线程终止规则

线程中的所有操作，happens-before 其他线程从 `join()` 成功返回，或观察到线程终止。

### 6. final 字段规则

对象构造完成后，只要没有让 `this` 在构造过程中逸出，其他线程一旦读到这个对象引用，就能看到构造函数里对 final 字段的正确初始化结果；但这种更强的初始化可见性主要针对 final 字段本身，不自动扩展为对象全部状态都线程安全。

这条规则也是 JVM 实现可见性的重要组成部分。

反过来说，如果两个线程之间没有建立 happens-before，那么程序并不是“可能慢一点看到最新值”这么简单，而是 JMM 不再保证你期望的读取结果、重排序方式和可见时机。某次运行恰好“看起来正常”，不能把它当成语义依据。

## 四、JVM 真正靠什么把可见性做出来

JMM 是规范，不是实现。真正把语义变成行为的是 JVM。对 HotSpot 来说，可见性主要靠下面几类机制实现：

- 特殊字段语义：volatile、final。
- 监视器语义：synchronized 对应的 monitorenter/monitorexit。
- 编译器约束：禁止某些重排序。
- 内存屏障：在关键读写前后插入 acquire、release、full fence 一类约束。
- 底层硬件支持：缓存一致性协议、原子指令、锁指令与屏障指令。

下面分别展开。

## 五、volatile：最直接的可见性实现手段

`volatile` 是 Java 里最典型、也最容易被拿来说明可见性的机制。

```java
class VisibilityDemo {
    static volatile boolean running = true;

    public static void main(String[] args) {
        new Thread(() -> {
            while (running) {
            }
            System.out.println("stopped");
        }).start();

        running = false;
    }
}
```

给 `running` 加上 volatile 后，JMM 就要求：

- 写线程对 `running = false` 的写入，必须对后续读取 `running` 的线程可见。
- 相关读写不能被随意重排，破坏这条语义。

### 1. 类文件层面：字段会带上 volatile 标记

Java 源码里的 volatile 字段，在 class 文件里会以 `ACC_VOLATILE` 访问标志出现。也就是说，JVM 在解析类元数据时就知道这个字段不是普通字段。

这一步本身不产生可见性，但它让解释器、JIT 编译器和运行时能对这个字段走特殊路径。

### 2. 编译器层面：不能按普通字段优化

对于普通字段，如果编译器证明某个值在循环中“看起来没有变化”，它可能把读操作缓存到寄存器里，或者减少重复加载。

但对 volatile 字段，JIT 不允许这么做。每次 volatile 读都必须保留“从内存语义上重新获取”的效果，每次 volatile 写都必须保留“对外发布”的效果。

换句话说，volatile 首先限制了编译器优化空间。

### 3. 内存屏障层面：在读写前后插入约束

JVM 最核心的实现动作，是在 volatile 读写周围插入内存屏障。

可以把内存屏障理解成一种约束点，它告诉编译器和 CPU：

- 某些读写不能穿过这个点重排。
- 某些写入必须在这个点之前真正对其他核心可见。
- 某些后续读必须在这个点之后重新观察共享状态。

从抽象语义看，volatile 常被概括为：

- volatile 写带有 release 效果。
- volatile 读带有 acquire 效果。
- 两者共同参与对 volatile 访问顺序的约束。

不过这更适合当作理解模型，而不是“每个平台都固定插入同一组屏障”的字面规则。更准确地说，HotSpot 会根据目标架构选择足以满足 JMM 的屏障或等价指令序列。

如果用更细的屏障术语去帮助理解，可以近似把它记成：

- 在 volatile 写附近，需要保证前面的普通读写不会越过这个发布点跑到后面。
- 在 volatile 读附近，需要保证后面的普通读写不会越过这个获取点跑到前面。
- 对于像 StoreLoad 这样最容易破坏发布-获取关系的重排，JVM 会在需要的地方补上更强的约束。

因此，volatile 真正做的不是“每次都直接读主内存”这么一句口号，而是通过屏障建立发布与获取关系。

### 4. 硬件层面：不同 CPU 的落地方式不同

JMM 是统一的，但不同 CPU 内存模型不一样，所以 HotSpot 生成的机器指令也不完全相同。

在 x86 这类相对强内存模型的架构上：

- 很多读写顺序天然比 JMM 要强。
- HotSpot 往往可以更多利用处理器已有保证，而不是为每次 volatile 访问都发出重量级栅栏。
- 具体落地可能是普通读写配合编译器约束，也可能在关键位置借助带锁前缀的指令或显式栅栏来补齐语义。

在 ARM、RISC-V 这类更弱的内存模型上：

- CPU 允许更多重排序。
- JVM 往往需要显式发出更明确的 acquire/release 或 full fence 指令。

也就是说，同样一行 `volatile`，在不同平台下的机器码未必一样，但最终都必须满足同一个 JMM 语义。

### 5. volatile 解决什么，不解决什么

volatile 能解决：

- 一个线程写入后，另一个线程随后读取能看到最新值。
- 以这个变量为同步点的部分有序性问题。

volatile 不能单独解决：

- 复合操作的原子性，比如 `count++`。
- 多个变量之间更复杂的不变式维护。

所以它适合做状态标志、发布通知、单次赋值后只读配置等场景，但不适合替代锁去维护复杂共享状态。

## 六、synchronized：通过锁的获取与释放保证可见性

很多人知道 synchronized 能保证互斥，却忽略了它同样保证可见性。

```java
class Counter {
    private int value;

    public synchronized void increment() {
        value++;
    }

    public synchronized int get() {
        return value;
    }
}
```

这里的关键不是“方法前面有 synchronized”这几个字，而是 JMM 规定：

- 释放同一把锁的线程，在临界区内的写入，必须对之后获取这把锁的线程可见。

### 1. 字节码层面：monitorenter 和 monitorexit

synchronized 代码块在字节码里会变成 `monitorenter` 和 `monitorexit`。同步方法则通过方法访问标志和隐式监视器语义实现，但本质效果一致。

JVM 在执行这些字节码时，不只是完成“谁拿到了锁”，还要兑现对应的内存语义。

### 2. 语义层面：unlock 是 release，lock 是 acquire

可以把 synchronized 的可见性理解成：

- 退出临界区时，线程执行一次 release。
- 进入临界区时，线程执行一次 acquire。

release 的意思是：

- 临界区里对共享变量的修改，不能在语义上被拖到 unlock 之后。

acquire 的意思是：

- 后续对共享变量的读取，不能在语义上跑到 lock 之前。
- 线程进入临界区后，必须能够观察到上一个持锁线程释放前已经发布的结果。

这就是为什么即便一个字段不是 volatile，只要所有读写都被同一把锁保护，线程之间依然能看到彼此的更新。

### 3. HotSpot 实现上并不只有一种锁路径

HotSpot 会根据竞争情况使用不同的锁实现路径，比如轻量级快速路径、膨胀后的 ObjectMonitor
路径等。具体锁状态细节可能随版本演进而变化，但对可见性来说有一条原则始终不变：

- 不管锁走的是哪条优化路径，最终都必须满足 JMM 对 monitor 的 happens-before 语义。

也就是说，锁可以优化，但可见性语义不能优化掉。

## 七、final：构造完成后的安全发布也是可见性

很多文章讲可见性只讲 volatile 和 synchronized，其实 final 也是 JVM 可见性设计里很重要的一环。

看下面这个例子：

```java
class Holder {
    final int value;

    Holder() {
        value = 42;
    }
}
```

如果一个 `Holder` 对象在构造期间没有发生 `this` 逸出，那么其他线程一旦读到这个对象引用，JMM 就要求它至少能看到`value = 42`，而不是默认值 `0`。

这背后的实现点在于：

- 编译器和处理器不能把 final 字段初始化重排到对象发布之后。
- JVM 需要在构造完成这一边界上维持 final 字段的冻结语义。

final 不等于对象内部状态永远线程安全。它保证的是“构造完成时写进去的 final 值”具备更强的初始化可见性；如果对象里还有普通可变字段，这些字段仍然需要额外同步来保证线程安全。

这也是不可变对象为什么更容易天然线程安全的重要原因之一。

## 八、线程启动、结束与其他同步原语也在提供可见性

除了 volatile、synchronized、final，JVM 还通过其他同步边界建立 happens-before：

- 调用 `Thread.start()` 之前的写入，对新线程可见。
- 线程执行完后，其他线程从 `Thread.join()` 返回时，可以看到它执行期间的结果。
- `java.util.concurrent` 里的原子类、锁、队列、Future、CountDownLatch 等，本质上也都是在 JMM 允许的范围内，通过
  volatile、CAS、park/unpark 和屏障组合来建立可见性。

也就是说，可见性不是一个孤立功能，而是整个并发库的共同基础设施。

## 九、HotSpot 从源码语义到机器行为的大致路径

如果把一段带同步语义的 Java 代码从上到下展开，整体链路大致是这样的：

1. `javac` 把源码翻译成 class 文件。
2. volatile 字段被标成 `ACC_VOLATILE`，synchronized 代码块被编译成监视器相关字节码。
3. JVM 解释执行或 JIT 编译这些字节码时，识别哪些操作带有特殊内存语义。
4. C1/C2 编译器在中间表示中插入对应的内存屏障节点，或者调用具有相同语义的运行时原语。
5. 平台相关后端根据目标 CPU 的内存模型，把这些语义翻译成合适的机器指令序列。
6. CPU 通过缓存一致性协议、写缓冲刷新、失效通知、屏障指令等机制，让其他核心在正确时机观察到更新。

这条链路里每一层做的事情不同：

- JMM 负责定义规则。
- JVM 编译器负责防止非法优化。
- 运行时负责落同步原语。
- CPU 负责真正传播和约束内存访问顺序。

只有这些层一起工作，Java 程序员写下的同步语义才不是“建议”，而是可执行的保证。

## 十、为什么说可见性总是伴随有序性

可见性和有序性经常一起出现，不是巧合。

假设线程 A 执行：

```java
data = 42;
ready = true;
```

线程 B 执行：

```java
if (ready) {
    System.out.println(data);
}
```

如果 `ready` 不是 volatile，也没有锁，那么问题不只是 B 可能看不到 `ready = true`。更麻烦的是，A 的两次写入还可能在语义上被重排，导致 B 先看到 `ready = true`，却还看不到 `data = 42`。

这就是为什么 volatile 写不只是“把 ready 刷出去”，还必须附带顺序约束：

- 在写 `ready = true` 之前，前面对 `data` 的写不能被排到后面。

同理，B 读到 `ready == true` 之后，也必须保证后续读 `data` 不能被提到前面去。

所以，JVM 实现可见性时，一定顺带在处理有序性，否则“看见了同步标志但没看见真实数据”这种错误仍然会存在。

## 十一、缓存一致性协议为什么还不够

有人会问：现代 CPU 不是已经有缓存一致性协议了吗，为什么还要 JMM 和内存屏障？

原因是缓存一致性只解决了问题的一部分。

### 1. 一致性不等于同步语义

缓存一致性协议能保证同一内存位置最终不会长期分裂成多个互相矛盾的值，但它不自动提供 Java 所要求的 happens-before 语义。

### 2. 一致性不阻止编译器重排

即便硬件最终能传播最新值，JIT 编译器仍然可能在没有同步约束时做激进优化。JMM 必须先约束编译器，再约束硬件。

### 3. 一致性不天然保证跨变量顺序

很多并发正确性依赖的是“先写数据，再发布标志”这种跨变量关系。缓存一致性协议并不会自动替你建立这种发布顺序。

所以，缓存一致性是基础设施，但不是 Java 可见性语义的完整答案。

## 十二、可见性不等于原子性

这是最容易被混淆的一点。

```java
volatile int count = 0;

count++;
```

即使 `count` 是 volatile，这段代码仍然不是线程安全的，因为 `count++` 会拆成：

1. 读出旧值。
2. 旧值加一。
3. 写回新值。

volatile 只能保证每一步读写的可见性和部分顺序约束，但不能把三步合成一个不可分割的原子操作。

如果多个线程同时执行，仍然可能发生丢失更新。

这时需要的是：

- synchronized 或显式锁。
- AtomicInteger 这类基于 CAS 的原子类。

因此，谈 JVM 可见性时，必须把它和原子性分开，否则很容易误用 volatile。

## 十三、JVM 为了可见性付出了什么成本

可见性保证不是免费的。

它的成本主要来自下面几方面：

- 编译器优化空间减少，某些读写不能缓存、不能重排。
- 内存屏障会影响指令流水和乱序执行收益。
- 锁获取与释放会带来元数据操作、竞争、自旋、阻塞与唤醒开销。
- 高频 volatile 写可能导致缓存行失效传播更频繁，增加核间同步成本。

所以工程上的正确思路从来不是“到处都加 volatile 或 synchronized”，而是：

- 先明确线程之间需要建立哪一条 happens-before。
- 再选成本最低、语义刚好足够的同步手段。

## 十四、实践中如何判断应该用什么机制

可以按下面的思路判断：

### 1. 只是一个状态开关或发布标志

例如停止位、初始化完成标记、配置版本号，这类场景通常优先考虑 volatile。

### 2. 需要保护多个变量的一致性

例如“余额减少同时流水增加”，这类跨变量不变式必须用锁或原子复合结构，volatile 不够。

### 3. 对象构造后只读

尽量使用 final 字段和不可变对象，并通过静态初始化、volatile 引用、锁保护或并发容器等方式发布对象引用，减少后续同步成本。

### 4. 已经通过并发容器或同步工具发布结果

不要额外再拼凑一套手写可见性协议，优先信任标准库已经实现好的 happens-before。

## 十五、总结

JVM 实现可见性，靠的不是单一技巧，而是一整套分层协作机制。

- 在规范层，JMM 用 happens-before 定义“什么结果必须可见”。
- 在语言与字节码层，volatile、synchronized、final、start/join 等同步动作表达这些语义。
- 在 JVM 实现层，解释器与 JIT 通过禁止非法优化、插入内存屏障、执行锁语义来兑现约束。
- 在硬件层，CPU 通过缓存一致性协议和屏障指令让修改按正确时机传播到其他核心。

如果把一句话说透，那么 JVM 的可见性原理就是：

- 用 JMM 规定发布与获取关系。
- 用 volatile、锁和其他同步原语建立 happens-before。
- 用编译器屏障和硬件屏障把这个语义真正压到机器执行层。

理解这条链路之后，再去看 volatile、synchronized、CAS、并发容器，很多看似零散的并发知识就会连成一张完整的图。
