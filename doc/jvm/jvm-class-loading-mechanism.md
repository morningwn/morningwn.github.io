# JVM 类加载机制：从加载流程到双亲委派

类加载机制是理解 JVM 运行时行为的核心基础之一。很多 Java 问题表面上看像是语法、框架或容器问题，往下追，最后都会落到类到底是怎么被加载、什么时候初始化、为什么同名类不能互转、为什么会出现 `ClassNotFoundException` 或 `NoClassDefFoundError`。

如果只先记一条主线，可以把 JVM 类加载理解成下面这句话：

- JVM 会把磁盘、网络或内存里的类字节码读进来。
- 再把它校验、准备、解析成运行时可以使用的类元数据。
- 最后在真正需要执行时完成初始化，让这个类变成“可被程序主动使用的类”。

这篇文章会按四条主线展开：

- 类从字节码变成运行时类，到底经历了哪些阶段。
- 双亲委派模型为什么存在，它到底解决了什么问题。
- 什么操作会触发类初始化，什么操作不会。
- 自定义类加载器、类卸载和常见误区应该怎么理解。

## 一、先看全貌：类的生命周期是什么

从 JVM 规范角度看，一个类从第一次被发现到最终被卸载，通常会经历下面这些阶段：

- 加载（Loading）
- 链接（Linking）
- 初始化（Initialization）
- 使用（Using）
- 卸载（Unloading）

其中，链接又可以继续拆成三步：

- 验证（Verification）
- 准备（Preparation）
- 解析（Resolution）

很多文章会把它画成“加载、验证、准备、解析、初始化”五步，这么记没有问题，但更准确的理解是：

- 验证、准备、解析都属于链接阶段。
- 使用不是一个瞬时动作，而是类进入正常运行后的整个阶段。
- 卸载也不是一定发生，很多类会一直活到 JVM 进程结束。

如果把整个流程压缩成一句话，就是：

- 先把类读进来。
- 再把它处理成 JVM 能信任、能引用、能执行的内部结构。
- 到真正需要执行静态逻辑时，再完成初始化。

## 二、加载阶段：JVM 到底做了什么

加载阶段最直观，但也最容易被说得过于简单。它不是“把 `.class` 文件读一下”就结束了，而是至少包含下面三件事：

- 通过一个类的全限定名，找到定义这个类的二进制字节流。
- 把这份字节流转换成方法区中的运行时数据结构。
- 在堆上生成一个对应的 `Class` 对象，作为程序访问该类元数据的入口。

这里有几个关键点必须先说清。

### 1. 类的来源不一定是本地文件

虽然我们平时最常见的是从 `.class` 文件或 jar 包里加载，但 JVM 并不要求类一定来自磁盘文件。理论上，类字节码可以来自很多地方：

- 本地 class 文件
- jar 包
- 网络传输
- 动态生成的字节码
- 数据库、加密容器或自定义存储

这也是为什么类加载器是一个非常重要的抽象。JVM 不关心你具体从哪里拿到字节码，它只要求你最终能提供一份合法的类定义数据。

### 2. 加载完成，不等于类已经初始化

这是类加载机制里最常见的误区之一。

加载阶段完成以后，说明 JVM 已经“认识”这个类了，但这不代表：

- 静态变量已经按代码里的值完成赋值。
- 静态代码块已经执行。
- 这个类已经进入可主动使用状态。

很多场景里，类可以先被加载、验证、准备，甚至解析一部分符号引用，但一直到真正触发初始化时，静态逻辑才会开始执行。

### 3. 类的唯一性不只看类名

在 JVM 里，一个类是否“是同一个类”，不是只看全限定名，还要看它由谁加载。

更准确地说，类的身份由两部分共同决定：

- 类的全限定名
- 加载它的类加载器

这意味着：

- 两个全限定名相同的类，如果由不同类加载器加载，在 JVM 看来就是两个不同的类。
- 它们不能直接互相强转。
- 这也是模块隔离、插件隔离和容器隔离的基础。

## 三、链接阶段：为什么 JVM 不能加载完就直接运行

类被读进来以后，JVM 还不能立刻放心执行。因为它必须先确认这份字节码是安全的、结构是正确的、静态字段有了初始空间、类之间的引用也能被定位。

这就是链接阶段要解决的问题。

### 1. 验证：先确认这份类定义靠得住

验证的目标很直接：保证字节码不会破坏 JVM 本身的安全性和正确性。

常见的验证内容可以粗略理解成四类：

- 文件格式验证：比如魔数、版本号、常量池结构是否正确。
- 元数据验证：比如当前类是否错误继承了 `final` 类，方法签名是否合理。
- 字节码验证：比如操作数栈、局部变量表的使用是否匹配，控制流是否可达。
- 符号引用验证：比如被引用的方法、字段、类是否满足访问权限要求。

验证阶段的意义是：

- JVM 不是“看见字节码就执行”。
- 它要先保证这份字节码至少是结构合法、语义可解释的。

很多基于字节码增强的框架之所以能工作，一个前提就是它们生成出来的字节码仍然必须通过 JVM 验证。

### 2. 准备：给类变量分配内存，并设默认值

准备阶段做的事情很容易记：

- 为类变量，也就是 `static` 字段分配内存。
- 给这些字段设置零值默认值。

这里的“默认值”不是你在代码里写的初始化值，而是 JVM 层面的类型默认值，例如：

- `int` 是 `0`
- `long` 是 `0L`
- `boolean` 是 `false`
- 引用类型是 `null`

例如下面这段代码：

```java
public class Sample {
    public static int value = 10;
}
```

在准备阶段结束后，`value` 的值是 `0`，不是 `10`。`10` 这个赋值动作发生在后面的初始化阶段。

不过这里有一个常见例外：

- 如果字段是编译期常量，也就是带有 `ConstantValue` 属性的 `static final` 常量，那么它在准备阶段就可能直接被赋成目标值。

例如：

```java
public class ConstSample {
    public static final int PORT = 8080;
}
```

这类字段和普通 `static` 字段的行为不完全一样，后面讲“初始化触发条件”时会再次说到。

### 3. 解析：把符号引用变成直接引用

Class 文件里的很多引用，在编译完成时并不知道目标在运行时内存中的实际位置，因此会先以“符号”的形式存在常量池里。

比如：

- 某个类名
- 某个方法签名
- 某个字段描述符

解析阶段要做的，就是把这些符号引用替换成 JVM 运行时可以直接定位的引用关系。

可以把它理解成：

- 编译时知道“我要调用谁”。
- 解析后知道“它在运行时到底对应哪个类、哪个方法、哪个字段”。

这里还有一个容易混淆的点：

- 从逻辑上看，解析属于链接阶段。
- 但从实现上看，解析并不一定非要在初始化之前一次性全部做完。

很多 JVM 实现会按需解析，也就是第一次真正用到某个符号引用时再把它解析出来。这种延迟解析并不违背整体模型。

## 四、初始化阶段：什么时候类才算真正“活了”

初始化是类加载机制里最关键的一道分界线。到了这个阶段，JVM 才会去执行类构造器 `<clinit>()` 方法。

这里的 `<clinit>()` 不是你显式写出来的方法，而是编译器收集下面两类语句后自动生成的：

- 静态变量显式赋值语句
- 静态代码块

例如：

```java
public class Demo {
    static int count = 10;

    static {
        System.out.println("Demo init");
        count = 20;
    }
}
```

这个类初始化时，JVM 执行的本质就是编译器合成出来的 `<clinit>()`。

### 1. 哪些情况会触发类初始化

按照主动使用的思路去记，最容易理解。常见会触发类初始化的情况包括：

- `new` 一个类的实例。
- 读取或设置某个类的非编译期常量静态字段。
- 调用某个类的静态方法。
- 通过反射主动使用这个类，比如 `Class.forName()` 的常见形式。
- JVM 启动时加载主类。
- 初始化子类之前，如果父类还没初始化，会先初始化父类。
- 某些 `MethodHandle`、动态语言支持场景，也可能触发初始化。

可以记成四个字：

- 真正要用。

只要 JVM 认为你已经不是“看看这个类”，而是开始主动依赖它的静态行为或实例行为，就会推进到初始化阶段。

### 2. 哪些情况通常不会触发类初始化

同样重要的是，很多操作虽然和类有关，但并不会触发初始化，例如：

- 通过子类引用父类中定义的静态字段，只会初始化真正定义该字段的类。
- 访问编译期常量，不会触发定义该常量的类初始化。
- 获取类字面量，比如 `User.class`。
- 创建某个类的数组，比如 `new User[10]`。
- 仅仅调用 `ClassLoader.loadClass()`，通常只会完成加载，不会初始化。

最常见的例子是编译期常量：

```java
public class Config {
    public static final int TIMEOUT = 30;

    static {
        System.out.println("Config init");
    }
}
```

如果别的类只是访问 `Config.TIMEOUT`，很可能不会打印 `Config init`。原因是：

- 编译期常量在编译阶段就可能被直接内联到使用它的类中。
- 运行时甚至不需要真的初始化 `Config` 就能拿到值。

### 3. `Class.forName()` 和 `loadClass()` 到底差在哪

这是面试和实际开发里都非常高频的一个点。

可以先记结论：

- `ClassLoader.loadClass()` 的核心目标是“把类加载进来”。
- `Class.forName()` 的常见用法通常会顺带触发初始化。

因此两者的差异，本质上是：

- 一个更偏“装载”。
- 一个更偏“装载并准备立即使用”。

当然，`Class.forName()` 也有可控制是否初始化的重载版本，所以真正准确的说法应该是：

- `Class.forName()` 默认更容易触发初始化。
- `loadClass()` 默认只到加载或链接相关阶段，不主动初始化。

## 五、双亲委派模型：为什么类加载器要一层层往上问

双亲委派是类加载机制里最有辨识度的一部分，但很多人把它背成了流程图，却没理解它的设计目标。

先说核心结论：

- 双亲委派的重点不是“层级好看”。
- 而是尽量保证核心类的唯一性与安全性，避免同名类被随意替换。

### 1. Java 中常见的类加载器层级

站在日常开发视角，通常可以先认识三层：

- 启动类加载器（Bootstrap ClassLoader）
- 平台类加载器（Platform ClassLoader）
- 应用类加载器（Application ClassLoader）

它们大致负责：

- 启动类加载器加载最核心的 Java 基础类库。
- 平台类加载器加载平台相关模块。
- 应用类加载器加载应用自己的 classpath 内容。

要注意两点：

- 启动类加载器通常不是一个普通 Java 对象，在很多 API 里会表现为 `null`。
- “双亲”更多是委派关系，不一定等于严格的 Java 继承关系。

### 2. 双亲委派的基本流程是什么

默认实现里，一个类加载器在收到加载请求后，通常不是立刻自己加载，而是按下面的顺序处理：

- 先检查这个类是否已经加载过。
- 如果没有，就把请求委派给父加载器。
- 父加载器再继续向上委派。
- 一直到顶层加载器无法完成时，子加载器才回退并尝试自己去加载。

这条链路可以概括为：

- 先让上层试。
- 上层不行，下层再自己来。

### 3. 双亲委派解决了什么问题

它至少解决了两个非常重要的问题。

第一，保证核心类的稳定性。

例如 `java.lang.String` 这种类，应该始终由受信任的核心加载器加载。如果应用自己随便放一个同名类就能替换它，整个 Java 运行时都会失去安全边界。

第二，避免同一个类被重复加载。

如果没有委派机制，多个加载器都可能各自去加载同一个类定义，最后就会制造出很多“名字一样但身份不同”的类，类型系统会变得很混乱。

### 4. 双亲委派不是绝对不可打破

这是另一个很常见的误区。

更准确的说法是：

- `loadClass()` 的默认实现遵循双亲委派。
- 但类加载器机制本身允许你通过重写逻辑来改变委派次序。

很多容器、插件系统和热部署系统都做过这件事。原因不是它们想“对抗 JVM”，而是它们需要类隔离能力。

例如一个插件框架往往希望：

- 不同插件可以带自己的同名依赖。
- 插件优先使用自己的实现，而不是宿主应用里的实现。

这时就可能采用“子优先”或更复杂的委派策略。

## 六、自定义类加载器：它到底适合做什么

理解自定义类加载器时，不要把重点放在“如何覆写一个方法”，而要放在“为什么需要另一套类命名空间”。

常见使用场景包括：

- 插件化系统
- 模块隔离
- 热部署或热替换
- 字节码加密与解密
- 按需从远程位置加载代码

在实现上，通常会通过继承 `ClassLoader`，然后在合适的位置覆写 `findClass()`。原因是：

- 默认的 `loadClass()` 已经把缓存检查和双亲委派流程组织好了。
- 你真正要定制的，往往只是“父加载器加载失败后，我自己如何找到并定义这个类”。

如果一上来就直接粗暴重写 `loadClass()`，很容易把：

- 重复加载检查
- 并发安全控制
- 既有委派语义

一起破坏掉。

所以在大多数场景里，更稳妥的策略是：

- 先理解默认委派模型。
- 只在确实需要改变策略时，再谨慎重写 `loadClass()`。

## 七、SPI 和线程上下文类加载器：为什么有时要“反向委派”

如果双亲委派总是从上往下，那就会遇到一个问题：

- 上层类加载器加载的基础框架代码，怎么才能发现并使用下层应用提供的实现类？

最典型的例子就是 SPI。比如 JDBC、日志门面或其他服务发现机制里：

- 接口往往由上层加载器可见。
- 具体实现却可能只存在于应用自己的 classpath 中。

这时如果严格只按父加载器向上找，实现类就根本看不见。

Java 为了解决这个问题，引入了线程上下文类加载器（Thread Context ClassLoader，TCCL）这套思路。它允许框架代码在需要时不再只依赖“加载我自己的那个类加载器”，而是改为使用当前线程绑定的上下文类加载器去查找实现。

可以把它理解成：

- 双亲委派解决的是基础安全与唯一性问题。
- 上下文类加载器解决的是框架扩展与服务发现问题。

## 八、类卸载：为什么有些类永远卸不掉

类加载讲得多，类卸载讲得少，但在线上问题里它经常非常关键，尤其是容器、插件、脚本引擎和热部署场景。

一个类要被卸载，通常至少要满足下面这些条件：

- 该类的所有实例都已经被回收。
- 加载这个类的类加载器本身可以被回收。
- 对应的 `Class` 对象没有再被强引用。

这意味着，真正决定类能不能卸载的，往往不是这个类本身，而是它背后的类加载器能不能一起被回收。

很多 Metaspace 增长过快的问题，根因其实不是“类太多”，而是：

- 某个自定义类加载器被静态变量、线程、本地缓存、线程池任务或 `ThreadLocal` 间接持有。
- 导致整批由它加载的类都无法卸载。

所以排查类加载泄漏时，主线通常不是只盯着类名，而是去找：

- 是谁把那个类加载器链路留住了。

## 九、几组最容易混淆的概念

把下面几组区别彻底弄清，类加载相关问题会清楚很多。

### 1. `ClassNotFoundException` 和 `NoClassDefFoundError`

两者都和“类没法正常使用”有关，但语义不同：

- `ClassNotFoundException` 通常发生在显式按名称动态加载类时，加载器没找到目标类。
- `NoClassDefFoundError` 往往表示这个类在编译时存在，运行时本该能被定义，但实际加载或初始化阶段出了问题，导致 JVM 最终没法得到这个类定义。

前者更偏“找不到”。

后者更偏“本来应该有，但运行时没能成功拿到”。

### 2. 加载和初始化不是一回事

可以这样记：

- 加载解决“JVM 认不认识这个类”。
- 初始化解决“这个类的静态逻辑有没有真正执行过”。

很多面试题、线上日志和框架行为差异，核心都卡在这个区别上。

### 3. 类相同不只看包名和类名

更准确的判断方式是：

- 同一个全限定名
- 由同一个类加载器加载

这两个条件都满足，JVM 才认为它们是同一个运行时类。

### 4. 双亲委派是默认模型，不是唯一模型

这句话很重要，因为很多资料会把双亲委派描述成一条不可违反的“铁律”。

更准确的说法是：

- Java 平台依赖双亲委派维持基础稳定性。
- 但具体业务系统可以基于类加载器机制做有边界的定制。

## 十、把整条主线串起来

如果把 JVM 类加载机制重新压缩成一条连续过程，可以这样理解：

1. 程序第一次需要某个类时，类加载器去定位它的字节码。
2. JVM 把字节码转成内部类结构，并创建对应的 `Class` 对象。
3. 链接阶段完成验证、类变量内存准备和符号引用解析。
4. 真正主动使用这个类时，JVM 执行 `<clinit>()` 完成初始化。
5. 运行过程中，类的身份始终由“全限定名 + 类加载器”共同决定。
6. 默认情况下，类加载遵循双亲委派，以保证核心类的唯一性与安全性。
7. 当类及其类加载器都不再可达时，这批类才有机会被卸载。

所以，类加载机制的本质不是一张流程图，而是一整套运行时边界设计：

- 它决定类从哪里来。
- 它决定类什么时候真正可用。
- 它决定同名类是不是同一个类型。
- 它也决定模块隔离、插件化、SPI 和热部署为什么能成立。

如果你后面要继续深入 JVM，最值得顺着往下看的两个方向通常是：

- 字节码与方法调用分派。
- Metaspace、类卸载与类加载器泄漏排查。

理解了类加载机制，JVM 运行时很多“看起来很绕”的行为，基本都会开始变得可解释。
