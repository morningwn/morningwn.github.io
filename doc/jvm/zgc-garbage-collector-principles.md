# ZGC 垃圾回收器原理与实现方式

ZGC 的设计目标很明确：

- 把 GC 停顿时间压到很低，而且尽量不随着堆大小线性增长。
- 允许堆很大时，应用线程仍然能保持稳定响应。
- 在低停顿前提下，尽量维持可接受的吞吐和内存利用率。

如果只先记一条主线，可以把 ZGC 理解成下面这句话：

- 大部分重活都并发做。
- 少量必须 Stop-The-World 的阶段只做切换和同步。
- 通过指针元数据和屏障机制，让对象在“正在搬家”的过程中仍然能被应用线程安全访问。

所以，ZGC 的核心并不是“又一种标记整理算法”这么简单，而是下面几种机制的组合：

- 并发标记。
- 并发转移。
- 染色指针。
- 读屏障。
- 基于页和转发表的地址重映射。

和传统 GC 相比，ZGC 最重要的变化不是“回收策略更聪明”，而是“对象可以在几乎不停应用的情况下被搬迁”。这件事一旦成立，低停顿这件事才真正有基础。

## 一、先看 ZGC 要解决的根问题

传统 GC 在堆较大时经常会遇到一个矛盾：

- 想要回收和整理更多内存，就需要扫描和移动更多对象。
- 想要保证对象引用在移动后仍然正确，就往往要暂停用户线程做修正。

这就导致一个直接结果：

- 堆越大。
- 活对象越多。
- 停顿就越难控制。

ZGC 的思路不是简单优化这个暂停过程，而是换一个问题定义：

- 能不能让对象移动这件事和应用线程并发进行？
- 能不能让引用修正不再依赖一次大停顿？
- 能不能让每次停顿只负责建立全局一致的阶段边界，而不是承担实际搬迁工作？

ZGC 的答案是可以，但前提是 JVM 必须拥有一套新的引用访问模型。

## 二、先抓住 5 个最关键的概念

如果一开始就陷入阶段名、屏障名和页表细节，ZGC 会显得很抽象。先把下面 5 个概念抓稳，后面的流程就容易理解了。

### 1. 染色指针：引用本身带状态

在很多传统理解里，指针就是对象地址本身。但 ZGC 会在 64 位引用的高位中放入额外状态位，让“引用”不仅表示“指向谁”，还携带“当前处于什么视图”这一类信息。

这就是所谓的染色指针。它的意义不是为了节省一个辅助表，而是为了让 JVM 在访问一个对象时，能立刻知道：

- 这个引用对应的标记视图是什么。
- 这个对象是否已经处于重定位相关阶段。
- 当前访问是否需要经过屏障修正。

可以把它理解成：

- 普通 GC 更像是“地址外加一堆旁路数据结构”。
- ZGC 则尝试让“引用自己就带一点运行时语义”。

### 2. 读屏障：每次读取引用时顺手校正

很多收集器更依赖写屏障，因为它们主要在“引用关系被修改”时记录额外信息。ZGC 最著名的地方在于，它 heavily 依赖读屏障。

简单理解就是：

- 当线程准备通过一个引用去访问对象时，JVM 会先过一道轻量检查。
- 如果这个引用仍然合法并且已经是当前期望的视图，就直接访问。
- 如果引用落在旧视图、旧地址或者需要重映射，屏障就负责把它修正到新位置。

这意味着对象即使已经被搬到新地址，只要旧引用还在应用线程栈里、寄存器里或某个字段里，程序也不一定会出错，因为真正解引用之前会被读屏障拦一下。

### 3. 页面与分段映射：ZGC 管理的是一组页，而不是一整块连续老年代

ZGC 把堆划分成多个 ZPage。它们是分配、标记、转移和回收时的重要管理单位。

你可以把它理解成：

- G1 的核心分治单位是 Region。
- ZGC 的核心管理单位更接近 Page。

ZPage 可以有不同大小级别，用来降低内部碎片，兼顾普通对象与较大对象的分配需求。这样做的目的不是为了复杂化，而是为了让并发转移和重定位过程更容易被分批处理。

### 4. 转发表与重映射：旧地址不必立刻失效

如果对象从旧地址搬到新地址，传统做法往往要想办法把所有引用一次性改掉。ZGC 不这么做。

它允许一种过渡状态存在：

- 对象已经搬家了。
- 一部分引用还是旧的。
- 但旧引用可以通过元数据找到新位置。

这个过程依赖重定位相关的数据结构。不同实现细节可以概括成一句话：

- JVM 为“旧地址到新地址”的映射留出一条可查询路径，读屏障负责在访问时完成跳转和修正。

### 5. 并发转移：对象整理不是靠一次长停顿完成

ZGC 不是只并发标记，它真正关键的是并发转移。也就是说：

- 找出还活着的对象之后。
- 不需要把所有线程长时间停下再做压缩。
- 可以一边运行应用，一边逐步把活对象复制到新页。

这一点是它和很多“低停顿但整理能力一般”的方案的重要区别。

## 三、为什么 ZGC 能把停顿时间压得很低

先直接说结论。

ZGC 停顿时间低，不是因为它完全没有 Stop-The-World，而是因为它把 Stop-The-World 的职责压缩到了非常窄的范围：

- 建立阶段边界。
- 扫描根对象。
- 切换全局状态。
- 确保并发阶段开始和结束时的一致性。

而真正耗时的大头，例如：

- 遍历对象图。
- 统计存活情况。
- 复制对象。
- 释放旧页。

这些工作尽量都放到了并发阶段。

这件事说起来简单，难点在于：

- 并发期间引用关系会变化。
- 对象可能在搬迁。
- 应用线程可能还拿着旧引用继续访问。

ZGC 之所以能成立，靠的不是单一算法，而是“屏障 + 染色指针 + 重映射 + 分阶段协议”同时配合。

## 四、ZGC 的整体回收流程

从高层来看，一轮 ZGC 周期大致可以分成下面几个阶段。

### 1. Pause Mark Start

这是一个很短的停顿阶段。它主要做几件事：

- 切到新的标记周期。
- 扫描根对象集合的起点。
- 建立这轮并发标记所需的全局状态。

这里的根对象通常包括：

- Java 线程栈上的引用。
- 寄存器中的引用。
- JNI 全局引用。
- 类元数据相关根。
- 运行时常量池、静态字段等。

这个阶段必须短，因为它仍然是停顿点。但它不做大规模堆遍历，只做“让并发标记能安全开始”的必要工作。

### 2. Concurrent Mark

进入并发标记后，GC 线程和应用线程一起运行。

这时 ZGC 会从根开始遍历对象图，找出活对象。标记期间最关键的问题是：

- 程序还在继续修改对象图。
- 某些引用可能刚刚变化。
- 某些对象可能刚刚变得不可达，或者刚刚被重新连回可达图。

ZGC 会结合屏障和阶段协议来保证“这一轮标记下哪些对象算活着”这个定义是自洽的。它并不是要求应用线程完全静止，而是通过一致的快照语义，让并发标记得到一个合法结果。

### 3. Pause Mark End

并发标记结束后，会有一个短暂停顿来收敛结果。这个阶段通常会做：

- 处理并发阶段末尾必须同步的一小部分工作。
- 最终确认活对象统计。
- 选出要进行重定位的页集合。

这个被选中的集合，可以理解成本轮“最值得整理和回收”的那批页。它和 G1 的 Collection Set 在目的上类似，都是为了把工作限定在一部分空间里，但
ZGC 关注的是页级重定位。

### 4. Concurrent Relocate

这是 ZGC 最有代表性的阶段。

GC 线程会把重定位集中的活对象复制到新的页中。这里最关键的不是“复制对象”本身，而是复制时应用线程仍然可能访问这些对象。

要让这件事成立，需要保证：

- 旧引用仍然能找到对象。
- 即使对象已经搬走，访问也能被修正到新地址。
- 同一个对象不会被重复错误搬迁。
- 访问和搬迁之间的竞争能被正确处理。

这正是读屏障和重定位元数据发挥作用的地方。

### 5. 并发重映射与旧页回收

当越来越多的引用被读屏障修正后，系统对旧地址的依赖会逐步降低。等到确认某批旧页不再需要作为重定位来源后，它们就可以被回收再利用。

所以，从宏观上看，ZGC 的对象移动不是“一口气全局纠偏”，而是：

- 先搬对象。
- 再让访问路径逐步转向新地址。
- 最后释放旧空间。

## 五、染色指针到底解决了什么问题

这是理解 ZGC 的关键。

如果没有染色指针，JVM 想知道一个引用当前属于哪个标记视图、是否需要重映射，通常只能：

- 查额外的 side table。
- 或者依赖更重的对象头状态。

这会带来几个问题：

- 访问路径更长。
- 元数据查询更频繁。
- 屏障判断成本更高。

染色指针的价值在于，它把一部分运行时判定信息和引用本身绑在一起，使得 JVM 在读取引用时更容易快速决定：

- 这是不是当前有效的 marked0 或 marked1 视图。
- 这个引用是否落在 remapped 语义下。
- 是否应该触发屏障慢路径。

很多文章会把它简化成“高位存几个标志位”，这句话不算错，但不够抓核心。真正重要的是：

- ZGC 把对象访问协议的一部分编码进了引用表示本身。

这样读屏障才能足够轻，否则每次对象访问都可能贵得不可接受。

## 六、读屏障的工作过程

ZGC 的读屏障不是“每次都做很重的事”，而是遵循快路径和慢路径分离。

### 1. 快路径

大多数情况下，引用已经是当前可接受状态，屏障只需要做非常轻的判断，然后直接放行。

这部分必须足够便宜，否则应用线程吞吐会被明显拖慢。

### 2. 慢路径

只有当引用落在特殊状态时，才进入慢路径，例如：

- 引用仍然指向尚未修正的旧地址视图。
- 当前对象所在页已经进入重定位相关阶段。
- 需要通过转发表查到新地址。

慢路径会做的事情通常包括：

- 解析引用上的状态位。
- 查询页或对象的重定位信息。
- 找到对象的新位置。
- 返回修正后的可用引用。
- 在合适时机把旧引用更新成新引用，减少后续重复修正。

从效果上看，读屏障就像一个“访问时修路”的过程：

- 第一次走这条路的人可能稍微慢一点。
- 路修好之后，后面再访问就能走快路径。

### 3. 为什么 ZGC 更偏向读屏障而不是重写所有引用

因为在低停顿目标下，最难的是“什么时候统一修正所有旧引用”。

如果坚持一次性全量修正，就会逼着 JVM 做更重的停顿。而读屏障提供了另一种策略：

- 不要求所有引用立刻一致。
- 允许局部旧引用短暂存在。
- 只要真正使用时能被安全修正即可。

这是 ZGC 实现并发搬迁的根本基础。

## 七、并发标记是如何保证正确性的

只要是并发标记，就一定会面对对象图变化的问题。ZGC 要解决的是：

- 标记线程看到的是一个变化中的堆。
- 应用线程还在不断创建、修改、丢弃引用。

要让最终结果正确，GC 需要先定义“正确”是什么意思。一般来说，核心要求是：

- 不该死的对象不能被错回收。
- 标记结果必须能支持后续安全重定位。

ZGC 通过并发标记协议、屏障和短暂停顿收敛阶段来保证这一点。你可以把它理解成：

- 并发阶段负责尽量把图遍历完整。
- 停顿边界负责收口那些必须同步确认的变化。

所以，ZGC 不是让并发阶段单独承担一切正确性，而是用“并发推进 + 停顿收敛”的方式把问题拆开。

## 八、并发转移为什么比并发标记更难

并发标记解决的是“哪些对象活着”，并发转移解决的是“活对象怎么搬，还不能把访问搞乱”。后者难度更高，原因主要有三点。

### 1. 对象地址真的会变化

标记阶段对象还在原地，只是要判断活性。转移阶段对象会被复制到新地址，因此任何旧引用理论上都可能失效。

### 2. 应用线程可能同时访问旧对象和新对象语义

在搬迁窗口期内，线程可能：

- 刚从某字段里读到旧引用。
- 下一步就要解引用访问对象内容。

如果没有屏障和映射支持，这一步就可能读到不再可靠的旧位置。

### 3. 多线程下要避免重复搬迁和状态竞争

多个 GC 线程或应用线程可能几乎同时触发同一个对象的转移相关逻辑。ZGC 需要保证：

- 对象最终只有一个合法的新位置。
- 引用修正过程不会相互覆盖出错。
- 旧页的回收一定发生在安全时机。

因此，并发转移本质上是“复制算法 + 并发协议 + 屏障修正”的联合实现，不只是单纯的内存拷贝。

## 九、重定位集是什么，为什么不是全堆一起搬

ZGC 不会每次都把整个堆全部重定位，这样没有必要，也会造成额外成本。它会根据存活分布、空间回收收益等信息，挑选一部分页组成重定位集。

这样做有几个明显好处：

- 把一次回收拆成可控工作量。
- 优先整理回收收益更高的区域。
- 降低一次并发转移对带宽和 CPU 的冲击。

从这个角度看，ZGC 和 G1 虽然机制很不同，但都体现了同一个现代 GC 思路：

- 不追求每次处理整个堆。
- 而是分批处理最有价值的一部分空间。

区别在于：

- G1 更强调 Region 级收益预测和停顿预算。
- ZGC 更强调并发可搬迁与极低停顿。

## 十、ZGC 的内存布局和大对象处理思路

ZGC 的堆并不是简单一整块平铺空间。为了兼顾分配效率和碎片控制，它会用不同大小级别的页来容纳对象。

这背后有两个目的。

### 1. 降低内部碎片

如果所有对象都塞进同一种粒度的页，较小对象和较大对象会互相影响，空洞也更难控制。分级页可以让不同体量对象更适合地放入对应空间。

### 2. 让大对象不至于把普通分配路径拖垮

大对象通常会影响：

- 分配延迟。
- 复制成本。
- 碎片情况。

ZGC 会针对不同大小对象使用不同布局策略，避免所有对象都走同一条最普通的路径。这和 G1 的 Humongous Region 思路方向相近，但实现抽象不同。

## 十一、吞吐、延迟和内存开销之间的真实权衡

ZGC 的优势非常明确，但它不是没有代价。

### 1. 延迟通常很好

这是 ZGC 最核心的价值。因为大多数重活是并发完成的，所以堆很大时，它仍然能把停顿控制在一个较小范围内。

### 2. 吞吐未必总是最优

原因并不复杂：

- 屏障本身有成本。
- 并发标记和并发转移会持续占用 CPU。
- 引用访问路径比无屏障方案更复杂。

所以，如果一个应用最关心的是极致吞吐，而不太关心尾延迟，ZGC 未必总是第一选择。

### 3. 对额外内存更敏感

因为并发转移期间，旧对象空间和新对象空间会在一段时间里同时存在，所以 ZGC 需要更从容的内存余量。如果堆压得太满，并发回收可能更容易追不上分配速度。

换句话说，ZGC 在工程上经常要求：

- 用更多并发资源。
- 预留更合理的堆空间。
- 换取更平滑的停顿表现。

## 十二、ZGC 和 G1 的核心区别

这两个收集器经常被放在一起比较，但关注点其实并不一样。

### 1. 停顿控制方式不同

- G1 主要通过分 Region、预测回收成本、控制 CSet 大小来尽量满足停顿目标。
- ZGC 主要通过把标记和搬迁并发化，把停顿阶段压缩为边界同步。

### 2. 屏障重心不同

- G1 很依赖写屏障来维护 Remembered Set 和并发标记语义。
- ZGC 更突出的设计是读屏障，因为它要解决“对象正在搬迁时还能被安全访问”的问题。

### 3. 整理方式不同

- G1 会在停顿阶段内对选中的 Region 做 evacuation。
- ZGC 则把重定位工作尽量放到并发阶段。

### 4. 适用场景不同

- G1 适合大多数通用服务端应用，平衡性很好。
- ZGC 更适合对尾延迟敏感、堆较大、能接受一定额外资源开销的场景。

## 十三、分代 ZGC 是对什么问题的进一步优化

早期 ZGC 的一个特点是没有传统意义上的强分代路径，它已经能实现很低停顿，但对于“绝大多数对象朝生夕死”这类典型代际特征，没有把收益吃得特别充分。

分代 ZGC 的目标，就是在保留 ZGC 低停顿优势的同时，引入更贴近对象年龄分布的回收策略，让短命对象优先被更便宜地处理。

你可以把它理解成：

- 原始 ZGC 重点解决的是“如何低停顿地并发整理”。
- 分代 ZGC 进一步解决的是“如何在这个框架下把年轻对象回收做得更经济”。

这不是推翻 ZGC，而是在它的并发、屏障和重定位基础上加入分代收益。

## 十四、从实现角度看，ZGC 最难的不是某一个算法，而是协议设计

很多人第一次学 ZGC，会把注意力放在某一个术语上，比如：

- 染色指针。
- 读屏障。
- 重映射。

这些都重要，但真正难的是它们必须组成一套闭环协议。

这个协议至少要同时回答下面几个问题：

- 当前引用属于哪个阶段视图。
- 对象是否已经被标记。
- 对象是否已经搬迁。
- 旧引用是否还允许被访问。
- 访问旧引用时如何修正。
- 什么时候旧页才可以安全释放。

只解决其中一个问题没有意义，因为任何一个环节断掉，都会导致并发搬迁失去正确性。

所以，ZGC 的工程价值不只是一个算法点，而是它把“低停顿并发整理”做成了一套可运行的 HotSpot 机制。

## 十五、可以把 ZGC 记成一条清晰主线

如果读完前面的细节，还想再压缩成一条主线，可以直接记下面这组因果关系：

- 因为目标是极低停顿，所以不能把大量标记和整理工作都放在 Stop-The-World 里。
- 因为要并发整理，所以对象搬家时不能要求所有引用立刻一次性修正。
- 因为不能一次性全修，所以需要读屏障在访问时动态修正引用。
- 因为读屏障要足够快，所以引用本身要携带状态，也就是染色指针。
- 因为旧地址和新地址会并存一段时间，所以需要重定位集和地址映射机制。
- 因为这一整套机制成立，ZGC 才能把大多数重活移到并发阶段，从而把停顿时间压低。

## 十六、总结

ZGC 最核心的突破，不是“把 GC 变得更会回收垃圾”，而是“把对象整理这件最容易导致长停顿的工作，改造成了并发可执行的过程”。

它的实现主线可以概括为：

- 用并发标记识别活对象。
- 用重定位集限定本轮要整理的页。
- 用并发转移搬迁对象。
- 用染色指针表达引用状态。
- 用读屏障在访问时修正旧引用。
- 用阶段边界停顿保证全局一致性。

因此，ZGC 特别适合下面这类场景：

- 堆很大。
- 延迟敏感。
- 不希望 GC 停顿随着堆增长显著拉长。

如果用一句最短的话来总结 ZGC：

- 它是一种依靠染色指针和读屏障，把标记与整理大规模并发化，从而实现超低停顿的 HotSpot 垃圾回收器。
