# CMS、G1、ZGC 垃圾回收器对比与选型

CMS、G1、ZGC 这三个回收器，经常会被放在一起比较，但它们的出发点并不一样。

- CMS 解决的是“老年代回收停顿太长”的老问题。
- G1 解决的是“在大堆场景里，让停顿更可控，同时别把吞吐量丢得太多”。
- ZGC 解决的是“把停顿时间继续压低，而且尽量不要随着堆变大而明显变长”。

所以它们并不是简单的前后替代关系，而是三种不同的工程取舍。

如果只先记一句话，可以先这样理解：

- CMS 是遗留时代的低停顿方案。
- G1 是通用服务端场景下最均衡的方案。
- ZGC 是延迟优先场景下更激进的方案。

这篇文章不只讲“谁更快”，而是重点讲清楚下面几件事：

- 它们各自试图解决什么问题。
- 它们在 HotSpot 里是怎么做到的。
- 它们在停顿、吞吐、碎片、CPU 开销和大堆支持上分别怎么取舍。
- 实际项目里应该怎么选。

## 一、先建立比较框架：到底在比较什么

比较 GC，如果只看平均停顿时间，很容易得出错误结论。真正应该比较的是下面几个维度：

- 停顿时间长不长。
- 停顿时间稳不稳定，能不能预测。
- 吞吐量损失大不大。
- 会不会产生碎片。
- 堆变大以后，表现会不会明显恶化。
- 对 CPU、内存元数据、屏障机制的额外成本高不高。
- JDK 版本和工程迁移成本高不高。

这几个维度里，最核心的是三组矛盾：

- 低停顿和高吞吐通常不能同时做到极致。
- 并发回收越多，运行期的协调成本通常越高。
- 如果不移动对象，就更容易产生碎片；如果移动对象，就必须解决引用修正问题。

CMS、G1、ZGC 的本质差异，正好落在这三组矛盾上。

## 二、先看总体结论：三者的核心差异是什么

可以先把三者的实现风格压缩成三句话：

- CMS：并发标记，并发清除，不默认整理内存。
- G1：把堆切成很多 Region，按收益优先回收，并在回收时复制整理对象。
- ZGC：让对象在并发阶段也能安全搬家，尽量把停顿阶段缩到只剩下同步和切换。

如果展开一点，它们分别是这样工作的：

- CMS 的关键是“并发标记 + 并发清除”，用更少的 Stop-The-World 换更复杂的并发一致性维护。
- G1 的关键是“Region + Remembered Set + SATB + 复制整理”，让 JVM 可以只挑最值得回收的一批区域来做回收。
- ZGC 的关键是“染色指针 + 读屏障 + 并发重定位”，让对象搬迁不再依赖一次很长的全局停顿。

先给出一张总表，后面再逐项拆开：

| 维度 | CMS | G1 | ZGC |
| --- | --- | --- | --- |
| 设计目标 | 缩短老年代停顿 | 停顿可预测、兼顾吞吐 | 极低停顿、弱化堆大小影响 |
| 主要单位 | 老年代整体 + 空闲链表 | Region | ZPage / 重定位集 |
| 核心算法 | 标记-清除 | 分区回收 + 复制整理 | 并发标记 + 并发重定位 |
| 整理内存 | 默认不整理 | 回收时顺带整理 | 回收时并发整理 |
| 碎片问题 | 明显 | 很轻 | 很轻 |
| 主要屏障 | 写屏障，服务于增量更新 | 前写屏障 + 后写屏障 | 读屏障为主 |
| 大堆支持 | 一般 | 较好 | 很好 |
| 吞吐量 | 中等 | 通常最均衡 | 往往略逊于 G1 |
| JDK 现状 | 已废弃并移除 | 主流默认选择 | 主流低延迟选择 |

## 三、这三个回收器，分别在和什么问题作斗争

理解三者差异，最好的办法不是先背阶段名，而是先看它们各自在对抗什么问题。

### 1. CMS 对抗的是“老年代 Full GC 停顿太长”

在 CMS 出现之前，老年代回收通常意味着：

- 需要较长的 Stop-The-World。
- 堆越大，停顿越重。
- 面向响应时间敏感的服务端程序时，体验很差。

CMS 的核心目标因此非常直接：

- 把老年代里最重的工作尽量挪到并发阶段去做。

但它的代价是：

- 不默认整理对象。
- 需要额外处理并发期间引用变化。
- 一旦回收跟不上分配速度，可能退化成一次很重的回收。

### 2. G1 对抗的是“大堆下，停顿不好预测”

G1 不是简单地追求比 CMS 更短，而是追求更可控。

它要解决的问题是：

- 堆已经很大，不能每次都围着整个老年代打转。
- 想在限定的停顿预算里，优先回收最有价值的那部分内存。
- 还希望避免 CMS 那种明显的碎片问题。

所以 G1 的核心思路不是“并发做更多”，而是：

- 把堆切小。
- 只收一部分。
- 优先收垃圾最多的那部分。

### 3. ZGC 对抗的是“即使 G1 也不够低的尾延迟”

当系统对 p99、p999 延迟非常敏感时，即使 G1 的停顿已经不算长，也可能仍然不够。

ZGC 试图继续推进一件事：

- 能不能让对象搬迁本身也并发进行，而不是主要依赖 Stop-The-World 来完成。

如果这件事成立，那么停顿阶段就不需要负责大量对象复制和引用修正，只需要负责很短的全局一致性切换。

ZGC 的整个设计，都是围绕这件事展开的。

## 四、CMS：原理、实现方式、优缺点与场景

CMS 的全称是 Concurrent Mark Sweep。它的名字已经说明了它的核心：

- Concurrent：尽量和应用线程并发执行。
- Mark：先找出活对象。
- Sweep：再把死亡对象占用的空间清掉。

### 1. CMS 的核心实现思路

CMS 主要面向老年代。年轻代通常搭配 ParNew 之类的收集器，因此 CMS 低停顿，主要说的是老年代回收停顿较低，不是整个 JVM 完全没有明显停顿。

CMS 的工作流程可以概括成下面几个阶段：

1. 初始标记。
2. 并发标记。
3. 重新标记。
4. 并发清除。
5. 并发重置。

其中真正必须 Stop-The-World 的，主要是初始标记和重新标记。

### 2. CMS 的各阶段分别在做什么

#### 2.1 初始标记

这个阶段会短暂停顿应用线程，先把和 GC Roots 直接关联的一批对象标出来。

它的目标不是完成整个可达性分析，而是建立并发标记的起点。因为 Roots 数量相对可控，所以这个阶段通常比较短。

#### 2.2 并发标记

从初始标记得到的起点出发，GC 线程并发遍历对象图，把能到达的对象继续标出来。

问题在于，这时应用线程还在运行，对象引用关系也还在变化。如果 GC 正在扫描对象 A，业务线程可能同时把 A 的字段改成另一个引用，或者把某条引用边断开。

这就带来一个核心难点：

- 并发标记期间，对象图不是静止的。

CMS 不能假设“我看到的对象图一直不变”，否则就会漏标或错标。

#### 2.3 重新标记

重新标记是 CMS 里非常关键的一次 Stop-The-World。

它的任务不是从头再标一遍，而是修正并发标记期间，由应用线程修改引用关系带来的偏差。也可以把它理解成：

- 把并发阶段来不及完全保证一致性的那部分账，在这里补齐。

#### 2.4 并发清除

对象图一旦确认，CMS 就可以并发回收那些没有被标记到的对象。

这个阶段的特点是：

- 它释放的是死对象占用的块。
- 但通常不搬动还活着的对象。
- 所以会形成很多不连续的空洞。

这就是 CMS 碎片问题的根源。

### 3. CMS 为了支持并发标记，做了什么额外设计

CMS 的关键问题不是“标记会不会做”，而是“标记时对象图一直在变，怎么还能保证最终结果正确”。

CMS 采用的是增量更新这一类思路。你可以把它理解成：

- 并发标记时，应用线程继续改引用。
- JVM 用写屏障把这些变化记下来。
- 到重新标记时，再把这些变动重新检查一遍。

这件事本质上是在回答一个问题：

- 当对象图在边走边变的时候，GC 怎么知道哪些地方需要补扫。

CMS 的答案是：

- 不试图在每次引用写入时立刻维持一张完整精确的实时对象图。
- 而是先把“这里发生过变化”这件事记下来，再在 remark 阶段集中修正。

### 4. CMS 最大的工程代价是什么

CMS 最大的代价有三个。

#### 4.1 内存碎片

因为 CMS 默认是标记-清除，不做常规压缩整理，所以老年代会逐渐形成很多空闲碎片。

碎片带来的问题不是“空闲总量不够”，而是：

- 明明总空闲空间不少。
- 但找不到足够大的连续空间分配大对象。

这也是 CMS 容易在运行一段时间后变得不稳定的原因之一。

#### 4.2 浮动垃圾

并发清除期间，应用线程还在创建对象，也还在制造新的垃圾。这部分在本轮回收开始之后新产生、但来不及纳入当前回收结果的垃圾，通常会留到下一轮处理。

这意味着：

- CMS 必须预留更多安全空间。
- 它不能把老年代用到特别满再开始工作。

#### 4.3 Concurrent Mode Failure

这是 CMS 很经典的问题。

如果 CMS 并发回收的速度跟不上应用线程分配对象、晋升对象的速度，就可能出现：

- 老年代还没来得及清出来足够空间。
- 分配却已经顶上来了。

这时 JVM 可能不得不退化到一次更重的 Stop-The-World 回收，停顿时间会非常难看。

这也是为什么 CMS 虽然平时停顿不长，但极端情况下尾部风险比较高。

### 5. CMS 的优点

- 老年代停顿相比传统 Full GC 明显更短。
- 在 JDK 8 时代非常成熟，很多历史系统积累了大量调优经验。
- 对响应时间敏感、但又暂时无法升级 JDK 的老系统，依然有现实价值。

### 6. CMS 的缺点

- 会产生明显的内存碎片。
- 对并发阶段的 CPU 竞争比较敏感。
- 存在浮动垃圾，需要更保守地预留空间。
- 一旦发生 concurrent mode failure，停顿会突然变得很长。
- 已经被废弃并移除，不适合新项目继续投入。

### 7. CMS 适合什么场景

CMS 更适合下面这类场景：

- 仍在 JDK 8 或更老环境上运行。
- 线上系统历史包袱很重，短期无法升级。
- 业务对停顿比较敏感，但迁移成本比性能问题更现实。

如果是新项目，或者已经在 JDK 11、17、21 这一代上，CMS 通常不应该再作为首选。

## 五、G1：原理、实现方式、优缺点与场景

G1 的全称是 Garbage-First Garbage Collector。它的名字里最关键的是 Garbage-First，也就是：

- 优先回收最值得回收的区域。

它不是简单地把老年代并发回收，而是把堆管理方式整个换掉了。

### 1. G1 的核心实现思路

G1 会把整个堆切成很多大小相同的 Region。每个 Region 在不同时间可以扮演不同角色：

- Eden。
- Survivor。
- Old。
- Humongous。
- Free。

这里最重要的一点是：

- 年轻代和老年代在 G1 中更多是逻辑分组，不是物理上固定不变的一整片内存区间。

这意味着 JVM 可以更灵活地决定“本轮到底收哪几块”。

### 2. G1 为什么能只回收一部分堆

如果想只回收若干个 Region，就必须知道：

- 堆里其他 Region 有没有对象引用到了这些待回收区域中的对象。

如果不知道，JVM 为了安全就只能扫全堆，那分区回收就失去意义了。

G1 为了解决这个问题，引入了 Remembered Set，也就是 RSet。

可以把 RSet 理解成：

- 每个 Region 都维护一份“外面哪些位置可能引用了我”的索引。

这样回收某个 Region 时，就不需要重新扫描整个堆，只需要关注：

- GC Roots。
- 当前 Collection Set 里的 Region。
- 以及这些 Region 对应的 RSet 提示出来的外部引用来源。

这就是 G1 能够局部回收的基础。

### 3. G1 的 Collection Set 是什么

G1 每次 GC 并不是随便收几个 Region，而是会先选出本轮要处理的一组 Region，这组集合叫 Collection Set，简称 CSet。

选择逻辑大体上会考虑：

- 哪些 Region 垃圾比例更高。
- 哪些 Region 回收收益更大。
- 在当前停顿预算内，最多能放进多少工作量。

这就是 G1 比 CMS 更“可预测”的关键原因之一：

- 它会先做成本估算，再决定本轮收多少。

### 4. G1 的并发标记为什么重要

如果 G1 不先知道各个 Region 的垃圾分布，就没法决定“垃圾优先”到底该优先谁。

因此，G1 会在合适的时候发起并发标记，大致流程可以理解成：

1. 初始标记，建立起点。
2. 并发标记，统计对象可达性和各 Region 的存活情况。
3. 重新标记，修正并发期间的变化。
4. 清理和筛选，决定哪些 Old Region 值得进入后续 Mixed GC。

这个结果的核心用途不是立刻全堆回收，而是：

- 给后续的 Region 选择提供依据。

### 5. G1 的屏障和 RSet 是怎么配合的

G1 为了既能并发标记，又能做分区回收，通常需要两类额外机制。

#### 5.1 后写屏障：维护跨 Region 引用线索

当程序执行类似下面这样的引用写入时：

```java
obj.field = newRef;
```

G1 会借助后写屏障把这次写入对应的 card 记成脏卡，后续再通过 refinement 线程或 GC 线程把这些卡片精化成 RSet 信息。

这一步的目标是：

- 让 JVM 知道哪些外部位置可能新产生了跨 Region 引用。

#### 5.2 前写屏障：服务于 SATB 并发标记

G1 的并发标记使用 SATB，也就是 Snapshot-At-The-Beginning。

它的直观意思是：

- 标记时尽量保住“标记开始那一刻”的对象图快照。

如果某个引用即将被覆盖，前写屏障会先把旧引用值记录下来，避免并发标记因为用户线程过早断开引用而漏标对象。

所以 G1 的一个重要特点是：

- 它同时维护“并发标记正确性”和“分区引用可追踪性”。

这也是它比 CMS 更复杂、但也更稳健的重要原因。

### 6. G1 的 Young GC 和 Mixed GC 有什么不同

G1 最常发生的是 Young GC，也就是主要回收 Eden 和部分 Survivor Region。还活着的对象会被复制到新的 Survivor 或 Old Region。

这件事非常关键，因为它意味着：

- G1 在回收时会顺手做整理。

只要活对象被复制走，原来的 Region 就可以整块释放，不会留下 CMS 那种大量空洞。

而 Mixed GC 则是在完成并发标记之后，不只回收年轻代，还会顺带回收一批垃圾比例较高的 Old Region。

所以 Mixed GC 是 G1 真正把老年代也纳入分批治理的方式。

### 7. G1 的优点

- 停顿时间比 CMS 更可预测。
- 通过复制整理，基本没有明显的老年代碎片问题。
- 对中大堆服务端应用更友好。
- 是现代 HotSpot 上非常稳妥的通用选择。

### 8. G1 的缺点

- 不是极限低延迟方案，尾延迟通常不如 ZGC。
- RSet、屏障、并发标记都会带来额外开销。
- 对大量 Humongous 对象的场景不算特别理想。
- 如果参数、堆大小、分配速率和业务负载不匹配，停顿目标也不一定总能满足。

### 9. G1 适合什么场景

G1 适合绝大多数普通服务端应用，尤其是下面这些情况：

- 使用较新的 JDK。
- 希望兼顾吞吐量、停顿时间和实现成熟度。
- 堆已经不小，但还没有到必须为极低延迟付出更高成本的地步。

如果没有特别强的低延迟指标要求，G1 往往是第一选择。

## 六、ZGC：原理、实现方式、优缺点与场景

ZGC 的目标比 G1 更激进。它要做的不只是“停顿可控”，而是：

- 尽量把停顿压到极低。
- 尽量让停顿时间不随着堆大小线性恶化。

它真正关键的变化，不是“标记更快”，而是：

- 对象搬迁可以在并发阶段继续进行。

### 1. ZGC 的核心实现思路

ZGC 的低停顿能力，主要建立在下面几组机制上：

- 染色指针。
- 读屏障。
- 并发标记。
- 并发重定位。
- 基于页和重定位元数据的地址重映射。

如果压缩成一句话，可以把 ZGC 理解成：

- 让引用在被访问时就有机会被修正，而不是要求 JVM 先把所有引用一次性改完，应用才能继续跑。

### 2. 染色指针到底在做什么

在传统理解里，一个引用主要就是“对象地址”。ZGC 会在 64 位引用的高位里携带额外状态信息，因此引用不只是“指向谁”，还带着一点运行期语义。

这样 JVM 在访问一个引用时，可以顺带知道：

- 这个引用是否属于当前标记视图。
- 这个对象是否已经进入重定位相关阶段。
- 当前这次访问是否需要通过屏障做修正。

这就是为什么很多材料会说：

- ZGC 不是单纯依赖外部表结构来维护状态，而是让指针本身带一部分状态。

### 3. 读屏障为什么是 ZGC 的核心

CMS 和 G1 更依赖写屏障，因为它们重点要记录“引用关系发生了什么变化”。

ZGC 最核心的是读屏障。直观理解就是：

- 线程每次准备用某个引用访问对象时，先经过一层轻量检查。
- 如果引用已经是当前合法视图，就直接用。
- 如果引用还指向旧地址，或者需要做重映射，屏障会把它修正到正确位置。

这一步的意义非常大，因为它让 ZGC 拥有下面这种能力：

- 对象已经搬到新位置了。
- 但应用线程手里还可能拿着旧引用。
- 程序依然可以继续安全运行，因为真正解引用时会被屏障纠正。

这就是 ZGC 能并发搬对象的底层基础。

### 4. ZGC 的回收流程可以怎样理解

ZGC 也有少量 Stop-The-World 阶段，但这些阶段通常很短，主要承担的是：

- 建立阶段边界。
- 扫描关键根集合起点。
- 做全局视图切换。

真正重的工作，主要放在并发阶段处理。可以按下面这条主线理解：

1. 短暂停顿，建立标记起点。
2. 并发标记，找出活对象。
3. 短暂停顿，完成标记闭环和阶段切换。
4. 选出需要重定位的页。
5. 并发把活对象搬到新位置。
6. 通过读屏障逐步把旧引用修正到新地址。
7. 当旧页不再被引用后，把旧页释放。

注意，这里的关键不在于“搬对象”这件事本身，而在于：

- 搬对象和修引用不再要求一次全局大停顿同时完成。

### 5. ZGC 为什么能把堆做得很大

传统 GC 在大堆下最难的是：

- 扫描更多对象。
- 移动更多对象。
- 在停顿里修更多引用。

ZGC 的核心改进是把第三件事拆掉。它不要求“所有引用都在停顿里改完”，而是允许应用线程继续持有旧引用，并在访问时由屏障修正。

因此，ZGC 的停顿时间与堆大小之间的关系会弱很多。堆变大，回收总工作量当然还是会增加，但不必直接表现为一次更长的 Stop-The-World。

### 6. ZGC 的优点

- 停顿时间极短，尤其适合看重 p99、p999 延迟的系统。
- 对大堆更友好，堆增大时停顿劣化通常没有传统方案明显。
- 具备整理能力，碎片问题较轻。
- 很适合延迟敏感的在线服务。

### 7. ZGC 的缺点

- 为了实现低停顿，需要更多并发协作和元数据机制。
- 对 CPU 余量更敏感，如果机器已经很紧，收益可能不如预期。
- 纯吞吐导向场景下，往往不如 G1 那么划算。
- 对运行环境和 JDK 版本要求更现代，老系统迁移成本更高。

### 8. ZGC 适合什么场景

ZGC 更适合下面这些场景：

- 核心指标是低尾延迟，而不是只看平均吞吐。
- 堆很大，或者预计以后会变得很大。
- 在线交易、搜索、推荐、实时网关、大缓存服务这类系统，对抖动非常敏感。
- 能接受一定额外 CPU 成本，以换取更稳定的响应时间。

如果系统最痛的不是停顿，而是机器不够、CPU 压得很满，那 ZGC 未必是第一优先。

## 七、三者在“并发正确性”上到底有什么本质差异

这一部分是最值得真正理解的地方。

三者都在尝试回答同一个问题：

- 应用线程不停地改对象引用，GC 线程怎么还能得出正确的回收结果。

它们的答案并不一样。

### 1. CMS 的答案：写入发生变化时记下来，remark 阶段补扫

CMS 的核心思路可以理解成：

- 并发标记时先尽量往前跑。
- 谁在并发期间改了引用，就把“这里变过”记下来。
- remark 阶段再把这些变动补齐。

它的重点是：

- 用一次较短但必要的重新标记，弥补并发标记的一致性缺口。

### 2. G1 的答案：用 SATB 保住标记快照，再用 RSet 支持局部回收

G1 比 CMS 多了一层复杂度，因为它不只要解决并发标记一致性，还要解决“我只回收部分 Region 时，怎么知道别人有没有引用我”。

所以它实际上同时做了两件事：

- 用 SATB 处理并发标记的一致性。
- 用 RSet 处理跨 Region 引用跟踪。

这也是为什么 G1 的实现明显比 CMS 更重，但也换来了更强的分区治理能力。

### 3. ZGC 的答案：引用在访问时即时修正

ZGC 采取的思路更激进：

- 与其把“所有引用都先修好”作为应用继续运行的前提。
- 不如允许旧引用继续存在，但保证每次真正访问它时都能被矫正。

这就是读屏障和染色指针配合的意义。

所以从实现哲学上看：

- CMS 更像是“变化先记账，停顿时补账”。
- G1 更像是“既要保快照，又要维护跨区索引”。
- ZGC 更像是“访问时纠偏，让搬迁与修正变成持续发生的事”。

## 八、三者的优缺点怎么横向理解

如果用工程语言总结三者的取舍，可以归纳成下面几条。

### 1. CMS 的优缺点本质

- 优点来自“不整理”，因此停顿较短。
- 缺点也来自“不整理”，因此会有碎片和失败回退风险。

CMS 的问题不是平时跑不动，而是长时间运行后的稳定性和极端尾部风险不够理想。

### 2. G1 的优缺点本质

- 优点来自“Region + 按收益回收 + 复制整理”，因此更均衡。
- 缺点来自“要维护更多元数据和屏障”，因此实现和运行时成本更复杂。

G1 的强项不是把某一个指标做到极致，而是把多数指标维持在一个比较稳的水平上。

### 3. ZGC 的优缺点本质

- 优点来自“并发搬迁 + 读屏障修正”，因此停顿极低。
- 缺点来自“并发机制非常重”，因此对 CPU 和环境要求更高。

ZGC 的强项非常明确，就是低延迟；它并不追求成为所有场景下最省成本的方案。

## 九、实际项目里应该怎么选

如果只给一个简单决策树，可以按下面这条线理解。

### 1. 新项目，普通服务端应用，没有极端延迟要求

优先考虑 G1。

原因很简单：

- 成熟。
- 默认支持好。
- 吞吐、停顿、碎片控制都比较均衡。
- 调优资料和线上经验也最丰富。

### 2. 延迟极其敏感，尤其关注 p99、p999

优先考虑 ZGC。

典型场景包括：

- 高频交易。
- 搜索和推荐链路。
- API 网关。
- 大缓存服务。
- 对请求抖动容忍度很低的在线系统。

如果系统的核心问题是一次几十毫秒甚至更长的停顿就会直接打坏 SLA，那么 ZGC 的意义就会很大。

### 3. 还在 JDK 8，且系统迁移成本远高于调优收益

CMS 可以作为短期现实选择，但它更像维持性方案，不应该再被当作长期方向。

更实际的路线通常是：

- 先把 CMS 系统稳定住。
- 再找合适窗口迁到 G1 或 ZGC。

### 4. 机器 CPU 已经很紧，吞吐量比延迟更重要

这时要非常谨慎地看待 ZGC。

因为 ZGC 的优势来自更多并发协调和屏障机制，如果系统本来就没有多少 CPU 余量，那么它带来的收益不一定能覆盖成本。

这类场景里，G1 往往更容易取得平衡。

### 5. 堆很大，而且未来还会继续增长

要重点评估 ZGC。

因为大堆场景下，停顿时间是否随着堆一起变坏，是选型的核心问题。G1 在很多大堆场景里也能工作得不错，但当低延迟要求继续提高时，ZGC 的优势会更明显。

## 十、选型时不要只看 GC 名字，还要看这些指标

真实选型不是“看一篇文章就决定”，而是要结合运行数据。至少要观察下面这些指标：

- GC 暂停时间分布，尤其是 p95、p99、p999。
- Full GC 是否出现，以及出现频率。
- 老年代回收后剩余占用是否持续偏高。
- 对象分配速率是否很高。
- 活对象集合是不是很大。
- 是否存在大量大对象或超大数组。
- 业务高峰时 CPU 是否还有余量。

如果这些数据不清楚，就很容易出现一种误判：

- 明明是对象分配模式的问题。
- 却以为只要换一个 GC 名字就能彻底解决。

GC 选型只能优化回收过程，不能替代对象生命周期设计、缓存策略设计和内存模型设计。

## 十一、最后给一个落地结论

如果把这篇文章压缩成最终结论，可以记成下面几句话：

- CMS 的核心价值在于“用并发标记和并发清除缩短老年代停顿”，但它的问题是碎片、浮动垃圾和失败回退，因此更适合遗留系统而不是新系统。
- G1 的核心价值在于“通过 Region、RSet、SATB 和分批回收，让停顿更可预测，同时避免明显碎片”，因此是大多数现代 Java 服务端应用最稳妥的默认选择。
- ZGC 的核心价值在于“通过染色指针、读屏障和并发重定位，把对象搬迁也并发化”，因此特别适合大堆、低延迟、对尾部停顿敏感的系统。

如果只做一句话决策：

- 默认先看 G1。
- 对低延迟要求极高时看 ZGC。
- 只有在遗留环境受限时才继续保留 CMS。

这三个回收器最大的区别，不是参数名不同，而是它们分别把工程复杂度放在了不同位置：

- CMS 把复杂度放在并发标记修正上。
- G1 把复杂度放在分区治理和停顿预算控制上。
- ZGC 把复杂度放在引用访问模型和并发搬迁上。

理解到这一层，很多表面的“哪个好”问题，基本就能自己判断了。
