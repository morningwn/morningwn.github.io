# MySQL 如何实现不同隔离级别

讨论 MySQL 事务隔离时，先要限定对象。SQL 标准定义的是现象和语义，真正决定实现细节的是存储引擎。下面的内容以 InnoDB 为准，因为日常讨论里的 MVCC、Read View、Gap Lock、Next-Key Lock 都属于 InnoDB 的实现机制。

从实现角度看，InnoDB 并不是靠一套纯锁模型来完成隔离，而是把两类机制组合起来：

- 一致性读依赖 MVCC，在版本链上选择对当前事务可见的历史版本。
- 当前读依赖锁，直接读取可操作的最新版本，并对记录或范围建立并发约束。

不同隔离级别，本质上是在调整三个问题：

- 一致性快照在什么时候创建。
- 同一事务内是否复用同一份快照。
- 当前读需要把锁扩展到记录，还是扩展到记录所在的间隙和范围。

## 一、实现隔离级别的基础部件

### 1. 版本链：Undo Log 提供历史版本

InnoDB 的更新不是简单覆盖。每次 UPDATE 或 DELETE 时，旧版本会被写入 Undo Log，记录本身则保留指向旧版本的回滚指针，同时携带最后一次修改它的事务标识。于是同一行记录会形成一条版本链。

这条版本链的意义在于：普通 SELECT 不必总是读取最新值，而是可以沿着版本链回溯，找到对当前事务可见的那个版本。

### 2. Read View：定义当前事务的可见性边界

Read View 可以理解为一致性读使用的快照边界。它会记录创建快照时系统中哪些事务仍然活跃，并据此判断某个版本是否可见。

可以把可见性规则概括为：

- 当前事务自己产生的版本，对自己可见。
- 在 Read View 创建之前已经提交的事务版本，可见。
- 在 Read View 创建时仍然活跃，或在此之后才启动的事务版本，不可见。

如果最新版本不可见，InnoDB 就沿着 Undo Log 向前查找，直到找到一个满足可见性规则的版本。这就是 MVCC 能够提供一致性快照的关键。

### 3. 一致性读与当前读

InnoDB 的读需要分成两类看：

- 一致性读：普通 SELECT，属于非锁定读，主要由 MVCC 决定结果。
- 当前读：SELECT ... FOR UPDATE、SELECT ... FOR SHARE（5.x 版本中为 SELECT ... LOCK IN SHARE MODE）、UPDATE、DELETE、INSERT，读取当前可操作版本，并参与加锁。

这一区分非常重要。很多事务行为看上去矛盾，本质上不是隔离级别失效，而是同一事务里混用了两套不同的读取规则。

### 4. 锁不是只锁“行”，还会锁“范围”

当前读要解决的不只是同一行被同时修改的问题，还要解决范围内插入导致的幻读问题。因此 InnoDB 使用的并不只有行锁：

- Record Lock：锁住已经存在的索引记录。
- Gap Lock：锁住索引记录之间的间隙，阻止新记录插入。
- Next-Key Lock：Record Lock 与 Gap Lock 的组合，用于保护一段索引范围。

锁范围和索引访问路径强相关。唯一索引上的等值命中，通常只需要锁记录本身；非唯一条件或范围扫描，则更可能落到 Gap Lock 或 Next-Key Lock。

## 二、四种隔离级别在调什么

| 隔离级别             | 一致性读快照                           | 当前读与锁                            | 主要保证                 | 主要代价          |
|------------------|----------------------------------|----------------------------------|----------------------|---------------|
| READ UNCOMMITTED | 不要求已提交可见性                        | 其余行为近似 READ COMMITTED            | 几乎只保留最弱隔离            | 可能脏读          |
| READ COMMITTED   | 每条语句创建新快照                        | 以记录锁为主，Gap Lock 大幅减少             | 避免脏读                 | 不可重复读、幻读仍可能出现 |
| REPEATABLE READ  | 事务内首次一致性读创建快照，后续复用               | 范围当前读使用 Gap Lock 或 Next-Key Lock | 避免脏读、避免不可重复读，并抑制常见幻读 | 锁范围更大，并发成本更高  |
| SERIALIZABLE     | 基于 REPEATABLE READ，并让普通读更积极参与锁竞争 | 读写都更接近串行化执行                      | 最强隔离                 | 吞吐下降，阻塞增加     |

## 三、READ UNCOMMITTED

READ UNCOMMITTED 的核心不是“完全不加锁”，而是对非锁定 SELECT 不再要求提交可见性。

在这个级别下：

- 普通 SELECT 可能读到其他事务尚未提交的修改。
- 如果对方事务随后回滚，之前读到的结果就成为脏读。
- 除此之外，其余锁行为大体可按 READ COMMITTED 理解。

因此，READ UNCOMMITTED 的主要特点不是实现更复杂，而是几乎放弃了一致性读应有的稳定性。它通常只出现在对结果精确性要求极低的特殊场景中。

## 四、READ COMMITTED

READ COMMITTED 的实现重点在于：每一条一致性读语句，都单独创建自己的 Read View。

这意味着：

- 事务内第一次普通 SELECT 和第二次普通 SELECT，看到的可能不是同一份快照。
- 某条语句只能看到该语句开始前已经提交的版本。
- 它可以避免脏读，但不能保证可重复读。

在锁策略上，READ COMMITTED 也比 REPEATABLE READ 更保守：

- 对 SELECT ... FOR UPDATE、SELECT ... FOR SHARE、UPDATE、DELETE 这类当前读，通常只锁命中的索引记录，不锁记录前后的间隙。
- Gap Lock 主要保留在外键检查和唯一键冲突检查等少数场景。
- 对 UPDATE 和 DELETE，条件过滤后不匹配的记录锁会尽早释放。

这套策略带来两个直接结果：

- 并发度通常更高，锁等待和死锁概率更低。
- 由于范围间隙没有被系统性保护，其他事务可以向范围内插入新记录，因此幻读仍可能发生。

MySQL 官方文档还提到一个仅适用于 READ COMMITTED 的重要细节：当 UPDATE 扫描到一条已被其他事务加锁的记录时，InnoDB 可以先读取该记录的最新已提交版本（不加锁），用来判断 WHERE 条件是否匹配。如果已提交版本不满足条件，就直接跳过，无需等待锁释放；如果满足条件，才再次读取并尝试获取排他锁。这种机制称为 semi-consistent read，是 RC 减少不必要锁等待的一个重要手段。

## 五、REPEATABLE READ

REPEATABLE READ 是 InnoDB 的默认隔离级别，也是 InnoDB 事务模型的核心平衡点。

它的实现原则很明确：事务内第一次一致性读创建 Read View，后续一致性读都复用这一份快照。

因此，在同一事务中：

- 多次普通 SELECT 会读取同一份一致性视图。
- 即使其他事务已经提交更新，当前事务后续的一致性读也不会看到这些新版本。
- 不可重复读由此被消除。

需要注意，上述行为只在显式事务中成立。MySQL 默认开启 `autocommit`，此时每条 SQL 语句都是独立事务，每次 SELECT 都会创建新的 Read View，RR 的快照复用效果无法体现。只有使用 `START TRANSACTION` 或 `BEGIN` 显式开启事务，并在事务内执行多条语句，才能观察到 Read View 复用的完整语义。

### 1. 快照读如何处理幻读

如果事务内执行的始终是普通 SELECT，那么查询结果始终基于同一份快照。其他事务在此期间插入了满足条件的新行，这些新行因为晚于快照创建时间，对当前事务不可见。

因此，对一致性读而言，幻影记录会被快照机制隐藏掉。

### 2. 当前读如何处理幻读

如果事务执行的是 UPDATE、DELETE 或 SELECT ... FOR UPDATE 这类当前读，情况就不同了。当前读必须基于最新可操作版本工作，仅复用旧快照并不能阻止其他事务向查询范围内插入新记录。

这时 InnoDB 会结合索引访问路径使用 Gap Lock 或 Next-Key Lock：

- 唯一索引上的唯一等值命中，通常只锁到目标记录。
- 非唯一条件、范围条件、范围扫描，则会锁住扫描到的索引区间以及相邻间隙。

它的目的不是让读取结果回到旧快照，而是防止并发事务在这段范围内插入新记录，从而避免当前读语义下的幻读。

### 3. 为什么说 RR 里可能看到“两张表状态”

REPEATABLE READ 下最容易误解的一点，是在同一事务里混用普通 SELECT 和当前读。

- 普通 SELECT 返回的是快照视图。
- UPDATE、DELETE、SELECT ... FOR UPDATE 操作的是当前版本，并按当前状态加锁。

因此，一个事务里可能同时接触到“快照中的表状态”和“当前时刻的表状态”。以下示例展示了这一现象：

```sql
-- 假设 accounts 表中 id=1 的记录 balance 初始为 100

-- 事务 A（REPEATABLE READ）
BEGIN;
SELECT balance FROM accounts WHERE id = 1;   -- 返回 100（快照读）

-- 此时事务 B 执行并提交：
-- UPDATE accounts SET balance = 200 WHERE id = 1;

SELECT balance FROM accounts WHERE id = 1;   -- 仍返回 100（复用快照）
UPDATE accounts SET balance = balance + 10 WHERE id = 1;
-- 当前读基于最新版本（balance=200）执行，结果变为 210
SELECT balance FROM accounts WHERE id = 1;   -- 返回 210
```

事务 A 的两次快照读分别看到 100 和 210，中间还通过当前读“跳过”了事务 B 的提交值 200。这种看似矛盾的行为正是混用一致性读与当前读的结果。MySQL 官方文档明确不建议在复杂事务里随意混用这两类语句；如果业务要求读取结果与后续修改严格对应，通常应使用显式锁定读，或者直接提升到 SERIALIZABLE。

## 六、SERIALIZABLE

SERIALIZABLE 可以理解为在 REPEATABLE READ 的基础上，进一步让普通读也积极参与锁竞争，从而尽量把并发执行逼近串行执行。

在显式事务语境下，可以把它理解为：

- 普通 SELECT 不再只是纯粹的一致性读。
- 读操作会按共享锁读处理，和写操作建立更强的冲突关系。
- 范围访问也会更严格地保护相关记录和区间。

这样做的结果是：

- 脏读、不可重复读、幻读都能被更严格地约束。
- 读写之间更容易互相阻塞。
- 吞吐、延迟和死锁处理成本都会明显变差。

因此，SERIALIZABLE 更适合极少数以严格正确性为最高优先级的场景，而不是常规 OLTP 系统的默认选项。

## 七、为什么 InnoDB 默认选择 REPEATABLE READ

REPEATABLE READ 被设为默认值，不是因为它最强，而是因为它在一致性和并发之间做了相对均衡的取舍：

- 普通读仍然走 MVCC，不会像串行化那样让读写全面互斥。
- 同一事务内结果稳定，业务逻辑更容易推导。
- 对范围修改和锁定读，系统又能借助 Next-Key Lock 把常见幻读风险压住。

换句话说，InnoDB 默认选择 RR，是因为它能把高频 OLTP 场景里最常见的读写冲突控制在一个工程上可接受的成本内。

此外，RR 被设为默认值还有一个历史原因：在 MySQL 早期使用 statement-based binlog 的时代，READ COMMITTED 下的 UPDATE/DELETE 执行顺序可能导致主从复制不一致。RR 通过让事务内的快照保持稳定，避免了这类复制问题。从 MySQL 5.7 开始，binlog 格式默认切换为 row-based，这个限制基本消除。因此在采用 row-based binlog 的现代部署中，越来越多的生产系统选择 READ COMMITTED 来获得更高的并发度。

## 八、理解隔离级别时最容易忽略的三个点

1. 隔离级别不是单纯的锁强弱排序，它同时决定快照的生命周期。
2. 是否出现幻读，不能只看隔离级别名称，还要看语句属于一致性读还是当前读。
3. 锁的实际覆盖范围取决于索引访问路径，同一条 SQL 在不同索引条件下，锁行为可能明显不同。

## 总结

InnoDB 对不同隔离级别的实现，可以归结为一套非常清晰的分工：

- Undo Log 和版本链负责保留历史。
- Read View 负责判定哪些历史版本对当前事务可见。
- MVCC 负责让一致性读在不加锁的前提下获得稳定结果。
- Record Lock、Gap Lock、Next-Key Lock 负责为当前读和范围修改建立并发约束。

四种隔离级别的真正差别，并不只是“谁更强”，而是对快照创建时机、快照复用方式以及锁范围扩张策略做出了不同选择。理解这一点，再去看脏读、不可重复读和幻读，就能把概念现象和底层机制对应起来。
