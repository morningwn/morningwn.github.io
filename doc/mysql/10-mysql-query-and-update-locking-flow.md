# MySQL 查询与修改操作的完整执行流程

讨论 MySQL 的执行流程，不能只盯着 SQL 语法本身。真正决定一次查询或修改如何落地的，是 Server 层、优化器、事务系统、日志系统以及 InnoDB 锁管理器之间的配合。

如果把问题聚焦到日常最常见的 `SELECT`、`UPDATE`、`DELETE`、`INSERT`，可以把整条链路概括成一句话：

- Server 层负责解析 SQL、生成执行计划、协调事务与返回结果。
- InnoDB 负责按执行计划访问索引和数据页，并根据语句类型执行一致性读或当前读。
- 一旦进入当前读或写操作，锁就不再只是“锁住某一行”，而是会随着索引访问路径扩展到记录、间隙甚至范围。

理解这条链路后，再去看锁等待、死锁、幻读、更新冲突，才有稳定的分析框架。

## 一、先建立一个正确的整体视图

一次 SQL 从客户端发到 MySQL，大致会经过下面几个阶段：

1. 连接线程接收 SQL，请求进入当前会话上下文。
2. Server 层做语法解析、语义检查、权限检查。
3. 优化器选择访问路径，决定走哪个索引、是否回表、是否做范围扫描。
4. 执行器调用存储引擎接口，按执行计划逐步取记录。
5. InnoDB 在读取记录时判断这是“一致性读”还是“当前读”。
6. 如果是当前读或写操作，InnoDB 会在索引记录和相关范围上建立锁。
7. 修改类语句还要写 Undo Log、Redo Log，并在提交阶段与 Binlog 协调。
8. 事务提交或回滚后，释放相应锁并对外可见。

真正和锁最相关的，不是解析阶段，而是第 3 到第 8 步。

## 二、锁在 SQL 真正执行前就已经埋下伏笔

很多人把锁理解成“扫描到哪一行就锁哪一行”，这只对了一半。锁的范围往往在优化器选定访问路径时就已经基本决定了。

原因很简单：InnoDB 的行锁本质上是索引锁，不是脱离索引存在的物理行锁。

- 如果 SQL 通过唯一索引做唯一等值命中，通常只会落到非常窄的记录锁。
- 如果 SQL 通过非唯一索引做范围扫描，锁通常会沿着扫描区间扩展为 Gap Lock 或 Next-Key Lock。
- 如果 SQL 根本用不上合适索引，执行器可能做大范围扫描，锁覆盖面也会随之放大。

所以分析锁问题，第一步通常不是问“这个语句是什么类型”，而是问“这个语句最终走了什么索引访问路径”。

## 三、查询操作的完整执行流程

### 1. 普通 SELECT：大多数时候走一致性读

对 InnoDB 来说，普通 `SELECT` 默认属于一致性读，也常被称为快照读。

它的执行流程可以概括为：

1. Server 层把 SQL 交给优化器，确定访问路径。
2. 执行器按计划向 InnoDB 请求记录。
3. InnoDB 读取索引记录时，不急着和其他事务争“最新版本”，而是先根据事务隔离级别和 Read View 判断当前事务能看到哪个版本。
4. 如果最新版本不可见，就沿着 Undo Log 版本链向前找可见版本。
5. 找到可见版本后返回给 Server 层，由 Server 层继续做投影、排序、聚合或直接回传客户端。

这条路径的关键点有两个：

- 普通 `SELECT` 读到的不一定是最新值，而是当前事务应当看到的那个版本。
- 它通常不对记录加行锁，因此读写可以并发。

这也是 InnoDB 在高并发下还能维持较好吞吐的基础。

### 2. 普通 SELECT 也不是完全“无锁”

虽然普通 `SELECT` 通常不加记录锁，但它并不是绝对无锁。

至少还存在两类约束：

- MDL 读锁：语句执行期间，Server 层会持有元数据读锁，防止表结构被并发 DDL 破坏。
- 页 latch、B+ 树节点 latch：这些属于内部短期闩锁，用来保护 Buffer Pool 中的内存页和 B+ 树结构的一致性，不等同于事务锁。

因此，讨论“查询是否加锁”时，要区分事务意义上的锁和引擎内部的短期并发控制。

### 3. 锁定读：SELECT ... FOR UPDATE / FOR SHARE

一旦 `SELECT` 带上 `FOR UPDATE` 或 `FOR SHARE`，它就不再是快照读，而变成当前读。

执行流程也会发生变化：

1. 执行器按索引路径去找满足条件的当前记录。
2. InnoDB 不再返回历史可见版本，而是读取当前可操作版本。
3. 在读取过程中，按访问到的索引记录建立锁。
4. 语句结束后，这些锁不会立即释放，而是通常持有到事务提交或回滚。

这类语句的目的不是“读得更快”，而是为后续修改建立先占约束。

例如：

```sql
SELECT *
FROM account
WHERE id = 10 FOR UPDATE;
```

如果 `id` 是主键或唯一索引并且等值命中，通常只会对目标索引记录建立 Record Lock。

但如果语句是：

```sql
SELECT *
FROM account
WHERE balance > 1000 FOR UPDATE;
```

这通常是范围当前读，InnoDB 为了阻止其他事务向该范围插入新记录，会使用 Next-Key Lock 保护扫描到的索引范围。

MySQL 8.0 起，锁定读还支持 `NOWAIT` 和 `SKIP LOCKED` 两种附加选项：

- `FOR UPDATE NOWAIT`：如果目标记录已被其他事务锁定，立即返回错误而不是等待。
- `FOR UPDATE SKIP LOCKED`：跳过已被其他事务锁定的记录，只返回当前可获取的行。

这两种模式在高并发队列消费、任务调度等场景中非常实用，可以避免长时间的锁等待。

## 四、修改操作的完整执行流程

### 1. UPDATE 的执行流程

`UPDATE` 本质上可以拆成“先找出要改哪些记录，再对这些记录做当前版本修改”。

典型流程如下：

1. Server 层完成解析、权限检查和优化。
2. 执行器按执行计划调用 InnoDB 搜索候选记录。
3. InnoDB 对候选记录执行当前读，并尝试建立排它锁。
4. 如果记录被其他事务锁住，当前事务进入等待，或者参与死锁检测。
5. 记录锁拿到后，InnoDB 判断该记录是否最终满足 `WHERE` 条件。
6. 对满足条件的记录生成新版本，同时写入 Undo Log 以支持回滚和 MVCC。
7. 修改对应数据页，并记录 Redo Log，保证崩溃恢复。
8. 提交时与 Binlog 协调，完成持久化与复制一致性要求。
9. 事务提交后释放锁，对其他事务可见。

从锁的角度看，`UPDATE` 有三个最容易被忽视的点：

- 它不是先把所有目标行算出来再一次性加锁，而是通常边扫描边加锁。
- 锁加在索引访问路径上，不是抽象地加在“逻辑结果集”上。
- 条件写得一样，不同索引计划可能导致完全不同的锁范围。

### 2. 通过二级索引更新时，锁往往不止一把

如果 `UPDATE` 是通过二级索引定位记录，执行路径通常不是“锁住二级索引项就结束”，而是还要继续找到对应的聚簇索引记录。

典型链路是：

1. 先扫描二级索引，定位满足条件的索引项。
2. 在二级索引记录或范围上建立对应锁。
3. 根据主键值回到聚簇索引。
4. 对真正要修改的聚簇索引记录加排它锁。
5. 如果更新字段影响到相关二级索引，还要删除旧索引项、插入新索引项。

这意味着一次看似简单的 `UPDATE`，可能同时涉及：

- 二级索引上的范围锁。
- 聚簇索引记录上的排它锁。
- 因索引键变化而产生的额外索引维护。

所以很多“只更新一行却锁很大”的场景，本质上不是主键行本身有问题，而是扫描入口选在了一个范围更宽的二级索引上。

### 3. DELETE 的执行流程

`DELETE` 和 `UPDATE` 的锁语义非常接近。

它同样会：

1. 按执行计划定位候选记录。
2. 对候选记录做当前读并加排它锁。
3. 生成 Undo 信息。
4. 在聚簇索引和相关二级索引上标记删除。
5. 等事务提交后由后台机制逐步完成物理清理。

因此，`DELETE` 的并发风险和 `UPDATE` 基本一致：如果是范围删除，就往往不是锁一条，而是锁一段。

### 4. INSERT 的执行流程

`INSERT` 的锁逻辑和 `UPDATE`、`DELETE` 不完全一样，因为它不是先锁住已有记录再修改，而是向某个索引位置插入新记录。

它的大致流程是：

1. 找到目标索引键应当插入的位置。
2. 在目标间隙上申请 Insert Intention Lock，表明自己准备向该间隙插入。
3. 检查唯一约束、外键约束以及可能的冲突。
4. 如果目标位置被其他事务的 Gap Lock 或 Next-Key Lock 覆盖，插入会等待。
5. 冲突检查通过后，写入新记录、Undo Log、Redo Log。
6. 提交事务后，新记录对其他事务可见。

Insert Intention Lock 的特点是：

- 它是间隙上的一种插入意向，而不是普通记录锁。
- 多个事务向同一个间隙的不同位置插入时，彼此未必冲突。
- 真正容易阻塞它的，往往是别的事务已经在这个间隙上持有 Gap Lock 或 Next-Key Lock。

## 五、InnoDB 里的锁到底有哪些

理解执行流程时，最常见的锁可以分成下面几类。

### 1. MDL：保护表结构

MDL 由 Server 层管理。

- 普通查询、更新、删除、插入都会持有元数据读锁。
- `ALTER TABLE` 这类 DDL 往往需要更强的 MDL 写锁。
- 因此长事务即使没有阻塞行锁，也可能卡住 DDL。

### 2. Intention Lock：表级意向锁

InnoDB 在加行锁前，会先在表上放置意向锁：

- `IS` 表示后续会在某些记录上加共享锁。
- `IX` 表示后续会在某些记录上加排它锁。

它们通常不直接造成业务层面的等待，主要作用是让表锁和行锁之间能快速判断兼容性。

### 3. Record Lock：记录锁

Record Lock 只锁定某条已经存在的索引记录。

最典型的场景是唯一索引上的唯一等值当前读，例如按主键 `FOR UPDATE` 或按主键 `UPDATE` 一行。

### 4. Gap Lock：间隙锁

Gap Lock 锁住的是两条索引记录之间的区间，或者边界外的开口区间。它不锁现有记录本身，而是阻止新记录插入。

它主要是为了解决范围当前读下的幻读问题。

### 5. Next-Key Lock：记录锁 + 间隙锁

Next-Key Lock 是 InnoDB 在可重复读下最常见的范围保护方式。

可以把它理解成：锁住当前索引记录，同时锁住它前面的间隙。这样既防止别人改这条记录，也防止别人往这个区间塞入新记录。

### 6. Insert Intention Lock：插入意向锁

这种锁出现在 `INSERT` 过程中，用来声明“我要往这个间隙里插入一条记录”。

它本身的冲突面通常不大，但会被别的事务持有的 Gap Lock 或 Next-Key Lock 卡住。

## 六、为什么很多锁要等到提交才释放

InnoDB 的事务锁整体遵循两阶段锁协议，可以简单理解成：

1. 执行过程中不断获取需要的锁。
2. 在事务结束前，不主动释放这些用于保证隔离性的锁。
3. 到提交或回滚阶段，再统一释放。

这也是下面这些现象的根本原因：

- 一条很快执行完的 `UPDATE`，只要事务没提交，别人仍然可能被它阻塞。
- 应用层忘记提交事务，会把行锁、间隙锁、MDL 一起拖长。
- 长事务不是只占连接，它会持续扩大整个实例的并发成本。

这里要特别注意区分两类控制手段：

- 事务锁服务于隔离性，通常跟随事务生命周期。
- 引擎内部 latch 只服务于内存结构保护，持有时间很短，通常在访问页或修改树节点时即刻释放。

## 七、锁是如何随着索引路径扩张的

锁问题最关键的不是锁名称，而是锁范围为什么会扩大。

下面这几种情况最典型。

### 1. 唯一索引等值命中

```sql
UPDATE user
SET status = 'active'
WHERE id = 100;
```

如果 `id` 是主键，并且执行计划确实通过主键唯一命中，那么锁通常集中在目标记录上，范围最小。

### 2. 非唯一索引等值匹配

```sql
UPDATE orders
SET flag = 1
WHERE status = 'NEW';
```

如果 `status` 是非唯一索引，那么这个语句实际上可能命中很多索引记录。InnoDB 通常需要沿着该索引区间逐条扫描和加锁，锁覆盖范围自然更大。

### 3. 范围条件

```sql
DELETE
FROM orders
WHERE created_at < '2026-01-01';
```

这类语句本质上就是范围当前读。为了避免事务期间有新记录插入到这个范围里，InnoDB 往往会用 Gap Lock 或 Next-Key Lock
保护整个扫描区间。

### 4. 无合适索引

如果 `WHERE` 条件没有可用索引，执行器就可能退化为大范围扫描。此时虽然逻辑目标是“删除符合条件的少数几行”，但引擎在查找过程中可能已经碰了大量记录，锁影响面也会显著扩大。

所以很多线上“锁太大”的根因，本质上不是事务写得多，而是访问路径选错了。

## 八、隔离级别如何影响查询和修改时的锁

同一条 SQL，在不同隔离级别下，锁行为并不完全相同。

### 1. READ COMMITTED

在 RC 下：

- 普通 `SELECT` 依旧走一致性读。
- 当前读和修改操作仍然加锁。
- 但 Gap Lock 明显收缩，主要保留在少数必要场景，例如唯一键检查、外键检查。
- InnoDB 在 RC 下还启用了半一致性读（semi-consistent read）优化：`UPDATE` 或 `DELETE` 扫描到的行如果不满足 `WHERE` 条件，可以提前释放锁，让其他事务有机会修改这些行，从而显著减少锁冲突。

它的工程效果通常是并发更高，但范围幻读保护更弱。

### 2. REPEATABLE READ

在 RR 下：

- 普通 `SELECT` 复用事务快照。
- 当前读、范围修改更倾向使用 Next-Key Lock 保护扫描范围。
- 因此更容易出现范围锁等待，但能更强地抑制当前读语义下的幻读。

这也是 InnoDB 默认隔离级别下，很多锁等待都带有明显“范围特征”的原因。

### 3. READ UNCOMMITTED

在 RU 下：

- 普通 `SELECT` 不生成 Read View，直接读取最新的已提交或未提交版本（脏读）。
- 当前读和修改操作仍然加锁，但快照读完全不加锁也不依赖 MVCC。
- 由于脏读风险，生产环境极少使用。

### 4. SERIALIZABLE

在 SERIALIZABLE 下：

- 普通 `SELECT` 自动转换为 `SELECT ... FOR SHARE`，即所有读都变成当前读。
- 所有扫描范围都使用 Next-Key Lock 保护，锁范围最大。
- 并发度最低，但能完全避免脏读、不可重复读和幻读。

实际生产环境中，绝大多数系统使用 RC 或 RR，SERIALIZABLE 和 READ UNCOMMITTED 通常只在特殊场景下出现。

## 九、一次 UPDATE 为什么会被阻塞

把阻塞拆开看，通常只有几类原因：

1. 目标记录已经被别的事务持有 Record Lock。
2. 目标插入位置或扫描范围被别的事务持有 Gap Lock 或 Next-Key Lock。
3. 唯一键冲突检查需要等待对方事务结束。
4. 事务过长，导致锁一直不释放。
5. 执行计划退化，让本来应当很窄的锁扩展成大范围扫描锁。

因此排查锁等待时，核心不是只看 SQL 文本，而是同时看：

- 事务是否已提交。
- 实际使用了哪个索引。
- 隔离级别是什么。
- 语句属于一致性读、锁定读还是写操作。

## 十、死锁是怎样形成的

死锁不是锁很多才会发生，而是等待关系形成了环。

典型例子是：

1. 事务 A 锁住记录 1，准备更新记录 2。
2. 事务 B 锁住记录 2，准备更新记录 1。
3. A 等 B，B 等 A，形成循环等待。

范围锁也会制造更隐蔽的死锁。例如两个事务以不同索引路径扫描同一批数据，获取锁的顺序不同，就可能形成交叉等待。

InnoDB 会做死锁检测，并主动回滚代价较小的一方。但这只是止损机制，不是高并发设计的替代品。

## 十一、把执行流程和锁逻辑串起来看

如果要用一句更工程化的话总结 MySQL 查询与修改流程，可以这样理解：

- 优化器决定“从哪里找”。
- MVCC 决定“普通查询能看到哪个版本”。
- 当前读决定“修改前必须拿到哪个版本的控制权”。
- 锁管理器决定“这个控制权只覆盖一条记录，还是扩展到整个索引范围”。
- Undo Log、Redo Log、Binlog 决定“修改如何回滚、恢复、复制和提交”。

只要这五件事放在同一张图里，查询和修改的很多现象就会变得很好解释：

- 为什么普通 `SELECT` 不容易阻塞写。
- 为什么 `SELECT ... FOR UPDATE` 可能锁住一个范围。
- 为什么同样的 `UPDATE`，加上合适索引后锁冲突会明显减少。
- 为什么长事务会把锁问题放大到 DDL、复制延迟和 purge 清理上。

## 总结

MySQL 中一条查询或修改语句的真正执行过程，并不是“找到数据然后读写”这么简单，而是 Server 层计划、InnoDB 版本可见性、索引访问路径、事务锁和日志系统共同作用的结果。

对锁问题最实用的理解方式只有两条：

1. 先区分这次访问是快照读还是当前读。
2. 再沿着实际索引路径判断锁到底会落在哪条记录、哪个间隙、哪段范围上。
