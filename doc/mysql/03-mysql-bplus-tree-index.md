# B+ 树索引原理：为什么 InnoDB 选择 B+ 树

数据库索引不是抽象的数据结构练习题，而是直接面向磁盘 IO 成本的工程方案。InnoDB 将数据持久化在磁盘上，CPU 与内存的访问延迟以纳秒计，而一次磁盘随机读以微秒甚至毫秒计，二者相差四个数量级以上。索引设计的核心目标，因此不是"在内存里少比较几次"，而是"尽可能少读几个磁盘页"。

InnoDB 选择 B+ 树作为默认索引结构，正是这一思路的集中体现：通过高扇出、矮树形，把一次点查的 IO 次数控制在 2 到 4 次；通过叶子节点的双向链表，让范围查询可以在少量页内顺序扫描。本文从磁盘 IO 模型出发，对比二叉搜索树、AVL 树、红黑树、B 树与 B+ 树的差异，深入讲解 B+ 树的结构、操作过程、容量计算，以及 InnoDB 中的实际落地方式。

## 一、索引要解决的核心问题

### 1. 磁盘与内存的速度鸿沟

理解索引，首先要理解存储层次的速度差异。现代计算机的存储体系呈金字塔结构：寄存器与 L1/L2/L3 缓存最快，DRAM 次之，SSD 与 HDD 最慢。数量级上可以这样粗略对比：

| 存储介质         | 典型访问延迟      | 相对内存的倍数         |
|--------------|-------------|-----------------|
| L1 缓存        | 约 1 ns      | —               |
| 内存（DRAM）     | 约 100 ns    | 1×              |
| NVMe SSD 随机读 | 约 10–100 μs | 约 100–1000×     |
| SATA SSD 随机读 | 约 50–150 μs | 约 500–1500×     |
| 机械硬盘随机读      | 约 5–10 ms   | 约 50000–100000× |

一次内存访问与一次磁盘随机读的成本差距，远大于在内存中多做几千次整数比较的成本。因此，索引优化的首要指标是**磁盘 IO 次数**，而非**内存比较次数**。

#### 机械硬盘 vs SSD 的 IO 特性

**机械硬盘（HDD）** 的随机读成本主要来自两部分：

- **寻道时间（Seek Time）**：磁头移动到目标磁道，典型 3–9 ms。
- **旋转延迟（Rotational Latency）**：等待目标扇区转到磁头下方，7200 RPM 磁盘约 4 ms 平均。

顺序读时，磁头无需频繁移动，磁盘预读（read-ahead）可以一次拉取连续扇区，吞吐可达数百 MB/s。随机读时，每次 IO 都要寻道 + 旋转，IOPS 通常只有几百。

**固态硬盘（SSD）** 没有机械部件，随机读延迟大幅下降，NVMe 设备随机读 IOPS 可达数十万。但 SSD 仍有以下特点：

- 单次随机读延迟仍远高于内存（微秒 vs 纳秒）。
- 写入涉及擦除块、垃圾回收，随机写放大问题比顺序写严重。
- 操作系统与文件系统的 IO 路径（系统调用、块层调度）本身有固定开销。

因此，即使全面使用 SSD，减少随机 IO 次数仍然是数据库索引设计的第一原则。Buffer Pool 可以缓存热点页，但无法把整个数据库常驻内存；冷数据访问、缓存未命中、实例重启后的首次访问，仍然要落到磁盘。

#### 随机读 vs 顺序读的成本差异

可以用一个简化的数值例子说明差异。假设：

- 单次随机读延迟：0.1 ms（SSD 乐观估计）。
- 顺序读带宽：500 MB/s，16 KB 页顺序读取约 0.032 ms/页。

若一次查询需要 100 次随机读，总延迟约 10 ms；若改为 2 次随机读（定位）+ 98 次顺序读（扫描），总延迟约 0.2 + 3.1 ≈ 3.3 ms。索引的价值，正是把"大量随机跳转"转化为"少量层级跳转 + 局部顺序扫描"。

InnoDB 的预读机制（linear read-ahead、random read-ahead）进一步利用顺序读优势：当检测到某区（Extent）内连续多个页被顺序访问时，会提前异步读取相邻页，减少后续 IO 等待。

#### 局部性原理与预读

**时间局部性**：最近访问的数据很可能再次被访问。Buffer Pool 的 LRU 策略正是利用这一点，让热点页长期驻留内存。

**空间局部性**：访问某地址附近的数据的概率较高。B+ 树在同一叶子页内按 key 有序存放记录，范围查询`WHERE id BETWEEN 100 AND 200` 时，找到起始位置后可以在页内顺序扫描，并沿叶子链表进入下一页，避免反复从根节点重新定位。

InnoDB 以 16 KB 页为 IO 单位，操作系统与磁盘控制器也按块（通常 4 KB 或更大）对齐读写。索引结构必须与这一粒度对齐，才能充分利用每次 IO 读入的数据量——这正是 B+ 树"一个节点 = 一个页"设计的出发点。

### 2. 页粒度读取

InnoDB 管理磁盘数据的基本单位是**页（Page）**，默认大小为 **16 KB**（16384 字节）。这一大小在实例初始化时通过`innodb_page_size` 设定（可选 4K、8K、16K、32K、64K），初始化后不可更改。

页粒度读取意味着：

- 即使只需要一行中的几个字节，InnoDB 也必须将整个 16 KB 页读入 Buffer Pool。
- 写操作同样以页为单位：修改页内一个字节，该页即成为脏页，最终整页刷回磁盘。
- B+ 树的每个节点对应一个完整的 InnoDB 页，不存在"只读半页"或"跨页节点"的情况。

#### 一次 IO 能读多少数据

以默认 16 KB 页为例，一次磁盘 IO 读入 16384 字节。这 16 KB 并非全部用于存储用户索引项，InnoDB 页有固定的头尾开销：

| 区域                 | 大致大小  | 作用                 |
|--------------------|-------|--------------------|
| File Header        | 38 字节 | 页号、校验和、页类型等        |
| Page Header        | 56 字节 | 页内记录数、层级、自由空间指针等   |
| Infimum + Supremum | 26 字节 | 虚拟最小/最大记录，界定用户记录边界 |
| User Records       | 可变    | 实际索引项或行数据          |
| Page Directory     | 可变    | 稀疏槽位，加速页内查找        |
| File Trailer       | 8 字节  | 校验和                |

可用于 User Records 的有效空间约为 **16384 − 38 − 56 − 26 − 8 ≈ 16256 字节**（Page Directory 占用通常较小，此处为估算）。

对于 B+ 树**非叶节点**，每个索引项包含一个键值和一个指向子页的指针。若主键为 BIGINT（8 字节），InnoDB 页指针约 6 字节（4 字节页号 + 记录头等内部开销），则每项约 14 字节：

```
16256 ÷ 14 ≈ 1161 个键值
```

工程上常取 **扇出 B ≈ 1170** 作为估算值。这意味着一层非叶节点最多可以指向约 1170 个子节点——一次 IO 读入一个非叶页，就获得了 1170 个"下一层入口"。

对于 B+ 树**叶节点**，每个索引项的大小取决于行宽或索引列宽度。若平均每条记录约 1 KB（含主键、索引列、行头 overhead），则：

```
16256 ÷ 1024 ≈ 15.9 → 约 16 条记录/叶页
```

行越宽，每页能容纳的记录越少，但树高主要由非叶扇出决定；叶层容量影响的是"需要多少个叶页"，对点查 IO 次数的影响相对间接（点查只访问一个叶页）。

### 3. IO 次数 = 树的高度

B+ 树（以及 B 树）的查找路径是从根节点出发，逐层向下，直到叶子节点。每一层对应一次页读取（Buffer Pool 未命中时即为一次磁盘 IO）。因此：

```
点查 IO 次数（冷缓存）≈ 树高 H
```

这是索引设计中最重要的等式之一。比较次数在内存中完成，成本极低；IO 次数直接决定延迟上限。

假设树高 H = 23（平衡二叉树在 1000 万数据下的高度），每次随机 IO 0.1 ms，仅 IO 等待就约 2.3 ms，还不含 CPU 与锁开销。若 H = 3，IO 等待约 0.3 ms，差距一个数量级。

索引设计的核心目标因此可以精确表述为：

1. **降低树高 H**：减少从根到叶的路径长度。
2. **增大扇出 B**：让每个节点在固定页大小内容纳更多键和指针，使 H 随数据量 N 增长更慢。
3. **对齐页粒度**：一个节点 = 一个页，使每次 IO 的信息密度最大化。

后续章节将看到，B+ 树通过"非叶只存键"和"叶子链表"两项改进，在相同页大小下获得比 B 树更大的扇出，从而进一步降低 H。

## 二、为什么不用二叉搜索树、AVL 树、红黑树

内存中的有序数据结构（如 C++ `std::map`、Java `TreeMap`）常用平衡二叉树，因为它们的数据全在内存中，每次指针跳转只是缓存访问，成本可忽略。磁盘索引则完全不同：每个节点可能不在内存中，每次跳转可能触发一次磁盘 IO。扇出为 2 的二叉结构，在数据量稍大时树高迅速增长，IO 次数不可接受。

### 1. 二叉搜索树（BST）

**二叉搜索树（Binary Search Tree, BST）** 满足：左子树所有键小于根，右子树所有键大于根，左右子树递归满足 BST 性质。中序遍历得到有序序列，查找时从根出发，比较后向左或向右，平均时间复杂度 O(log N)。

BST 的致命问题是**高度不可控**：

- **有序插入导致退化为链表**：若按 1, 2, 3, …, N 顺序插入，每次新键都落在最右端，树变成一条向右的链表，高度 H = N。
- **查找复杂度退化为 O(N)**：查找第 N 个元素需要 N 次比较、N 次节点访问；若每个节点对应一次磁盘 IO，等价于全表扫描。

即使插入顺序随机，BST 高度的期望值约为 O(log N)，但最坏情况仍为 O(N)。生产环境无法依赖"数据恰好随机"这一假设。

**具体计算**：100 万数据，退化链表高度 = 1,000,000，需要 100 万次 IO；即使平均情况 log₂(10⁶) ≈ 20，仍需约 20 次 IO。对于磁盘索引，20 次随机 IO 已经是不可接受的延迟（SSD 上 2 ms 量级，HDD 上 200 ms 量级）。

### 2. AVL 树

**AVL 树**通过旋转操作维持严格平衡：任意节点的左右子树高度差不超过 1。这保证了树高 H = O(log N)，最坏情况也不会退化为链表。

对于 N 个节点，AVL 树高度上界约为 **1.44 × log₂(N + 2) − 0.328**。代入 N = 1,000,000：

```
log₂(1,000,000) ≈ 19.93
H ≈ 1.44 × 19.93 − 0.328 ≈ 28.4 → 约 28 层
```

100 万数据需要约 **28 次**节点访问；1000 万数据 log₂(10⁷) ≈ 23.25，高度约 **33 层**。

AVL 树解决了 BST 的退化问题，但**每个节点只存一个键值、最多两个子指针**，扇出固定为 2。在磁盘场景下：

- 每个节点对应一个 16 KB 页，页内只存一个键和两三个指针，空间利用率不足 0.1%。
- 无法通过"增大节点体积"来增大扇出——节点已经等于一整页，扇出仍然只有 2。
- 28 层意味着 28 次 IO，远超 B+ 树 3 层 3 次 IO 的设计目标。

AVL 树优化的是**内存比较次数**；磁盘索引需要优化的是**IO 次数**，二者目标函数不同。

### 3. 红黑树

**红黑树**通过颜色标记与旋转规则维持近似平衡，保证最长路径不超过最短路径的 2 倍，树高仍为 O(log N)，上界约为 **2 × log₂(N + 1)**。

对于 N = 1,000,000：

```
H ≤ 2 × log₂(1,000,001) ≈ 2 × 19.93 ≈ 40（上界）
实际高度通常约 20–24 层
```

与 AVL 树一样，红黑树扇出为 2，1000 万数据仍需约 23 层 IO。

**Java TreeMap 用红黑树是因为数据在内存中**：

- `TreeMap` 的节点通过 Java 对象引用连接，每个节点几十字节，不涉及 16 KB 页对齐。
- 一次查找 23 次指针跳转，每次跳转是 L1/L2 缓存访问或内存读取，总延迟约数百纳秒。
- 内存数据结构不需要考虑"一个节点 = 一个 IO 单位"的约束。

若把 TreeMap 的节点映射为磁盘页，23 次随机 IO 的延迟将是 TreeMap 的数万倍。这是内存索引与磁盘索引的根本分野。

### 4. 对比表格

下表对比各类树结构在磁盘场景下的表现（假设 N = 1000 万行，16 KB 页，冷缓存）：

| 结构    | 扇出 B   | 树高 H（量级） | 点查 IO 次数 | 空间利用率（每页）  | 范围查询   | 是否适合磁盘索引     |
|-------|--------|----------|----------|------------|--------|--------------|
| 二叉搜索树 | 2      | 最高 O(N)  | 最高 10⁷   | 极低         | 中序遍历   | 否            |
| AVL 树 | 2      | 约 33     | 约 33     | 极低（< 0.1%） | 中序遍历   | 否            |
| 红黑树   | 2      | 约 23     | 约 23     | 极低         | 中序遍历   | 否            |
| B 树   | 数百     | 约 3–4    | 约 3–4    | 高（> 90%）   | 需跨分支   | 是            |
| B+ 树  | 约 1170 | 约 2–3    | 约 2–3    | 高          | 叶子链表扫描 | 是（InnoDB 选择） |

结论：平衡二叉树（AVL、红黑树）解决的是"在内存中保持 O(log N) 比较"的问题；B+ 树解决的是"在磁盘中保持 O(log_B N) 次 IO"的问题，其中 B 为扇出（数百到上千）。数据库外存索引必须选择 B 树族。

## 三、B 树的结构与特点

B 树（B-Tree）是多路平衡搜索树，专为磁盘等外存设备设计。理解 B 树是理解 B+ 树的前提——B+ 树是 B 树的变体，InnoDB 在 B+ 树基础上做了针对数据库 workload 的优化。

### 1. 多路搜索树

**多路搜索树**的核心思想是：每个节点可以有多个子节点，而不是二叉树的两个。这样在相同的树高下，可以索引远多于二叉树的数据量。

一棵 **m 阶 B 树**（m ≥ 3）满足以下性质：

1. **每个节点最多 m 个子节点**，即最多 **m − 1 个键**。
2. **根节点**至少有 2 个子节点（非空树时）；**其他非叶节点**至少有 **⌈m/2⌉** 个子节点，即至少 **⌈m/2⌉ − 1** 个键。
3. **所有叶子节点在同一层**（绝对平衡）。
4. 节点内的键**有序排列**；节点内查找使用**二分查找**。
5. 对于非叶节点，键将子树划分为区间：第 i 个键左侧子树的所有键 < 第 i 个键，第 i 个键与第 i+1 个键之间的子树键值在该区间内。

**m 阶**中的 m 决定了节点的最大容量，进而决定扇出。InnoDB 的 B+ 树可以类比为"页满度约 1170 阶"的结构，但 m 不是固定配置项，而是由页大小和键值大小动态决定。

B 树节点的典型布局（对应一个磁盘页）：

```
┌─────────────────────────────────────────┐
│  [P0] K1 [P1] K2 [P2] ... Kn-1 [Pn-1]   │  非叶节点：键 + 子页指针
└─────────────────────────────────────────┘
         │       │              │
         ▼       ▼              ▼
       子树1   子树2          子树n

┌─────────────────────────────────────────┐
│  K1,Data1 | K2,Data2 | ... | Kn,DataN   │  叶节点：键 + 数据（B 树）
└─────────────────────────────────────────┘
```

指针数 = 键数 + 1（非叶节点）；叶节点在经典 B 树中既存键也存数据记录。

### 2. B 树如何降低树高

B 树降低树高的机制是**增大扇出**：一个 16 KB 页内存储数百到上千个键，一层就可以指向数百到上千个子节点，树高 H = O(log_B N)，B 越大 H 越小。

**计算示例：1000 阶 B 树**

设每个节点最多 1000 个键（1000 个指针），即 B ≈ 1000：

| 层数       | 节点数（最大） | 说明                    |
|----------|---------|-----------------------|
| 第 1 层（根） | 1       | 1000 个指针              |
| 第 2 层    | 1000    | 1000 × 1000 = 10⁶ 个指针 |
| 第 3 层（叶） | 10⁶     | 若每叶存 100 条记录 → 10⁸ 条  |

**两层**（根 + 叶，仅适用于极小表）：最多 1000 个叶节点，每叶 100 条 → **10 万条**。

**三层**：10⁶ 个叶节点 × 100 条/叶 = **1 亿条**。

对比 AVL 树 1000 万数据需要 33 层，B 树三层即可覆盖 1 亿数据，IO 次数从 33 次降到 3 次。这就是"用扇出换高度"的核心思路。

InnoDB 实际扇出约 1170（见第五节计算），三层 B+ 树可索引约 2190 万行（每叶 16 行），与上表量级一致。

### 3. B 树的局限

B 树虽然适合磁盘，但相对 B+ 树仍有两个关键局限：

#### 非叶节点也存储数据，减少了扇出

在经典 B 树中，**所有节点（包括非叶节点）都可能存储键值对**。非叶节点既要存键用于路由，又要存数据（或数据指针），占用了本可用于存放更多路由键的空间。

假设非叶节点中每个键值对占 200 字节（键 + 行数据摘要），16 KB 页只能存约 80 个键，扇出 B ≈ 80。三层 B 树容量约 80 × 80 × 100 = 64 万条，远小于"非叶只存键"时的 1 亿条。

InnoDB 的 B+ 树改进正在于此：非叶节点**只存键和子页指针**，不存行数据，扇出从 80 提升到 1170。

#### 范围查询需要中序遍历，效率不高

B 树的叶子节点**没有链表连接**。范围查询 `WHERE id BETWEEN 100 AND 200` 时，即使定位到 id=100 的节点，扫描到 id=200 的过程中可能需要：

- 在当前叶节点内顺序扫描；
- 到达叶节点末尾后，通过父节点找到"下一个"叶节点（中序遍历的后继）；
- 可能涉及向上回溯、再向下进入兄弟子树。

这一过程伴随大量随机指针跳转，无法像 B+ 树那样沿叶子链表顺序扫描。对于 OLTP 与 OLAP 中常见的范围查询、排序、`ORDER BY`、`GROUP BY`，B 树的效率明显低于 B+ 树。

## 四、B+ 树相对 B 树的改进

B+ 树（B+ Tree）是 B 树的变体，也是 **InnoDB 索引的实际结构**。它在 B 树基础上做了三项关键改动，每一项都直接服务于"减少 IO"或"优化范围扫描"这两个数据库核心需求。

### 1. 非叶节点不存储数据

B+ 树规定：**非叶节点只存索引键和指向子节点的指针，不存完整行数据**。所有行数据（或指向数据的指针）**仅出现在叶子层**。

这一改动的效果可以用数字说明。设主键 8 字节，页指针 6 字节，非叶项 14 字节：

- B 树非叶项若含 200 字节数据：16256 ÷ 200 ≈ **81 扇出**。
- B+ 树非叶项仅 14 字节：16256 ÷ 14 ≈ **1161 扇出**。

扇出提升约 **14 倍**，树高相应降低。对于 1000 万数据：

- B ≈ 81：log₈₁(10⁷) ≈ 3.7 → 需要 **4 层**。
- B ≈ 1170：log₁₁₇₀(10⁷) ≈ 2.4 → 需要 **3 层**（或 2 层非叶 + 1 层叶）。

少一层 IO，在毫秒级延迟预算中意义重大。

非叶节点职责也因此更清晰：**仅负责路由**，不参与数据存储。内部节点的键是"分隔键"（separator key），用于指引查找方向，不一定对应实际存在的行。

### 2. 叶节点形成双向链表

B+ 树的所有**叶子节点通过双向链表串联**，键在全局范围内有序。每个叶节点除了存储数据，还包含 `prev_page` 和 `next_page`指针，指向同层的前一个和后一个叶页。

范围查询的执行过程：

1. 从根到叶，定位到范围起始键所在的叶页（一次树查找，H 次 IO）。
2. 在叶页内顺序扫描，直到超出范围或页末。
3. 若未结束，沿 `next_page` 进入下一个叶页，继续扫描——**无需回到父节点**。
4. 重复直到超过范围上界。

这一设计使范围扫描的 IO 模式接近**顺序读**：叶页在逻辑上连续，InnoDB 的 linear read-ahead 可以预读后续叶页，进一步降低延迟。

对比 B 树：范围扫描可能需要在不同分支间来回跳转，IO 模式以随机为主，预读效果差。

### 3. 所有数据都在叶节点

B+ 树强制规定：**任意键对应的数据记录只存在于叶子节点**。非叶节点中的键仅作路由，不携带完整数据。

这一性质带来三个好处：

**查询路径长度一致**：任何键的查找都必须从根走到叶，路径长度 = 树高 H。不存在"在非叶节点命中则少一层"的情况，IO 次数可预测、可建模。

**点查与范围查的统一**：点查走 H 次 IO 到叶；范围查走 H 次 IO 到起始叶，再沿链表扫描。两种操作共享同一套叶子结构。

**全表扫描可只扫叶子层**：若需要遍历全部索引键（如 `SELECT id FROM t` 只查主键），可以沿叶子链表从左到右扫描，不必经过非叶节点。这称为
**索引全扫描（index-only scan on leaf level）**。

B 树在非叶节点也可能存数据，点查有时可在非叶终止，路径长度不一致，优化器难以统一估算 IO 成本；B+ 树则一律 H 次 IO，模型简单。

#### B 树与 B+ 树对比小结

| 特性        | B 树        | B+ 树      |
|-----------|------------|-----------|
| 非叶节点是否存数据 | 是          | 否         |
| 叶子双向链表    | 无          | 有         |
| 扇出（同页大小）  | 较小         | 较大        |
| 点查 IO 次数  | ≤ H        | = H       |
| 范围查询      | 中序遍历，随机跳转多 | 叶子链表，顺序扫描 |
| 全键扫描      | 需遍历所有节点    | 只扫叶子层     |
| InnoDB 采用 | 否          | 是         |

点查时 B+ 树必须走到叶子，理论上可能比 B 树多一层 IO；但更高扇出带来的更矮树高，通常完全抵消这一代价，且范围查询的优势在综合 workload 中更为显著。

## 五、B+ 树如何与磁盘页对齐

InnoDB 的 B+ 树不是抽象意义上的数据结构，而是与 16 KB 数据页严格绑定的物理结构。本节给出页内容量与扇出的详细计算，这些是估算树高、评估索引设计是否合理的基础工具。

### 1. 一个节点 = 一个数据页（16KB）

InnoDB 规定：**B+ 树的每个节点对应一个 InnoDB 索引页**，页类型为 `FIL_PAGE_INDEX`。这样设计的原因包括：

**IO 对齐**：磁盘与操作系统按块读写，读一个节点 = 读一页，无跨页碎片，无"读半页"浪费。

**Buffer Pool 对齐**：Buffer Pool 按页缓存，页是最小缓存单位。一个 B+ 树节点在内存中的映像就是一个 Buffer Frame。

**崩溃恢复对齐**：Redo Log 记录的是页的物理修改（如"在第 5 槽插入一条记录"），页是日志与恢复的基本单位。

**预读对齐**：InnoDB 的 read-ahead 以区（64 页）为单位检测访问模式，页边界与预读粒度一致。

若节点小于页，则扇出无法随页增大而增大，空间浪费；若节点大于页，则无法一次 IO 读完整节点。B+ 树与页等大的设计是外存索引的行业标准，Berkeley DB、PostgreSQL（B-Tree 实现）、SQL Server 等均采用类似策略。

InnoDB 索引页的大致布局：

```
┌──────────────────────────────────────────────────┐
│ File Header (38B)                                 │
├──────────────────────────────────────────────────┤
│ Page Header (56B) — level, n_recs, free space...  │
├──────────────────────────────────────────────────┤
│ Infimum (13B) → 虚拟最小记录                       │
│ Supremum (13B) → 虚拟最大记录                      │
├──────────────────────────────────────────────────┤
│ User Records — 有序链表，键 + 数据/指针              │
├──────────────────────────────────────────────────┤
│ Free Space                                        │
├──────────────────────────────────────────────────┤
│ Page Directory — 稀疏槽位                         │
├──────────────────────────────────────────────────┤
│ File Trailer (8B)                                 │
└──────────────────────────────────────────────────┘
```

非叶页 `level > 0`，存 `{键, 子页号}`；叶页 `level = 0`，聚簇索引存完整行，二级索引存 `{索引键, 主键}`。

### 2. 非叶节点的容量计算

**假设条件**：

- 页大小：16384 字节。
- 固定开销：File Header 38 + Page Header 56 + Infimum/Supremum 26 + File Trailer 8 ≈ **128 字节**（Page Directory
  动态，此处从简）。
- 可用空间：**16384 − 128 ≈ 16256 字节**（保守估计）。
- 主键类型：**BIGINT UNSIGNED，8 字节**。
- 子页指针：InnoDB 非叶记录中存储子页号（4 字节），工程估算中通常取 **6 字节**（包含记录结构开销）。
- 每条非叶索引项还需 **记录头（Record Header）** 约 5 字节。

**单条非叶索引项大小**：

```
8（键）+ 6（指针）+ 5（记录头）≈ 19 字节
```

更简化的工程估算（忽略记录头，与 MySQL 官方文档常用口径一致）：

```
8 + 6 = 14 字节/项
16256 ÷ 14 ≈ 1161 项
```

取整后 **扇出 B ≈ 1170**。

**影响因素**：

- 主键越长（如 UUID 字符串 36 字节），每项越大，扇出越小，树高增加。
- 页大小改为 32 KB，可用空间翻倍，扇出近似翻倍，树高降低。
- 复合主键使非叶项变宽，扇出下降。

**示例**：主键为 `CHAR(36)` UUID 时，每项约 36 + 6 + 5 = 47 字节，16256 ÷ 47 ≈ **346 扇出**。1000 万数据 log₃₄₆(10⁷) ≈ 2.5，仍约 3 层，但比 BIGINT 主键多一层 IO 的风险上升。

### 3. 叶节点的容量计算

叶节点存储完整行数据（聚簇索引）或 `{索引列, 主键}`（二级索引）。容量取决于**单行大小**。

**假设**：表平均行宽 **1 KB**（1024 字节），含：

- 主键 BIGINT 8 字节。
- 若干业务列。
- InnoDB 行头（约 5–25 字节，含 trx_id、roll_pointer 等）。
- 变长字段长度列表等 overhead。

**单叶页记录数**：

```
16256 ÷ 1024 ≈ 15.9 → 约 16 条/页
```

**更窄的行**：若行宽 200 字节，16256 ÷ 200 ≈ **81 条/页**。

**更宽的行**：若行宽 4 KB，16256 ÷ 4096 ≈ **3 条/页**；大字段可能溢出到溢出页，叶页只存 20 字节指针，此处不展开。

**二级索引叶项**：若索引列为 INT（4 字节），主键 BIGINT（8 字节），加记录头约 5 字节，每项约 17 字节：

```
16256 ÷ 17 ≈ 956 条/页
```

二级索引叶页往往比聚簇索引叶页能存更多条，因为不存完整行。

叶节点容量决定**叶页总数**，进而与扇出共同决定树高；点查只访问一个叶页，叶页内记录数影响的是页分裂频率与范围扫描的页数，不直接影响点查 IO 次数（点查 IO = 树高，与每页多少行无关）。

## 六、B+ 树的操作过程（详细讲解）

B+ 树的查找、插入、删除都发生在页粒度上，并与 InnoDB 的 Redo Log、Buffer Pool、 latch 机制紧密配合。本节按操作类型逐步展开，并给出具体数值示例。

### 1. 查找过程

**等值查找** `SELECT * FROM t WHERE id = 500`（id 为主键）的完整路径：

**步骤 1：定位根页**

根页号存储在数据字典中，访问固定。根页通常常驻 Buffer Pool（见第八节），首次访问后多为内存命中。

**步骤 2：根页内二分查找**

根页为非叶页（除非表极小，根即叶）。页内键有序，InnoDB 通过 Page Directory 的稀疏槽位加速定位：先槽位二分缩小范围，再在记录链表中顺序比较。

假设根页有键 `[100, 300, 700, 1000]` 和 5 个子指针 P0–P4：

- id=500 > 300 且 ≤ 700 → 走 P2 指向的子页。

**步骤 3：递归下降**

对 P2 指向的中间层页重复二分，直到 `level = 0` 的叶页。

**步骤 4：叶页内定位**

在叶页内找到 id=500 的记录，返回行数据。若不存在，报告未找到。

**IO 次数**：冷缓存下 = 树高 H（每层一次页读）。三层树 = 3 次 IO：根 + 中间层 + 叶。

**具体示例**（三层，扇出 1170，叶存 16 行）：

表共有 50 万行，树高 3。查找 id=250000：

1. 读根页（IO 1）：键分区 [0–1170×16), [1170×16–2×1170×16), … → 250000 在第 14 个中间节点区间。
2. 读中间页（IO 2）：进一步定位到第 15625 个叶页。
3. 读叶页（IO 3）：页内 16 条记录，二分找到 id=250000。

**范围查找** `WHERE id BETWEEN 100 AND 500`：

1. 树查找定位 id=100 所在叶页（H 次 IO）。
2. 页内顺序扫描，收集 id ∈ [100, 500] 的记录。
3. 若 500 不在当前页，沿 `next_page` 继续，直到 id > 500。

后续叶页的 IO 可能因 read-ahead 而部分重叠，实际延迟低于"每页一次随机 IO"的简单累加。

### 2. 插入过程

插入**总是在叶子层**进行；非叶节点只会在叶分裂时被动的"上推"键而更新。

**流程概览**：

1. 按查找路径定位应插入的叶页（与查找相同，H 次 IO 读路径上的页）。
2. 若叶页**未满**（free space 足够）：在有序位置插入新记录，更新 Page Directory，写 Redo Log，结束。
3. 若叶页**已满**：触发**页分裂（Page Split）**。

#### 叶节点未满：直接插入

假设叶页当前 15 条记录（容量 16），插入 id=501：

- 在 id=500 与 id=502 之间插入。
- 更新页内链表指针、Page Directory 槽位。
- 生成 Redo Log 记录，事务提交时随 WAL 持久化。

此过程不涉及树结构变化，不增加树高，也不更新父节点。

#### 叶节点已满：页分裂

叶页已有 16 条记录，再插入第 17 条。InnoDB 典型分裂策略（简化描述）：

1. **分配新页**：从索引段申请一个空闲页 NewPage。
2. **分裂记录**：将原页约一半记录移到 NewPage，原页保留约一半。分裂后两页记录数均约 8 条，满足 B+ 树"至少半满"的不变式。
3. **链表更新**：原页 `next_page` 指向 NewPage，NewPage 的 `prev_page`、`next_page` 接好双向链表。
4. **上推分隔键**：将 NewPage 的**最小键**（或分裂点键）插入**父节点**，作为分隔符，父节点中增加指向 NewPage 的指针。
5. **Redo Log**：分裂涉及多页修改，必须原子地写 Redo，崩溃恢复时重放。

**分裂向上传播**：若父节点插入分隔键后也**满**，父节点同样分裂，可能一直传播到根。若**根分裂**，B+ 树**增高一层**：旧根成为新根的子节点，新根只有一个键两个指针，树高 +1。

**示例**：四层变五层的极端情况很少见；常见的是叶分裂偶尔向上更新一层父页。自增主键插入总在最大键之后，新记录追加在**最右叶页**，该页满时才分裂，且新页在链表右端，父节点只需追加指针，传播路径短。随机主键（UUID）插入位置分散，分裂频繁且可能发生在任意层级，写入放大明显。

### 3. 删除过程

删除同样在**叶子层**完成；InnoDB 对删除的策略与纯教科书 B+ 树略有不同，引入了**标记删除**与**延迟合并**。

#### 标记删除 vs 物理删除

InnoDB 的 `DELETE` 通常**不立即物理移除页内记录**，而是：

- 将记录的 **delete mark** 位置 1（在记录头中）。
- 写入 Undo Log，供 MVCC 与 rollback 使用。
- 后续 purge 线程在不再有事务需要该版本时，才真正物理清除记录。

这样设计是因为 MVCC 要求旧版本对快照读可见，物理删除会破坏一致性读。

#### 页合并的触发条件（MERGE_THRESHOLD）

当物理删除（或 purge 后）导致页内记录数**低于阈值**时，InnoDB 可能触发**页合并（Merge）**或**借位（Redistribute）**：

- 若兄弟页有多余记录，从兄弟页**借一条**到当前页，避免合并。
- 若兄弟页也接近半满，则**合并**两页，从父节点删除对应分隔键。

InnoDB 使用 **`MERGE_THRESHOLD`**（默认 50，表示页满度的 50%）：当页内空间使用率低于 50% 时，才考虑合并。可通过 `MERGE_THRESHOLD` 选项为特定索引调整（MySQL 5.7+，通过 `ALTER TABLE` 的 `COMMENT` 语法或建表选项设置）。

#### InnoDB 的延迟合并策略

InnoDB **不会**在每次删除导致 underflow 时立即合并，原因包括：

- 合并涉及多页与父节点更新，IO 与 latch 成本高。
- 若紧接着有插入，合并后的页可能再次分裂，白白浪费一次合并 IO。
- 延迟合并让页内留有空闲，吸收后续插入，减少分裂。

因此，高频删除后表可能出现**页利用率下降**（数据行数不多但占页很多），此时 `OPTIMIZE TABLE` 或`ALTER TABLE ... ENGINE=InnoDB` 可以重建表，紧凑页布局。

**删除与树高**：合并可能导致根的唯一子节点上升为新根，树高减 1；这一操作相对少见，远少于分裂。

## 七、树的高度与数据量的关系

树高 H 与数据量 N、扇出 B、叶页容量共同满足近似关系 **N ≈ B^(H−1) × R**（R 为每叶平均记录数，简化模型）。本节给出与 InnoDB 默认页大小、BIGINT 主键一致的计算，并解释为何"三层 B+ 树"在工程中足够覆盖绝大多数 OLTP 表。

### 1. 具体计算

**基准参数**（与第五节一致）：

- 非叶扇出 **B = 1170**
- 聚簇索引每叶记录数 **R = 16**（行宽 1 KB）
- 树高 **H** = 从根到叶的层数（根算第 1 层）

**一层（H = 1）**：根即叶，仅适用于空表或极少数据。

```
最大行数 = 16
```

**两层（H = 2）**：根（非叶）+ 一层叶。

```
叶页数 ≤ 1170
最大行数 = 1170 × 16 = 18,720 ≈ 1.9 万行
```

**三层（H = 3）**：根 + 一层中间非叶 + 一层叶。

```
中间层节点数 ≤ 1170
叶页数 ≤ 1170 × 1170 = 1,368,900
最大行数 = 1,368,900 × 16 = 21,902,400 ≈ 2190 万行
```

**四层（H = 4）**：

```
第 3 层非叶节点数 ≤ 1170² = 1,368,900
叶页数 ≤ 1170³ = 1,601,613,000 ≈ 16 亿
最大行数 ≈ 1,601,613,000 × 16 ≈ 2.56 × 10¹⁰ ≈ 256 亿行
```

（实际受表空间大小、文件系统限制，不可能达到理论上限，数量级用于理解 H 的增长。）

汇总表：

| 树高 H | 点查 IO（冷） | 最大叶页数（约） | 最大行数（R=16） |
|------|----------|----------|------------|
| 2    | 2        | 1,170    | 1.9 万      |
| 3    | 3        | 136 万    | 2190 万     |
| 4    | 4        | 16 亿     | 256 亿      |

若行宽 200 字节，R = 81，三层容量：

```
1170 × 1170 × 81 ≈ 1.1 亿行
```

仍在一个数量级内。

### 2. 为什么说三层 B+ 树够用

**千万级数据只需 3 次 IO**：1000 万 < 2190 万，三层 B+ 树（BIGINT 主键、KB 级行宽）足够，点查最坏 3 次磁盘读。

**根节点常驻内存，实际只需 2 次 IO**：

- 根页在整个实例生命周期内访问频率极高，几乎总是命中 Buffer Pool。
- 中间层页在热点表上也有较高命中率。
- 冷缓存理论 3 次 IO，热运行时常为 **1 次 IO（仅叶页）** 或 **0 次（全在内存）**。

**与业务规模的对照**：

- 绝大多数 OLTP 单表在 **百万到千万** 行量级，三层足够。
- **亿级**单表仍可能在三层（窄行、大扇出）或四层（宽行、长主键），点查 3–4 次 IO 仍可接受。
- 四层以上在 InnoDB 生产中极为罕见，若出现应检查主键是否过长、页大小是否过小。

**树高不变的工程含义**：从 100 万行增长到 1000 万行，树高可能仍为 3，点查 IO 次数**不随数据量线性增长**——这是 B+ 树相对全表扫描的核心优势。全表扫描 IO 与行数成正比；B+ 树点查 IO 与 log_B(N) 成正比，B 很大时 log 增长极慢。

## 八、InnoDB 中 B+ 树索引的实际落地

InnoDB 不是"在表旁边挂一棵通用 B+ 树"，而是将**表数据本身**组织为 B+ 树，并在此基础上派生二级索引。理解聚簇索引与二级索引的叶节点差异，是理解回表、覆盖索引、索引下推的前提。

### 1. 聚簇索引

**聚簇索引（Clustered Index）** 即按**主键**组织的 B+ 树，**整张表的数据就存储在这棵树的叶子节点中**。

特点：

- **叶节点 = 数据页**：每条记录存完整行（含隐藏列 DB_TRX_ID、DB_ROLL_PTR 等）。
- **表数据物理顺序与主键逻辑顺序一致**：同一叶页内按主键有序；叶页之间通过双向链表按主键顺序连接。
- **每表一棵**：InnoDB 表必须有且仅有一个聚簇索引。若未定义 PRIMARY KEY，会选择第一个 UNIQUE NOT NULL 索引；若都没有，则隐式生成 6 字节 ROW_ID 聚簇索引（不推荐依赖此行为）。

没有 MyISAM 式的"堆表 + 独立索引文件"：除聚簇索引外，其他索引都依赖主键定位行。

**插入与主键顺序**：自增主键使新行总是插入**最右叶页**，分裂少、缓存友好；随机 UUID 主键使插入点分散，页分裂与碎片增加，这是 B+ 树物理特性与 schema 设计的交汇点。

### 2. 二级索引

**二级索引（Secondary Index）** 是除聚簇索引外用户创建的索引（`CREATE INDEX`、`UNIQUE` 除主键外等），每棵二级索引都是**独立的 B+ 树**。

叶节点存储：

```
{索引列键值, 主键值}
```

**不存完整行**。查找非索引列时需要**回表（Bookmark Lookup）**：

1. 在二级索引树上找到满足条件的索引项，取得**主键值**。
2. 拿主键到**聚簇索引树**上再查一次，取得完整行。

回表使一次查询可能访问两棵 B+ 树，IO 次数约为 **H₂ + H₁**（二级 + 聚簇）。若结果集很大，回表次数等于匹配行数，成本极高——因此覆盖索引（查询列全部在二级索引中）和 ICP（索引下推）是重要优化手段。

**一个表多棵二级索引**：每个索引独立维护，INSERT/UPDATE/DELETE 需更新所有相关树的叶页，索引过多会显著拖慢 DML。

**唯一二级索引**：叶页上索引键唯一，插入时可直接判断冲突；非唯一索引的写操作可能走 Change Buffer 延迟合并（唯一索引必须即时读页校验唯一性，不能走 Change Buffer）。

### 3. 根节点的特殊处理

每棵 B+ 树（聚簇或二级）的**根页号**记录在数据字典（InnoDB Data Dictionary）中，位置固定。实例启动后，任何使用该索引的查找都从这一页号开始。

**根页常驻 Buffer Pool**：

- 根页体积仅 16 KB，访问频率极高（每次索引查找必经）。
- 在合理配置的 Buffer Pool 下，根页几乎不会被 LRU 淘汰。
- 中间层页在较大表上也会被频繁访问，常处于热缓存。

因此，**实际生产中的点查 IO 往往少于理论树高**：三层树理论 3 次 IO，根与中间层命中内存后，可能只有叶页一次磁盘读，甚至全部命中。

MySQL 8.0 可通过 `INNODB_INDEXES` 等视图查看索引页统计；`page_no` 为 3 的页常为段头，根页号需从数据字典或`SHOW TABLE STATUS` 等间接推断，具体页号因表而异，但"根极小且极热"这一性质不变。

## 九、哈希索引与自适应哈希索引

B+ 树是 InnoDB 的**持久化索引**主体；哈希结构在 InnoDB 中仅作为**辅助加速**出现，不能替代 B+ 树承担范围查询、排序与持久化存储。本节对比二者，并说明自适应哈希索引（AHI）的适用边界。

### 1. 哈希索引的特点

**哈希索引**通过哈希函数 `hash(key) → bucket` 定位记录，等值查询平均 **O(1)**，无需树形 descent。

**优势**：

- 等值查 `WHERE id = 100` 在理想无冲突时，一次哈希计算 + 一次 bucket 访问即可。

**局限**：

- **不支持范围查询**：`WHERE id > 100` 无法利用哈希有序性。
- **不支持排序**：`ORDER BY id` 无法按哈希顺序输出。
- **不支持最左前缀**：复合键 `(a, b)` 的哈希通常对整体计算，无法单独用 `a` 查。
- **哈希冲突**：冲突时需链表或开放寻址扫描 bucket 内多条，最坏 O(N)。
- **扩容/rehash**：数据量变化时哈希表需 rehash，不适合作为磁盘持久化结构的主索引。

MySQL **Memory 引擎**支持显式 `HASH` 索引；**InnoDB 不提供**用户可创建的哈希索引类型，默认索引均为 B+ 树。

### 2. 自适应哈希索引（AHI）

**自适应哈希索引（Adaptive Hash Index, AHI）** 是 InnoDB **内部自动维护**的内存哈希结构，**不是**第二种用户可见的索引类型。

**工作原理**：

- 当 InnoDB 检测到对**某个 B+ 树索引页**的**等值查询**极为频繁（同一页内同一模式反复出现），会在内存中为该页构建哈希映射：`索引键 → 页内记录位置`。
- 后续相同模式的等值查，若命中 AHI，可跳过 B+ 树页内二分，直接定位记录。
- AHI 完全在内存中，**不持久化**；实例重启后需重新"学习"热点。

**什么时候有效**：

- workload 以**热点等值查**为主，如会话表、配置表、频繁按主键点查的同一批 id。
- 目标页已在 Buffer Pool 中（AHI 加速的是页内定位，不能替代读盘）。

**什么时候是负担**：

- 高并发混合负载下，AHI 的 **latch 竞争**可能成为瓶颈（多个线程访问同一哈希桶）。
- 范围扫描、全表扫描对 AHI 无帮助，维护哈希结构仍消耗 CPU。
- 部分压测显示关闭 AHI 后 TPS 反而上升，需以实际 workload 为准。

**参数与监控**：

```sql
-- 开关（默认 ON）
SHOW VARIABLES LIKE 'innodb_adaptive_hash_index';

-- 关闭（需评估）
SET GLOBAL innodb_adaptive_hash_index = OFF;
```

```sql
-- 查看 AHI 状态（部分版本）
SHOW ENGINE INNODB STATUS\G
-- 关注 INSERT BUFFER AND ADAPTIVE HASH INDEX 段：
-- Hash table size, node heap, hit rate 等
```

命中率没有全局统一的 `SHOW STATUS` 变量，需从 `SHOW ENGINE INNODB STATUS` 或 Performance Schema 中间接分析。若 hit rate 低而 latch 竞争高，可尝试关闭 AHI 做 A/B 对比。

**B+ 树与 AHI 的分工**：

| 能力   | B+ 树（持久化）    | AHI（内存辅助）   |
|------|--------------|-------------|
| 等值查  | O(H) IO      | 命中时 O(1) 内存 |
| 范围查  | 叶子链表         | 不支持         |
| 排序   | 支持           | 不支持         |
| 崩溃恢复 | 页 + Redo     | 无需（重建）      |
| 用户可控 | CREATE INDEX | 仅全局开关       |

InnoDB 选择 B+ 树作为唯一持久化索引结构，是因为 OLTP/OLAP 混合 workload 中范围扫描、排序、分页、`JOIN` 范围匹配远多于"纯等值且无范围"的场景；AHI 是在 B+ 树之上的**可选热点补丁**，而非架构替代。

## 总结

索引设计的本质，是在磁盘 IO 成本远高于内存操作的前提下，**用尽可能少的页读取找到目标数据**。InnoDB 选择 B+ 树，是这一原则在工程上的标准答案。

**从问题出发**：机械硬盘与 SSD 的随机读延迟比内存慢数个数量级；InnoDB 以 16 KB 页为最小 IO 单位，一次 IO 应承载尽可能多的路由信息；
**IO 次数 ≈ B+ 树高 H**，降低 H 是索引设计的第一目标。

**为何不用平衡二叉树**：BST 可能退化为链表；AVL 与红黑树虽 O(log N) 但扇出仅为 2，1000 万数据需约 23–33 次 IO，且每页空间利用率极低。它们为内存设计，不适合外存。

**B 树与 B+ 树**：B 树通过多路扇出降低树高；B+ 树进一步让非叶只存键（扇出约 1170）、叶层双向链表（高效范围扫描）、所有数据在叶（IO 可预测）。InnoDB 采用 B+ 树而非经典 B 树。

**容量与树高**：BIGINT 主键、16 KB 页下，非叶扇出约 1170，叶页约 16 行（1 KB/行）；**两层约 1.9 万行，三层约 2190 万行，四层约 256 亿行**。千万级 OLTP 表通常三层以内，点查冷缓存 3 次 IO，根常驻内存后常为 1–2 次甚至全内存命中。

**操作与落地**：查找从根到叶每层二分；插入在叶页，满则分裂并可能上推；删除多标记删除，低于 MERGE_THRESHOLD 才延迟合并。聚簇索引叶存完整行，二级索引叶存主键需回表；根页固定且极热。

**哈希的角色**：哈希等值 O(1) 但无范围与排序；AHI 为热点等值读提供内存加速，需监控 latch 与命中率，不能替代 B+ 树。

理解 B+ 树，等于理解 InnoDB 从优化器选路、执行器读页到加锁落点的共同物理基础。后续分析慢查询、索引设计、页分裂与表膨胀，都可以回到**树高 H、扇出 B、叶子扫描页数**这三个量上逐项量化。
